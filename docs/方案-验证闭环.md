## 一、先用 PA 的四条路径检验设计

以 F18「任务投递」为例。验收预期是 PA 能接收任务、启动它并通知本人。项目提供飞书替身、临时投递目录和 dev-loop 替身。协调方把立项时定下的预期对应到 S3、S4。开发可以用同一套工具自查。正式结果取交付提交上的复测。评审看到场景编号、实际行为和证据。对应版本部署成功后，协调方才更新功能清单。其他项目可以使用浏览器、接口或本地进程，通用层只处理选跑清单和检查结果。

| PA 场景 | 首批从哪儿动手 | 要拿到的证据 |
|---|---|---|
| S1 · PA039 设置通知 | 复用 `code/agent/test/self-started.test.ts` 的 A8，补核对保存非默认配置后的再次重启 | 设置没变时没有新通知。停机改值后恰好一条，带真实旧值和新值。保留两版证明 |
| S2 · PA024 投递目录 | 复用 `code/agent/test/task-delivery.test.ts` 中的移出项目、陌生目录用例，用同一份种子串起必要操作 | 已移出的目录仍在时没有“子文件夹不认识”。随后新建错名目录有提醒。保留两版证明 |
| S3 · PA046 原单重投 | 参考 `self-started.test.ts` 的 A7，但 A7 在一个用例里连着检查了首次拒绝、链路检查、重投和重复投递，所以要拆出一条只检查原问题的定向用例，目标断言命名为「原单重投」 | 第一次启动零次，只修其指向的开发卡，原样重投相同任务单后恰好启动一次。再投相同合法单仍只启动一次。保留两版证明 |
| S4 · 合法任务完成通知 | 沿用 `code/agent/deploy/snapshot.mjs` 的隔离场景，按同一任务编号检查飞书替身收到的消息 | 恰好一条完成通知才通过。只有停下通知、重复完成通知都失败。环境没启动时保存失败步骤和原始报错。此场景检验判定是否准确 |

从 PA 的 Git 历史定位到两组可供回放的提交。S1、S3 为 `07e7738 → 99654f7`，S2 为 `de0c930 → 3661ed3`。这两组提交尚待实际回放。制作证明时解析成完整提交号，并确认旧版确实走到目标断言。首批修复已在当前开发基线之前，直接拿今天的开工基线充当“修复前”会得出错误结论。[历史问题回放](分析-漏网问题回放.md)

**两版证据由谁跑。** G13 排在 PA 首批之后，所以首批 S1～S3 的两版证据由协调方在 PA 批合入后手工跑一次：在系统临时目录检出上面两组的旧提交和修复提交，装入 PA 批交付的同一份测试，分别运行，原始输出存进 PA 批次目录。PA 批的开发方只负责让这些测试在当前版本通过，并在断言里写出期望值和实得值。pi 开发会话的权限扩展是否允许在系统临时目录检出旧版本还没确认，确认之前不交给开发方做。

项目的“手”包括注入用户输入、制造外部事件、启停和重置环境、让依赖按剧本回应、预置数据。“眼”包括用户收到的消息、对外请求、内部状态、原始日志、耗时和用量。PA 的飞书替身可以注入带时间的原始事件、模拟断连并保存消息。模型替身可以检查请求里的规则、出处和工具响应。临时 Git 仓、任务目录与 SQLite 可以还原投递过程。每个场景单独隔离，用任务编号串起观察点。例如模型收到规则后，S5 仍须单独看实际回答是否引用了正确版本。

第一批可以先改项目的 `tasks[].test`，让同一命令保留原有测试并调用这四条路径。下文的卡字段等 G11/G13 生效后才填写。第一批的项目报告能区分环境故障，**现有核心仍会把非零退出计作复测失败**。报告里分别写项目结果和核心结果。S5 使用真实模型，按 D16 提请本批授权，评审后另行运行并绑定同一提交。授权前记录“授权未做”。若本批明确要求看到 S5 结果才部署，制卡时选用现有的“评审后停下”，协调方取得结果后再依本批授权安排收尾。

## 二、G11 怎样知道本次该跑什么

交付方继续使用一个项目测试命令。通用层需要在命令运行**之前**知道应收到哪些结果，否则脚本漏跑 S4 并返回零也会得到通过。建议在 `tasks[]` 增加可选 `e2e` 清单。协调方制卡时从起点版本的功能地图取相关条目，加上本批新增路径及立项确认的检查点。以下是只展示两条路径的字段示例。PA 首批的选跑范围是 S1～S4。

```json
{
  "e2e": [
    {"id": "S3", "paths": ["code/agent/src/task-delivery.ts"], "checks": ["首次拒绝", "原单重投", "合法单去重"]},
    {"id": "S4", "checks": ["同一任务完成通知"]}
  ]
}
```

每次交付按 `baseCommit → delivery.commit` 的累计改动选跑，重命名同时看新旧路径，删除也计入。省略 `paths` 表示本批每次必跑，填写后任一仓库相对路径或通配符命中即选，复用现有 scope 的匹配规则。协调方把共用模块列到所有受影响路径。刚新增的场景可以直接列为本批必跑。首版由协调方摘取地图，D19 的自动体检以后可以代办这一步。执行时的清单随卡存入 `task.json`，场景脚本不能通过少报一条来缩小范围。只在制卡时校验字段格式，场景和脚本可以由本批新建。 已批准脚本及种子用现有 scope.deny 保护。本批的新脚本放在允许修改的范围，协调方按立项预期和本次证据核对后纳入回归。

**开工后正式改了预期，清单怎么跟着变。** 本人正式修改验收标准时（写法第二节末尾的规则），如果增删了场景或检查点，协调方同步更新功能地图和开发卡上的 `e2e` 清单。G11 每次复测开始时，从卡的源文件重新读取清单，把清单的摘要和提示词、验收标准两份哈希一起绑定到检查记录：清单一变，旧的复测结论就不再算数，按新清单重新检查。这和现有「提示词或验收标准变了，旧结论自动作废」是同一个机制。普通的澄清不动清单，沿用原流程。例如后来给 S4 加上「重启以后不得再发完成通知」，就要同时给 S4 加这个检查点；只改验收标准文件、不动清单，新标准就会挂上旧检查的通过记录。

未声明 `e2e` 的卡、已在跑的旧任务继续按原测试命令和记录格式处理。声明了 `e2e` 而测试命令写“无”的卡，读卡时只提示两者冲突，不拒绝启动，不新增拒绝点。复测时照旧记「没验证」，但接入卡的合入资格只认「通过」或「本人接受环境缺项」（第四节第 3 条），所以拿不到合入资格；复测摘要和评审材料写明「声明了必跑场景，却没有执行命令」。选中零条时仍跑项目测试，在摘要中记“本次未选中 E2E 场景”。不把未选项目写成“未验证”。卡上已经声明的合入、部署、推送授权仍各自生效。[开发卡解析与路径匹配](../src/core/card.ts) · [执行登记](../src/core/store.ts)

## 三、一次复测怎样取证

核心在执行目录内为每次尝试创建独占子目录 `e2e/<本次编号>/`，先写 `plan.json`，内容包括执行编号、交付提交、两份输入哈希和选中的场景/检查点。通过拟新增的 `LOOP_E2E_DIR` 把该目录交给现有 `run`。项目按计划使用临时数据和替身，等就绪信号后操作，写证据到此目录，最后以临时文件改名的方式提交 `result.json`。失败和超时都保留原始输出，清理本次起的服务与临时数据。项目文件只描述观察结果，提交和哈希以核心写入的计划为准。[测试子进程入口](../src/core/run.ts)

下面是仅选中 S4 时的**格式样例**，编号和提交号为示意值。`unit` 是开发卡中 E2E 以外的普通项目检查，示例中已跑完。失败和未验证必须写出具体步骤、实际观察和证据。环境故障另附外部前置检查的实测结果及原始报错，例如隔离依赖无法建立连接。连接对象来自该场景事先列明的外部依赖，不能用产品自身启动失败来代替。

```json
{
  "executionId": "pa-demo",
  "attempt": "a2",
  "commit": "1111111111111111111111111111111111111111",
  "unit": "通过",
  "scenarios": [
    {
      "id": "S4",
      "status": "通过",
      "steps": [
        {"id": "同一任务完成通知", "status": "通过", "actual": "T17 收到 1 条完成通知", "evidence": ["S4/通知.json"]}
      ]
    }
  ]
}
```

程序把报告同本次计划逐项比对。每个选中编号只有一条结果。通过的场景必须覆盖每个预期检查点，每条证据指向本次目录内真实存在的普通文件。环境故障时可在首个未到达的检查点给出 `status: "未验证"`、`cause: "外部环境"`、`actual` 和诊断证据。被同一故障挡住的后续场景也逐项注明，可引用同一份报错。报告缺失、重复、版本串用、证据越出目录、声称通过却少了检查点，均记录实际原因。已有合格结论不会因事后挪走一张截图而作废。

正式报告还须回写计划中的执行编号、尝试编号和交付提交，程序逐一比对。本次目录首次创建时为空，证据路径经规范化后须仍位于该目录，防止误拿旧报告。检查点结论用“通过 / 失败 / 未验证”，诊断产物只存必要的脱敏输出。进入等待前须先写检查事实和原错，查询由此列出缺项。进入评审前复查输入仍与启动这次复测时一致。确认中断的是 dev-loop 自身时沿用执行器故障分支，项目脚本或报告错误则计入项目复测失败，两种情况都不会产生可接受的环境缺项。

| 本次观察 | 核心怎样记，接下来谁处理 |
|---|---|
| 项目测试通过，命令退出 0，所有选中的场景通过 | 追加「复测 / 通过」，给静态评审一份逐场景摘要和证据路径 |
| 普通项目检查失败，或某个产品断言失败 | 追加「复测 / 失败」，保留首个失败步骤，沿用开发返修计数。其他场景同时受环境影响时一并列出，仍先处理已知失败 |
| 已确认外部前置不可用，且没有已知产品失败 | 建议项目以专用退出码 75 配合完整报告。核心追加「复测 / 环境未验证」，保存场景清单，转「等你」（等待原因「复测环境未就绪」），不增加返修次数 |
| 脚本损坏、结果缺行、退出码与报告冲突或无法确定原因 | 保存命令、退出码和原始报错，摘要标明“检查未完成”及原因。项目脚本或报告的问题：追加「复测 / 失败」，退回开发，扣复测次数。确认是 dev-loop 自身中断：沿用执行器故障分支，转失败，不扣次数。两种情况都不能列为可接受的外部环境缺项 |
| 用户停止 | 沿用「已停止」，保留本次已写出的记录。迟到的报告不能覆盖停止决定 |

核心只在本次有完整且一致的证据时认可 75。仅凭“超时”“找不到文件”无法认定外部故障。PA 曾有九批找不到 `delivered/status.json`，这也可能是投递从未成功。先看替身有没有收到启动请求，再看状态文件，才能决定由谁修。项目普通检查与外部前置应分开运行，这样一个外部服务缺席不会盖住已知的测试失败。[历史现场](需求-验证闭环.md#现状数据) · [当前复测和评审入口](../src/core/settle.ts)

**记录和评审。** `checks.jsonl` 仍为判定出处。复测行沿用 `commit / tree / promptHash / acceptanceHash / result / evidence`，`evidence` 指向计划、报告和原始日志。增加可选 `missingScenarios` 保存实际缺项编号，使恢复及用户处理不依赖工作区里的文件。失败则把摘要随退回原因交给开发。走到评审才把当前结果和相关历史失败摘要放进现有“复测结果”段。`summary.md` 和批次 `结果.md` 引用同一组记录。纯测试卡也能从执行目录找到证据。

## 四、D20 怎样补跑，什么情况下能合入

假设 S1～S3 已通过，S4 因隔离服务未启动而未运行。`查询` 显示缺项 S4、原始错误和恢复入口。复用 `input_required / 等你`，新增等待原因“复测环境未就绪”。保留原 `testReturns` 和额度。

这个状态只接受三种操作：不带话的 `续跑`（补跑）、`续跑 <执行编号> --接受环境缺项 <尝试编号>`（接受缺项）、`停止`。`答复` 和带话续跑在这个状态下不送进开发会话，回执列出当前的尝试编号和这三种操作：外部环境不归开发方处理，送进去只会白开一轮。新等待原因要同步写进 README（`loop.wait` 从六种变成七种）。PA 的接手表是固定选项表，表里没有的等待原因不给任何操作，所以要同步加上这个原因（见第七节）。开卡预先声明 `无：原因` 时的旧结果“没验证”继续与 D20 分开记录。

**尝试编号要绑定到本人看到的那一次。** 等待消息（状态里的 `message`）必须写明本次的尝试编号和缺项清单；公开查询另给出 `尝试编号`、`缺项`、`能否接受` 三项，供 PA 生成命令。PA 现有的现场标记（`takeover.ts` 的 `sceneToken`）已经把 `message` 算进去，所以同一提交补跑后进入第 2 次等待时，标记会变，本人在第 1 次现场做的选择会被 PA 的 `--现场` 校验挡下（「现场已变化，请重新接手」）；dev-loop 这边也会拒收过时的尝试编号（A10）。两道检查都过，才产生接受记录。

1. **环境恢复。** 在该等待原因下，无附言的 `续跑` 重新核对登记交付、干净工作区和两份输入哈希。完全相同则在后台重跑该卡原来的复测命令，生成新的尝试目录，随后照常评审。首版整组补跑，省去把不同尝试的部分结果拼成一次通过。相同故障再次等待。产品断言失败则正常返修。输入或代码已经变化，转回常规交付检查。
2. **本人接受本次缺项。** 用显式参数 `续跑 <执行编号> --接受环境缺项 <尝试编号>`，不靠在答复里写固定字样。PA031「授权操作要求原话一字不差，输错就找不到」是同类的真实问题；PA 的接手表也只认固定选项。参数里的尝试编号必须是当前待处理的那一次，程序核对执行、提交、两份哈希和本次缺项集合，全部吻合才追加「复测 / 本人接受环境缺项」，记下这次操作、对应尝试和原始未验证记录，随后照常评审。编号对不上或已经过时，就拒收并给出当前待处理的编号。**只有普通测试（结果里的 `unit`）已经通过、剩余缺项全部是事先列明外部依赖的场景，才提供这个参数。** 普通测试也因环境没跑成（`unit` 为未验证）时，只能补跑或停止；有普通测试失败或材料不完整时，同样不提供。既有手工 `合入 --接受未验证` 是独立的显式操作，自动收尾不会代调。
3. **统一取资格。** 新卡的正常合入要求本次绑定下有效的复测「通过」或「本人接受环境缺项」，且独立评审通过。仅有「环境未验证」时不启动自动合入、部署或后继接力。旧卡仍按已有规则认「没验证」。交付复用、补评审、普通合入和自动收尾读取同一判定。结论仍仅绑定提交与两份输入哈希，不因其他批次的报告或证据文件变化失效。 对接入卡按同一绑定下最近一次完整的复测判定和对应的缺项处理取资格，避免现有 `some(曾经通过)` 跳过仍在等待的尝试。正常流程会先复用该绑定已完成的结论，不主动为同一版本重测制造新的否决点。
4. **停止、并发和恢复。** `续跑`（含接受参数）对同一等待记录在原执行锁内认领。后台取得执行权后再次检查提交、停止状态及未处理的等待事实。复用现有后台补评审的派发和宿主返修交接，环境恢复无需启动开发模型。记录已落盘而进程中断时，以本次尝试的完整记录恢复到下一步。半份报告只能重作本次检查。重复点击不会重复消耗额度、追加接受或启动两次收尾。

D20 是待批准的合入行为变化。真实依据是 PA 的必跑场景反复跳过却照常通过。实施时只影响明确登记 E2E 的执行。现有 `missingChecks` 同时接受“通过”和“没验证”，只改提示文案无法得到上述行为。[合入资格](../src/core/store.ts) · [复用与续跑](../src/core/lifecycle.ts) · [手工合入](../src/steps/merge.ts) · [自动收尾](../src/cli/finish.ts)

## 五、D12 怎样把陪跑并进复测

**G11 首卡只做交付版。** D12 定的是「并进 E2E，只看场景完成没有，状态变化交给程序判断」。G11 首卡完成交付版的检查，逐个检查点做断言；D12 里起点和交付两个版本的比较，待后续决定（见下文「起点对比」），不能当作已经完成。PA 那个场景连续 9 批被跳过，靠 S4 的断言就能抓住，不需要和起点比。

接入 G11 的同一场景，停掉旧的起点陪跑和交付快照的重复采集，场景证据进入复测。尚未接入的旧卡继续走原有的快照路径。部署前后用于回退和观察的线上快照仍由部署步骤管理，交给复盘当信号用。项目开发自查可以复用同一套手和眼，复测由程序触发。部署后的 `check` 只复用适合线上、已获准的冒烟检查。[现有陪跑](../src/cli/companion.ts) · [场景快照](../src/core/snapshot.ts) · [部署检查](../src/steps/deploy.ts)

**起点对比（暂缓）。** 用同一套场景在起点和交付两个版本上各跑一次、比较关键输出，属于文章第 2 课的差分测试，适合迁移、重写这类「旧系统就是标准答案」的场合。目前没有真实事故需要它，按 AGENTS.md「不为理论上可能加机制」，先不做。等出现真实的差分需求（例如 Promate v1 到 v2 的行为对齐）再启动。到那时要补的内容：场景项的可选 `compare`（要比的检查点）和 `changes`（已批准的旧值和新值，与提示词同一项）、起点版本的临时检出和构建、起点记录的复用条件，以及「环境不同或起点没跑到检查点时记未验证」的规则。

## 六、G13 怎样证明测试抓到了原问题

协调方用问题单确定一个可观察的错误，再选择仍含该错误的旧提交。普通修复批默认用开工时固定的 `baseCommit`。事后补测试的批次显式写历史提交。修复版固定为本批登记的交付提交。两边使用交付版本里**同一份测试、同一检查点、同一份种子**。旧版必须走到那个断言并产生单中描述的实际错误，修复版必须走到同一断言并得到预期结果。

**卡怎样声明。** 建议新增可选 `tasks[].proofs` 数组，启动时同样快照进 `task.json`。每项写问题单标识、场景、目标检查点、旧提交（缺省取起点）、需要带到旧版的测试文件、定向测试命令。下例路径和命令仅示范 G13 的提案格式，PA 项目内的实际文件由首批实现确定。单元测试层的证明把 `scenario`、`checkpoint` 换成 `testName`（定向测试名），其余字段相同。

```json
{
  "proofs": [{
    "issue": "PA046",
    "scenario": "S3",
    "checkpoint": "原单重投",
    "before": "07e7738",
    "testFiles": ["code/agent/e2e/S3.mjs"],
    "test": "node code/agent/e2e/S3.mjs"
  }]
}
```

**什么时候跑。** 修复批交付以后，协调方在准备关单时按执行编号发起一次拟新增的 `bin/loop 证明 <执行编号>`。它读取已登记的项目、提交和证明声明，可在开发工作区释放后运行。核心既不读取问题单目录，也不等待证明结束。交付版在普通复测中真实暴露的产品失败仍照常处理。

1. **还原两份产品。** 从同一仓库为旧提交和交付提交分别建立临时 detached worktree，复用 `checkout`。从交付提交的 Git 对象提取清单内的测试、替身和种子，只覆盖临时工作区里的测试材料。清单逐文件限制在项目明确的测试目录。产品源码、构建产物和产品依赖来自各自版本。两边用相同配置和构建步骤，在各自目录编译，避免旧版本误加载当前目录的产物。测试引入的辅助文件也须显式列出。任一版本、材料或运行前置不可得时，记录“未证明”和原始原因。[临时检出实现](../src/infra/checkout.ts) 版本引用在登记时解析并保存完整 SHA，限制在本仓库历史内。将交付版的指定测试文件按相同相对路径装入旧版与交付版，再在对应检出目录运行命令。证明用独立的临时配置和数据，不读正式凭证或共用运行中的服务。版本间 API 不兼容导致测试无法执行时，记录缺少什么适配。
2. **用同一个断言跑两次。** 目标观察值可以来自 G11 的结果文件（场景、检查点、观察值和原始证据），也可以来自定向测试本身：单元测试层的问题（回放里 11 张漏网单有 8 张属于这一层）用定向测试的名称和断言信息（期望值、实得值）作证，不必先改造成 E2E 报告。两边的命令都必须实际执行目标测试。旧版“红”要求目标断言命中问题单指定的错误观察值，并返回产品断言失败。修复版“绿”要求同一检查点的正确值和整个定向命令成功，两者齐全才记“已证明”。两边都过说明这条检查抓不到旧问题。两边都失败说明当前结果尚未满足预期。编译失败、导入失败、无测试被选中、环境故障或其他断言提前失败，都不能充当旧版的失败证明。旧报告若已含相同版本、测试内容、种子和检查点的完整证据可以引用。 为避免把无关异常算成“红”，断言应报告本次输入、所期待的业务值及实得值。例如 S3 的旧版在原样重投后实际启动 0 次、期望为 1。修复版同一处实得 1。证据从执行目录取，不能用复制到旧版的测试文件改变产品实现。 用定向测试作证时，**目标断言要有稳定名称**（断言信息里带检查点名，比如「原单重投」），或者为原问题单独拆一条定向用例。旧版必须在这条断言处失败，并且实得值符合问题单的描述（S3：原样重投后实得启动 0 次，期望 1 次）；修复版在同一处得到期望值，才记「已证明」。旧版在前面的步骤就失败、没走到目标断言的，记「未证明」。
3. **留给关单的人。** 每次证明在执行目录独立保存两版完整 SHA、测试材料摘要、定向命令、目标断言的预期与实得、两份日志和判定。向 `checks.jsonl` 追加「防复发证明 / 已证明或未证明」，在批次 `结果.md` 按问题单链接。任务锁防止同时为同一份声明重复执行，重试保留旧尝试并用同一个记录编号防止重复写摘要。临时目录只清理由本次调用创建的部分，先归档证据再清理。已有完整相同证明可复用。
4. **由协调方关单。** 按 D9 提案，结合修复批复测、评审、问题单字段与防复发证据决定能否归档。用 REVIEW.md 防复发的个案，引用“新规则在旧问题 diff 报出目标、在已知正常对照中不误报”的回放。三层都拦不住时按写法记录原因。涉及真实账号的证据仍须另获授权。S4 的判定反例属于测试本身的检查，G13 不要求为它虚构一个产品修复提交。[问题单的关单条件](写法-需求提示词与验收标准.md)

## 九、并入的 bug 单：链路入口（G20）

[问题单](../issues/【bug】已提交的任务漏登记或反复催交付，超长复测日志使评审重复失败.md)记的是 Promate B4 的三处卡点。它们都在链路入口：交付登记不上，后面的复测、E2E、评审就都跑不起来。决定见需求 D21~D24。

**① 交付候选只提醒一次（D23）。** 会话停下时，「待交付的候选」包括：HEAD 领先于起点或上次登记的提交，或者工作区有未提交改动。

```
会话停下
  ├─ 已经登记交付，代码也没变 → 照常进复测
  └─ 有候选
       ├─ 这个候选还没提醒过 → 提醒一次：当前提交 · 上次登记的提交（或「还没登记」）· 交付命令
       └─ 候选没变，又停下了 → 立即转「等你」（停下没交付），消息里列出上次登记和当前提交
```

首次只提交没登记、返修后只提交没登记，走同一条判断。候选以「当前提交 + 未提交文件清单」来区分，换了提交或改动清单变了，算新候选。只有未提交改动时，照常提醒开发方交付。

**② 本人确认交付（D22）。** 「等你」时，只有任务分支正确、工作区干净、有未登记的提交 B，才提供「用当前提交 B 交付」；PA 接手表同步加这个选项，编号绑定本人看到的现场（和第四节同一个办法）。确认后在执行锁内重新核对提交、分支和文件范围；期间变成别的提交或出现未提交修改，就保留现场，让本人重选。登记成功后由程序直接推进复测，复用后台补评审的派发方式，不等已经停下的会话再停一次。现有 `交付` 在「等你」时拒收、还会暂存并提交工作区改动，所以这里要单独接入登记逻辑，不复用它。

**③ 评审材料瘦身和超限识别（D24）。** 正文保留需求、验收标准和完整代码差异。复测日志只放摘要：命令、结果、通过和失败的条数、失败的测试名、末尾若干行，同时限制行数和总字节，避免一行超长输出把摘要撑满；另附原文路径和大小，评审需要时自己去读。B4 当时手工这么做，材料从 7,597,553 字节降到 320,674 字节，评审随即拿到了有效报告。G11 的 E2E 证据照同一条规则放进评审材料。上下文超限的原错只在评审模型的会话记录里（B4 两次评审的输出文件各只有 120 字节），所以评审调用结束后要读这份会话记录的结束原因：识别到超限，就展示模型原错，不拿同一份输入原样重投；普通的临时故障保留现有重试。

**④ 会话说明写清楚（D21）。** dev-loop 的开发会话说明加一句，和本人修改后的全局规则保持同一层意思：「本会话是本人已明确授权由 dev-loop 管理的开发卡；开发完成后按本批说明登记交付。」全局规则由本人改，dev-loop 不动。
