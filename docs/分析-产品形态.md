# 分析：dev-loop 的产品形态

> 2026-11-11 记录，供以后回看。依据为当天的 README、AGENTS.md、`src/` 源码，以及 `~/.dev-loop/tasks/` 下 8 次真实执行的 `summary.md` 和 `checks.jsonl`。
> 标「判断」的条目是分析者的看法，不是实测结论。

## 一、定位

dev-loop 是 **agent 开发的质检闭环**。它不是 agent，也不是编排平台。它位于「派活的一方」和「干活的 agent」之间，只回答一个问题：**凭什么算干完了。**

```
派活   人 / PA：写开发卡、提示词、验收标准
  ↓
dev-loop：独立复测 + 独立评审 + 自动退回 + 只认 commit
  ↓
干活   pi（可换）
  ↓
附加   合入 / 推送 / 部署（人显式触发）
```

和 pi 的关系：pi 定位是轻量零件（能关的都能关，有非交互模式、事件钩子，会话可指定和恢复），dev-loop 是装这个零件的上层体系。dev-loop 的主见是**不信执行者自己报的完成**：执行者运行 `交付` 后，由内核独立复测、另开干净的评审进程，结论只绑定 commit、提示词哈希和验收标准哈希。

## 二、结构要点

| 组成 | 在 dev-loop 里 |
|---|---|
| 推进内核 | `settle()`，三家宿主共用的唯一推进点；顺序固定为开发 → 复测 → 评审 |
| 节点 | 3 个核心节点加附加步骤（合入、推送、部署）；5 种 state，19 个阶段 |
| 执行者 | 开发用 pi（sol/max，可写）；评审用 pi（astra/xhigh，只读、全新上下文，关闭扩展、技能、上下文文件），可用 `reviewerCmd` 替换；复测用 shell |
| 挂载点 | pi 用扩展事件（`session_start`、`agent_before_settle`、`session_shutdown`）；Claude/Codex 用钩子 |
| 系统工具 | `bin/loop` 命令、git、infra；其中「交付」是交给执行者自己调用的 |
| 判定依据 | commit + 提示词哈希 + 验收标准哈希，记录在执行目录的文件中；聊天内容不参与判定 |

执行者在内核层面可替换（开发卡 `host` 可选 pi/claude/codex），但接入层目前只完成了 pi。Claude/Codex 不能自动开会话，插件没安装，受 Stop 钩子时限约束，也没有心跳和状态栏。

## 四、价值（判断）

| 价值 | 依据 |
|---|---|
| 人只在关键点出现 | 「等你」只有 4 种原因；实际运行中一次都没触发 |
| 结论可信 | 只认 commit 加需求哈希，执行者在聊天里的说法不参与判定；评审看不到开发聊天 |
| 窄而硬 | 只做一圈；2000 行上限和依赖方向都有测试守着 |

## 五、短板（判断）

| 短板 | 严重度 | 说明 |
|---|---|---|
| 质量上限取决于输入 | 🔴 | 「通过」= 开发卡的测试命令通过 + 评审模型静态看过。测试弱则通过弱。瓶颈在开发卡和验收标准的写法上 |
| 没有合入后的反馈 | 🟡 | 不知道「评审通过」的代码合入后出了多少问题，这是验证 dev-loop 核心价值最缺的数据 |
| 只能处理单张卡 | 🟡 | 多任务、整合、验收（第 3 步）未实现 |
| 不加速开发 | 🟡 | 省的是人检查和来回的时间，不省执行者的时间 |
| 个人工具形态 | 🟡 | 写死本机路径（node、pi 的位置），只支持 macOS 终端，中文命令，Claude/Codex 接入未验证 |
