## 预期结果

### 总体结构 ✅

```
                        你 / PA
        看：一行状态、状态文件  ▲   │  做：派工、答复、续跑、停止、发布
                               │   ▼
┌──────────────── 接口层：bin/loop 命令 + 状态文件 ────────────────┐
└──────────────────────────────────────────────────────────────┘
┌──────────────── 核心（每个任务一份，多个任务并行） ──────────────┐
│  建 worktree + 任务分支 → 跑项目 setup 命令（装依赖）             │
│  开发会话（pi / Claude / Codex）                               │
│    开发（自测）→ bin/loop 交付 → 复测 → 评审 → 完成             │
│        ▲                           │        │                 │
│        └──── 退回（测试输出 / 必修，有上限，到上限交给人）───┘   │
│  检查记录：按 commit 记复测、评审的结果                          │
│  状态文件：按 PA 约定的字段，每次变化重写，运行中定时心跳         │
└──────────────────────────────────────────────────────────────┘
┌──────────────── 附加步骤（卡上选配，按顺序跑） ─────────────────┐
│  整合：各任务分支 git merge 进批次分支，冲突就退回对应任务        │
│  验收：按验收标准逐条跑，失败项用核心的「退回」送回责任任务      │
│  合入：把检查过的 commit 合进 dev 并推送（PA 的「发布」就是这个）│
│  部署：项目自己的脚本（CI/CD，本期不做）                         │
└──────────────────────────────────────────────────────────────┘
```

- ✅ 核心只管「开发 → 复测 → 评审」这一圈，验收不放进核心。
- ✅ 依赖只有一个方向：附加步骤只能调用核心对外的命令（查状态、读检查记录、退回），核心不知道附加步骤的存在。加步骤或去掉步骤都不碰核心。

### 一个任务的一圈 ✅

```
开发（开发方边写边自测，跑到通过）
  ▼
开发方运行 bin/loop 交付：程序把 scope 内的改动提交成 commit 并登记，马上返回
  ▼
会话停下（pi 的 agent_before_settle / Claude、Codex 的 Stop hook）
  ├─ 交付之后又改了代码 → 提醒重新交付
  ▼
复测：在任务 worktree 里原样跑卡上的测试命令
  ├─ 失败 → 把命令、输出末尾、错误行退回原会话（pi 用 continue:true，Claude/Codex 用 exit 2）
  ▼
评审：新上下文，输入是提示词 + 验收标准 + diff + 复测命令和结果，只报正确性，跳过风格
  ├─ 有必修 → 退回原会话，每条写清 文件:行 和触发条件；建议只记进文件，不退回
  ▼
完成：检查记录里这个 commit 有「复测通过、评审通过」两条
```

- ✅ 测试分两层：开发方自测，交付后程序再跑一次脚本复测。复测不是单独的节点，没有自己的会话、预算、排队或隔离检出。
- ✅ 交付信号用 `bin/loop 交付` 命令，不再解析【交付完成】文本。
- ✅ 复测失败不再分产品、环境、方法、未知，一律把输出退回开发方，由开发方自己判断、自己修。开发方判断是环境问题、自己处理不了时，转「要你决定」，并写明原因。
- 🔧 退回次数：复测退回和评审必修分开计数，默认分别 3 次和 4 次，到上限后状态改为「要你决定」。
- 🔧 时限沿用现有默认：复测 20 分钟，评审每轮 60 分钟，卡上可以改。
- 🔧 卡模式下每个任务都建 worktree。另外保留「在当前目录直接开发」的单会话模式，走同一圈逻辑，只是不建 worktree。

### 信息放在哪 ✅

原则：信息放在 git 里的文件中，消息只用来通知，不改变任何结论。

```
项目仓库（git，唯一的事实来源）
  docs/prompt/提示词-X.md           需求；改需求就改它
  docs/batches/X/开发卡.json         任务、scope、测试命令、选了哪些附加步骤
  docs/batches/X/验收标准.md          附加的验收步骤用
  任务分支                            成果；每次交付对应一个 commit

~/.pi-autoreview/runs/X/<任务>/
  状态.json                          给你和 PA 看
  检查记录.jsonl                      追加写：commit → 复测、评审的结果和耗时
  测试-<commit>.log、评审-<commit>.md  证据
```

| 通道 | 做法 |
|---|---|
| 开发 → Loop | `bin/loop 交付` |
| Loop → 开发 | 测试失败：给命令、末尾几十行和错误行。评审：只给必修 |
| Loop → 评审 | 提示词 + 验收标准 + diff + 复测结果 |
| 你 / PA → 开发 | 聊天只是聊天，不作废结论；改需求就改提示词文件，由提示词变化触发重审 |
| Loop → 你 / PA | 一行状态（开发中、复测中、评审中、等你、完成、失败、已停止）+ 一屏以内的总结，细节写进文件、给路径 |

### 底线规则（只留这六条，由程序强制） ✅

| 规则 | 作用 |
|---|---|
| 多任务卡必须选验收步骤，验收标准每条都标明归属任务（沿用 `[任务名]` 写法；[人工] 条目不标） | 启动时检查卡，不合规就拒绝并写明改法；只检查卡，不牵连核心 |
| 结论只绑 commit，加上提示词和验收标准的内容 | 聊天、原目录文档、构建产物、证据文件在不在，都不作废结论 |
| 复测不过不评审，评审有必修不算完成 | 保住核心价值 |
| 退回有上限，到上限交给人 | 防止死循环（pi 不自带上限） |
| 交付时只认 scope 内的改动 | 越界就拒绝交付，指出越界的文件 |
| 合入只合检查过的那个 commit，不碰 main，不强推 | 版本不符就拒绝；没检查过的 commit 要你明说接受 |

### 速度怎么保证

原则 ✅：和直接用 pi + Astra 相比，Loop 多出来的时间只能是复测和评审本身。

| 措施 | 针对的浪费（证据） |
|---|---|
| ✅ 同一个 commit 的结论一直有效，交付、续跑都直接沿用，不重跑 | PA 甲评审通过 4 次、测试通过 2 次，全部作废 |
| ✅ 先复测后评审，测试不过不花评审时间 | 00:11 评审通过，00:12 测试失败，00:33 又重审一遍 |
| ✅ 复测只跑任务自己的测试命令，不跑全量；直接在 worktree 里跑，不建隔离检出 | 3 次测试被 Loop 自己的隔离中断；全量基线一次 10–15 分钟 |
| ✅ 评审只报正确性，跳过风格 | 内核每一步都评审 3–7 轮；官方说法是「要求找问题的评审总能找到点什么」 |
| 🔧 返修轮的评审只看「上轮必修解决了没有 + 本轮新改动」，首轮才看完整 diff | 每轮都重审全部，单轮 2–11 分钟 |
| ✅ 评审输入只给提示词、验收标准、diff 和复测结果 | 单轮评审输入最大 213KB |
| ✅ 任务并行，默认不排队 | 本机测试和验收共用一个排队槽 |
| 🔧 项目如果声明「测试不能同时跑」，只在这个项目内排队 | 并发跑全量时出现过大量计时类假失败 |
| ✅ 不需要人盯：交付靠命令，失败自动退回，只有到上限或开发方要你决定时才找人 | 6 条协调消息里有 5 条在解释 Loop 自己的问题 |
| ✅ 每一步都计时，总结里分列开发、复测、评审、等你、Loop 自身各花了多久 | 现在看不出时间花在哪 |

🔧 目标值（是设计目标，不是验收标准）：
- 不算开发、测试命令和评审模型的时间，Loop 自身每圈不超过 30 秒。
- 读状态不超过 1 秒。
- 交付后会话一停，10 秒内开始复测。

### 对 PA 的接口 ✅

字段和指令以 PA 需求书第七节「统一接入约定」为准，本单不复写。

| PA 的指令或字段 | 在 Loop 里是什么 |
|---|---|
| 状态报告（5 种执行状态） | 状态文件。开发中、复测中、评审中都算「进行中」，另有等你、完成、失败、已停止 |
| 心跳、序号、约定版本、代次 | 运行中定时重写状态文件，每写一次序号加 1 |
| 简要查询 | 读状态文件 |
| 任务定义与验收标准引用 | 提示词和验收标准文件的路径 |
| 派工 | `bin/loop 启动 <开发卡>`，带上派单编号 |
| 答复 | 消息直接送进会话，记一笔来源「经 PA」，不作废结论 |
| 续跑、停止 | `bin/loop 续跑` / `bin/loop 停止` |
| 发布 | 附加步骤里的「合入」，带上你确认的 commit，不符就拒绝 |
| 逐条验收结果与证据 | 由附加的验收步骤写出；卡上没选验收，就全部按「要你看」 |
| 能力声明 | 一份静态声明 |
| 指令去重 | 派工、答复、续跑、停止、发布每条指令都带编号。编号重复时，返回第一次的结果，不执行第二次；结果说不清就如实报「说不清」，不重发（需求书-PA 第七、八节） |
| 回执 | `启动` 几秒内就返回执行编号；建 worktree、跑 setup 放在返回之后。回执不等于已开工 |
| 发现与完整列表 | 所有状态文件放在一个固定根目录下。`bin/loop 查询 --all` 有简要版，一次返回全部执行，并标明「覆盖完整」，PA 才能据此判断「没有活动任务」 |
| 失败 | 复测失败属于 worker 自己返修，不算失败。Loop 自身的失败（setup、git、评审调用重试后仍失败等）才报「失败了」，按 PA 的六类错误类别归类，并原样附上原始报错 |
| 进程可达 | 状态文件写入开发会话的进程身份（进程号和启动时间），供 PA 判断是否意外退出 |
| 要你决定 | 状态说明写清要决定什么、有哪些选项（如再给它一轮、停止、接受未验证） |

🔧 心跳：pi 由扩展定时重写状态文件。Claude、Codex 没有常驻进程，只能在每次工具调用和 Stop 处理时重写，所以模型连续 15 分钟不调工具会被 PA 判成交接断。PA 派工的卡用的是 pi，主路径不受影响。

两张 PA 对接单的承接方式（11-09 已写进各单）：
- **统一接入**：状态文件在第一步随核心一起写出，读状态、简要查询和心跳当时就能用。派工、答复、续跑、停止和能力声明在第四步补齐。
- **安全发布**：本期发布就是附加的「合入」步骤，即合入本人确认的 commit 并推送 origin/dev。部署和回退移到以后的 CD。

### 附加步骤：验收、合入、部署与 CI ✅

```
Loop 核心         开发 → 复测 → 评审                        本期
Loop 附加步骤     整合 → 验收 → 合入（= PA 的「发布」）        本期
                                 └→ 部署（CD）              以后
项目自己的 CI     推到 origin/dev 后跑全量测试                以后
```

| 部分 | 做法 |
|---|---|
| 整合 | 各任务完成后，依次 git merge 进批次分支；冲突就退回对应任务，不扣验收次数 |
| 验收 | 复用现有的自动验收执行器（`acceptance.ts`、`acceptance-core.ts`），剥掉它和内核缠在一起的部分，在批次分支上统一跑一次。失败条目只退回名下有不通过条目的任务；这一轮返修的任务全部重新整合后，统一重验一次，范围是「不通过的条目 + 返修任务名下的全部条目」，未返修任务已通过的条目沿用（沿用 11-06 的决定）。[人工]、[授权] 规则不变。验收有自己的返修计数，🔧 默认 3 次 |
| 合入 | 只合入复测、评审（以及卡上选了的验收）都在这个 commit 上通过的版本，推送 origin/dev；版本不符就拒绝。`--接受未验证` 和 `--仅本地` 保留 |
| 部署 | 现有 `deployment-node.ts`（cmd、check、失败回退）以后挂在合入之后，本期不做 |
| CI | Loop 不当 CI。全量测试以后放到推送 origin/dev 之后，由 GitHub Actions 跑。两个仓库目前都是公开的，公开仓库用 GitHub 托管机器跑是免费的。Loop 的测试能不能在 GitHub 的机器上跑通，⏳ 还没验证 |

### 与 11-06 设计（【req】Loop内核与节点编排）的关系 ✅

方向没有推翻，推翻的是「内核要证明一切」这种实现方式。

| 11-06 的决定 | 本单 |
|---|---|
| 固定步骤由卡来选，编排由协调方写进卡、不由模型临时决定；每张卡都要评审；结论绑在代码上，没变就复用；Loop 不跑全量测试 | 保留 |
| 并行开发、批次分支、统一验收一次、按归属定向退回、定向重验；多任务必须带验收 | 保留，移到附加步骤 |
| git 是唯一记录、程序代为提交、隐藏 worktree 合入后删除、只推 origin/dev、不碰 main | 保留 |
| 状态说真话、拒绝合入时列出欠项和补救命令、接受未验证、能认出 Loop 外的合入 | 保留 |
| 开发评审是原子能力，测试排在评审之后 | 改成「开发 → 复测 → 评审」作为一个原子圈，测试提前 |
| 各节点独立预算 | 核心只留复测退回和评审必修两个计数，验收单独计数 |
| 测试和验收在本机排队 | 去掉。默认不排队，项目声明了才在项目内排队 |
| 其他节点运行时工作区一变，结论就作废 | 去掉，只看 commit |
| 失败分产品、环境、方法、未知四类分别处理 | 复测失败一律退回开发方 |
| 实现时加上的账本指纹、隔离检出、释放证明、贡献映射 | 去掉（这些不在 11-06 的需求单里） |

```
设计原则「任何不确定就拒绝或作废」

```

分层归因：设计层（定位成证明者）是主因；实现层（指纹范围、隔离检出）放大了它；流程层（文本标记、送话算需求）需要人一直盯着。

## 验收标准

A1. 操作：在一个测试仓库里，用单任务卡分别通过 pi、Claude Code、Codex 启动。开发方改完代码后运行 `bin/loop 交付`。
    预期：会话停下后，程序跑卡上的测试命令，通过后启动评审。评审通过后状态是「完成」，检查记录里这个 commit 有复测通过、评审通过两条。
A2. 操作：让开发方交付一个会让测试失败的改动。
    预期：不启动评审。测试命令、输出末尾和错误行退回原会话，开发方接着修改。
A3. 操作：让评审给出必修，开发方修完再交付；再构造一次连续退回到上限的情况。
    预期：退回内容只有必修，每条带文件:行和触发条件。修完再交付时先复测再评审。到上限后状态是「要你决定」，并写明原因。
A4. 操作：评审通过后，在开发会话里问一句「完成了吗」，修改原目录的 AGENTS.md，在任务工作区跑一次构建，然后查询并合入。
    预期：这个 commit 的结论仍然是通过，查询显示「完成」，合入时不需要接受未验证。
A5. 操作：对已检查通过的同一个 commit 再交付一次，再续跑一次。
    预期：不重跑复测和评审，直接沿用原记录，总结写明「沿用」。
A6. 操作：开发方改了 scope 外的文件，然后运行 `bin/loop 交付`。
    预期：拒绝交付，指出越界的文件，不生成 commit。
A7. 操作：用两个任务的卡同时开发。
    预期：两个任务各有自己的 worktree 和会话，并行推进，互不等待，各自的状态互不影响。
A8. 操作：卡上选整合、验收、合入三个附加步骤，两个任务都完成后观察；再构造一条验收失败的条目。
    预期：两个任务依次合进批次分支后跑验收。失败的条目按归属退回对应任务，返修后重新复测、评审，再重新验收。全部通过后合入 dev 并推送 origin/dev，main 不变。
A9. 操作：模拟 PA 读取状态文件，然后发一条答复，再发停止。
    预期：状态文件包含 PA 约定的必填字段，执行状态是五种之一。答复送进会话，并记录来源「经 PA」，已有结论不作废。停止后状态是「已停止」。
A10. 操作：任务完成后打开总结。
    预期：一屏以内，列出每一步的结论和耗时（开发、复测、评审、等你、Loop 自身），细节给文件路径。
