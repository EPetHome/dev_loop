# N1-看账本补步骤新版

## 目标

把 dev-loop 的推进方式从「收到事件迁移状态」换成「每次读账本、补缺的那一步」：机械故障（网络断、评审格式错、忘了交付、会话断线、合入冲突）不再等本人，失败后不用挑恢复命令，对外接口不变。

权威依据是 `docs/需求-调度改为看账本补步骤.md`（11-24 定稿，待决表全部已定）。本提示词只列要点和不能改坏的地方，细节一律以需求文档为准；两者有出入时按需求文档，并在交付说明里写出来。本批起点已包含 R1 批次（评审门槛规则、评审材料里的「项目评审规则」、复盘工具修复），新的评审工具沿用 R1 的材料拼装。

## 已拍板

**架构**（需求文档用词、第二至四节、第八节）

1. 账本：每张卡一个只追加的新文件，记意图和事实。状态一律从账本现算，不另存。四条铁律照第二节。
2. 推进：`bin/loop tick [--all]` 不调模型、不存状态，跑一次就退出。每张卡一把锁；工具开跑先记「开始（步骤 · sha · pid）」，跑完记结论，pid 死了又没结论算一次失败尝试。规则表 ⓪–⑧ 照第四节，每次命中哪条记一行，`loop 查询` 能看到。叫醒：工具或插件写完事实后顺手调一次；launchd 每 `tickIntervalSec` 兜底调一次。提供安装、卸载 launchd 定时项的方法，写进 README。
3. 工具化：准备、开窗口、收货、复测、评审、合入、部署、推送、释放都是能单独调用的命令，只认「卡 + sha」输入，只往账本写结论，同样的输入成功过就直接返回（缓存键见第十节硬约束 3，失败不缓存）。
4. 「待办」「提交（收货提交）」「起点（合并基点，现算）」三个词按需求文档用词表实现。

**开发窗口和交付**（第六节、C2、I1、P1–P4）

5. pi 插件只报事实、送待办，不在任何钩子里跑检查：`agent_start` 记忙；`agent_settled` 记闲、最后一段话、结束方式和是否被中止；`input` 记窗口原话；每秒检查没送达的待办，窗口闲时 `sendMessage(triggerTurn)` 并记「送达」。
6. 交付是快速通道，不强制：pi 调 `loop 交付` 就是收货工具本身；有改动但没调交付，先提醒一次（中性措辞），再停下仍没交付才分诊；分诊判「做完了」才代为收货。pi 自己 git commit 不算做完。
7. 只有结束方式是 `stop` 才可能收货；其余 6 种不收货、不评审、不扣轮数并记一行。出错按 `retry` 退避发「继续」，用完转「环境修不好」；上下文超长且 pi 自己压缩后仍失败，开新会话附交接笔记；本人按 Esc 中止后不动，本人再说话（窗口原话，或答复意图）才解除，解除后窗口不在就重开。
8. 开发会话：每卡一个可视窗口，固定会话文件跨轮续用；交接笔记由程序从账本生成（B2）。

**恢复和准确性**（第十节、K1、K2）

9. 错误不落成状态；按 `retry` 统一退避，每卡累计不超过 `cardRetryBudget`，熔断后只等一次本人。
10. 五条硬约束全部做到：格式重排时结论以原文为准；测试不稳只能重跑、第二次不稳当产品问题；缓存键覆盖全部输入；合入、部署工具自己核对放行证据（A 或 B），不信调度器；分诊拿不准一律当疑问，只能给收货、重跑、发回、等本人四种结果。环境和产品分不清时做起点对照。

**等本人、合入、批次**（第七、九节，B4、C3、C4、D1）

11. 只在四类情况等本人（需求疑问含评审标了「阻断：」的、轮数用完、开发推不动、环境修不好），另有本人中止不推飞书。等待内容自带说明、2–4 个选项；轮数用完时附收敛趋势（每轮必修几条、是否集中在同一文件同一类问题）。
12. 合入冲突发回开发，不扣轮数，冲突往返单独计数，上限 `retry.times`，超限归开发推不动。起点按合并基点现算，dev 上别人的改动不算越界、不进评审 diff。
13. 一次开工可放多张卡和依赖，默认同批一次推一张（`maxParallelCards`）；被依赖的卡必须授权合入，开工时核对，不满足同步返回原因、不写任何东西；下一张在准备时才取 dev 起点；前一张被停，后一张也停。

**配置、接口、界面卡**（第十三、十四节，CF1、IF1、UI1）

14. 配置三层：仓库 `config/defaults.json` → 项目 `.autoreview.json` → 开发卡 `limits`，开工时合并并固定。字段和默认值照第十三节（分诊 gpt-6.2-sol、xhigh）。代码里不写死这些值。
15. 对外接口不变：照旧写出 `status.json`（字段、取值都在原范围内）和 `checks.jsonl`，dev-loop 自己不读它们；保留 `启动 / 查询 / 续跑 / 答复 / 停止 / 放弃 / 合入 / 部署` 的命令名、参数和回执，翻译规则照第十四节对照表。PA 和 `tools/coordinate.ts` 一行不改也能照常用。
16. 界面卡：开发卡可选字段 `tasks[].版式`（草图文件、页面清单）；`loop 交付` 加可选 `--截图 <文件…>`，收货工具把截图复制进执行目录、记进账本，缺卡上列的页面就不收货、写待办发回，不等本人、不扣轮数；评审材料带上草图和截图。

**删掉的**（第十一、十二节，H1）

17. 删掉旧推进逻辑和状态机（settle、lifecycle、deliver 里的推进与迁移）、续跑的各种变体、本人确认交付（`续跑 --交付提交`）、收尾一条龙和 `next` 接力（由 C4 批次替代）、Claude/Codex 的 hook 接入。现有工具（合入、部署、推送、释放、证明、对比、陪跑、复测和评审的调用）尽量复用。
18. 体量：`src/` 不含测试回到 2000 行以内，`test/dependencies.test.ts` 恢复成超过就失败的硬检查（A6）。

## 边界

- 只改开发卡 scope 里的文件。不改需求文档、写法文档、AGENTS.md、`tools/`、`issues/`，不改 PA、Promate 等项目仓库。
- 没有账本的旧执行：`查询` 照常显示（读旧 status.json），tick 不推进它们。
- 测试全部跑完不超过 2 分钟；重试间隔、叫醒频率用可注入的时钟或配置调小，不写死等待秒数；模型、pi 窗口、评审一律用测试替身；测试产物写系统临时目录并清理；测试里不真的安装 launchd。
- README 和 `docs/参考-运行细节.md` 按新命令、新配置、新的等待原因同步改。

## 验收标准

A1. 操作：一张卡在准备、开窗口、收货、复测、评审、合入这几步，各杀一次 tick、正在跑的工具、开发窗口，之后不做任何操作
    预期：卡自己走到「完成」，没用任何人工命令；开发窗口用原会话文件重开，带上待办；账本里每一步的成功事实都只有一条（转换类：重启前后、重复）
A2. 操作：往账本里手工加一条「完成」，这个提交其实没有复测通过或评审通过，然后调合入
    预期：合入工具拒绝；`loop 查询` 报出这条缺证据的记录
A3. 操作：pi 有改动、正常停下，没调交付，最后一段话是在提问；收到提醒后又停下，还在提问；本人答复后，pi 调 `loop 交付`
    预期：先提醒一次；第二次停下由分诊判成疑问，不收货、不进复测；答复送进窗口；pi 调交付后不经分诊，直接收货、进复测
A4. 操作：pi 改到一半，这一轮因网络出错结束（`error`），工作区留着半成品；另起一次：本人按 Esc 中止后关掉终端，再写入答复意图「继续」
    预期：出错那次不收货、不复测、不评审、不扣轮数，按 `retry` 第一档间隔自动发「继续」；Esc 之后既不自动继续，也不重开窗口；答复后中止解除，重开窗口并带上待办
A5. 操作：评审调用前 3 次返回网络错误，第 4 次正常
    预期：不等本人；账本里只有一条评审结论；`loop 查询` 里没有待通知的事
A6. 操作：评审员交出一份内容合格、但没有「触发：」标签的评审（用 W3-C 首轮原文）
    预期：交回评审员重排一次后登记；结论仍是需返修，必修条数和原文一致；不出现「临时故障」
A7. 操作：一批两张卡，B 依赖 A，A 没授权合入，调 `loop 开工`（或 `启动`）；给 A 补上合入授权后原样再调一次；然后再原样调一次
    预期：第一次当场返回原因，账本里什么都没写；第二次返回新的执行编号，开始准备；第三次返回同一个编号，不再开窗口（转换类：失败以后重来、重复）
A8. 操作：合入时和 dev 冲突，pi 把 dev 合进来解决后交付
    预期：冲突清单发回开发窗口，不扣轮数；收货时不出现越界；评审看到的 diff 里没有 dev 上别人的改动；新提交复测、评审都通过后合入
A9. 操作：评审连续 4 轮都有必修，然后写入「加轮 2」意图
    预期：只停一次；`loop 查询` 给出剩余必修、已用轮数、收敛趋势和 4 个选项；加轮后自动继续评审
A10. 操作：把全部历史执行的 checks.jsonl（含 W3-C、B6、W3-D）交给新版回放
     预期：新版能读旧记录；机械类停下（网络、格式、未登记、断线）都不再等本人，需要判断的停下照样保留；新闸门放行的提交和旧闸门完全一致，不一致的逐条列出（转换类：旧数据）

另有测试清单 T1–T20，见需求文档「完成后需要提供」，每条都要有对应的测试。
