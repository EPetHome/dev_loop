# 提示词：收尾全部走完后自动释放 worktree，释放前检查未提交文件

> 来源：[需求-验证闭环](../需求-验证闭环.md) 待决项 D14、缺口 G4（本人 11-20「认同」）。

## 目标

磁盘一直在累积。11-20 统计，44 次执行的 worktree 一个都没释放过，promate-v2-web 的单个 worktree 就有 200~415 MB。原因是 README 规定「本人验收通过后运行 `释放`」，而本人不会去核销验收（需求-验证闭环 D13）。

改成：**卡上约定的收尾全部成功以后自动释放，释放前先确认没有未提交的文件。**

现状（11-20 协调方核实；行号会变，以函数为准）：

- `src/cli/inspect.ts` 的 `releaseWorktree`：只有 completed 且没释放过才能执行；直接 `git worktree remove --force`，写 `loop.released=true`，并记一条「释放 / 已释放」。
- `src/cli/finish.ts` 的 `finish`：成功时依次写 `结果.md`（`facts`）、记「收尾 / 通过」、转 completed；失败进 catch，按情况退回返修或转「等你」。接力的中间批在 `step="接力"` 处用本批交付 commit 建下一批。
- `src/core/lifecycle.ts` 的 `resume`：已释放的拒绝续跑。
- 已有用例：`test/companion.test.ts` 有释放，`test/finish.test.ts` 有一条龙收尾和接力。

## 已拍板

- 本人 11-20「认同」D14：本批约定的收尾**全部成功**以后再释放。只约定合入的，合入完就释放；还约定了部署或推送的，等这些都走完。收尾失败时不释放，因为部署失败返修还要用 worktree。
- 释放前确认 worktree 里没有未提交的文件（未跟踪、已暂存、已修改都算），有就保留不删。这一条写在 D14 里，起因是 Astra 11-20 评审指出 `--force` 会把未提交的文件一起删掉。
- **自动释放只在一种情况下发生：卡上约定了合入，并且收尾全部成功**，也就是本批的交付 commit 已经进了 dev。下面两种卡都不自动释放，手工 `释放` 照旧可用：
  - 没有约定收尾的卡（flow 只有「开发评审, 测试」，也没有 next）；
  - 接力的中间批（有 next，按规定不能写合入）。它的 commit 要等最后一批合入以后才进 dev，所以先保留，和协调方这次对 promate-v2-server B2、B3 的处理一致。
- 中间批和存量的 worktree，以后由协调方的收单在它们的 commit 进了 dev 以后再处理，不在本卡范围内。
- 「已释放不能续跑」不变。不新增命令或参数。

## 做完后的行为（以此为准）

| 情形 | 结果 |
|---|---|
| 卡上约定了合入，收尾全部成功（合入以及约定的部署、推送都走完） | worktree 删除，`loop.released=true`，分支、日志、证据保留；记一条「释放 / 已释放」；`结果.md` 和完成 message 写明「工作区已释放」 |
| 接力中间批收尾成功（下一批已启动） | 保留 worktree，`released` 仍为 false |
| 收尾成功，但 worktree 里有未提交的文件 | 不删除，`released` 仍为 false；记一条「释放 / 保留」，detail 列出文件路径（最多 20 个）；完成 message 写明「工作区有未提交文件，已保留」；state 仍是 completed，不转「等你」，也不算失败 |
| 收尾成功，但删除本身出错 | 记一条「释放 / 失败」并保留原始报错；收尾结果不变 |
| 收尾失败（退回返修、等你、已停止） | 不释放 |
| 手工 `bin/loop 释放`，worktree 里有未提交的文件 | 拒绝，退出码 1，错误里列出文件；不删除，也不写记录 |
| 手工 `bin/loop 释放`，worktree 是干净的 | 和现在一样 |

README 里「本人验收通过后运行 `释放`」等相关描述，按新行为改。

## 边界

- 只改 `src/**`、`test/**`、`README.md`。
- 不改开发卡解析和 flow 白名单，不改续跑规则，不改合入、部署、推送的逻辑。
- 自测只跑相关的：`PATH=/Users/Admin/.hermes/node/bin:$PATH node --test test/finish.test.ts test/companion.test.ts`；全量测试由 dev-loop 复测时跑。

## 验收标准

A1. 操作：一张 flow 为「开发评审, 测试, 合入」的卡，复测、评审通过后收尾走完
    预期：dev 上有合入提交；worktree 目录不存在；`loop.released=true`；任务分支还在；`checks.jsonl` 里有「释放 / 已释放」；`结果.md` 里写着「工作区已释放」
A2. 操作：一张 flow 带「部署」的卡，部署 check 失败并回退
    预期：worktree 还在，`released=false`，按现有规则退回开发
A3. 操作：A1 那张卡在收尾开始前，往 worktree 里放一个未跟踪的文件
    预期：收尾照常完成（state 为 completed）；worktree 和这个文件都还在；`released=false`；`checks.jsonl` 里有「释放 / 保留」并列出这个文件；完成 message 写明已保留
A4. 操作：一条接力链，中间批评审通过
    预期：下一批已启动，并且从中间批的交付 commit 开始；中间批的 worktree 还在，`released=false`
A5. 操作：对一个 completed、worktree 里有未提交改动的执行，运行 `bin/loop 释放 <执行编号> --json`
    预期：退出码 1，错误里列出这个文件；worktree 和文件都还在；没有新增「释放」记录
A6. 操作：一张 flow 只有「开发评审, 测试」、也没有 next 的卡跑完
    预期：worktree 还在，没有自动释放
A7. 操作：运行全量测试 `PATH=/Users/Admin/.hermes/node/bin:$PATH node --test test/*.test.ts`
    预期：全部通过，2 分钟内跑完
