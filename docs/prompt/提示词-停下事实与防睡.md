# 提示词：状态里写出停下的事实、跑任务时不让电脑空闲睡眠、评审临时失败只重做评审、评审材料不放被删文件全文

## 目标

四件小事，都是 PA（个人助手）读 dev-loop 时遇到的真实问题。PA 只读公开查询 `查询 --all --brief --json`，不读 `checks.jsonl`、`task.json`。

### ① 状态里写出停下的事实

现在公开状态里的东西不够：

- 执行什么时候开始：只在 `task.json` 的 `createdAt`，状态里没有。
- 停下的原因：`loop.wait` 离开等你就清空（README「数据与状态」）；失败、已停止根本没有记录。`checks.jsonl` 里只有一条「等你 / 已续跑」，而且没写原因。
- 续跑过几次：没有。
- 任务名：状态里没有（只有 `refs.card` 路径）。

结果是 PA 的台账只能从累计耗时、`stepStartedAt` 倒推「什么时候停的、等了多久、怎么解开的」，接力时还把第二张卡记成了第一张卡的名字（11-12 核实）。

要的结果：状态里直接写出这些事实，PA 照抄。

### ② 有任务在跑时，不让电脑空闲睡眠

本机设置是无操作 180 分钟后关屏，再过 1 分钟整机睡眠；近 7 天（11-05～11-12）空闲睡眠 5 次。睡着时开发、复测、评审全冻住。

要的结果：本机有执行处于 working 时，系统不进入**空闲**睡眠；没有执行在 working 时自动放开。

### ③ 评审调用临时失败后，续跑只重做评审

现在评审调用失败会记 `failed`、类别「临时故障」（`src/core/settle.ts` 评审那段）。续跑（`src/core/lifecycle.ts` 的 `resume`）只有在这个 commit 已经检查通过时才沿用，否则回到「开发中」：要重开开发会话、重新交付、重跑复测。11-11 删旧主线那张卡第 3 轮评审就返回过一次 Bad Request。

PA 下一批会在这种失败后等 3 分钟自动续跑一次，所以续跑要能只补做失败的那一步。

要的结果：评审调用临时失败、之后什么都没变，续跑就只重做评审。

### ④ 评审材料里，被删的文件只列名字

评审材料的「本轮改动」是整段 `git diff`，被删文件的全文都在里面。删旧主线那张卡第 1 轮评审输入 3.09MB，接通那张卡只有 0.28MB。

要的结果：被删的文件只列路径和原来的行数，不放内容。

## 对外接口（PA 照此读，字段名不要改）

`status.json` 的 `loop` 下新增 `facts`，公开查询（含 `--brief`）原样带出：

```json
"facts": {
  "name": "卡上 tasks[].name，即 task.json 的 name",
  "startedAt": "执行开始时间，等于 task.json 的 createdAt（ISO）",
  "resumes": 0,
  "stops": [
    {
      "at": "停下的时间（ISO）",
      "step": "停下前所在的阶段，取 PHASES 里的值，例如 评审中、复测中、准备中、开发中、收尾中",
      "state": "input_required | failed | cancelled",
      "reason": "等你取 loop.wait 的五种原因之一；失败取 error.category；停止写「已停止」，放弃写「已放弃」",
      "message": "当时的原话，最多 200 字",
      "resumedAt": "解开的时间（ISO），没解开为 null",
      "resolvedBy": "续跑 | 收尾 | 合入（接受未验证） | 停止 | 放弃 | 沿用通过记录；没解开为 null"
    }
  ]
}
```

- 进入 input_required、failed、cancelled 时追加一条。上一条还没解开就先关掉它，`resolvedBy` 写这次的去向（例如等你之后被停止，写「停止」）。
- 续跑、收尾、`合入 --接受未验证` 让执行离开这三种状态时，补上最后一条的 `resumedAt` 和 `resolvedBy`。`resumes` 只数成功的续跑。
- `stops` 最多保留最近 50 条。
- 原有字段（包括 `loop.wait` 的清空规则）不变。没有 `facts` 的旧状态文件照常能读、能查询、能续跑。

## 边界

- ② 的做法由开发方定，有四条要求：
  - 不新增常驻进程。
  - 防睡跟着干活的进程或心跳走：dev-loop 自己崩了，防睡也会在几分钟内自动失效，不靠「记得去关」。
  - 等你、完成、失败、已停止时不保持防睡，最迟 3 分钟内放开。
  - 只用 `caffeinate -i` 这一类用户态命令，不用 `-s`、`-d`，不调 `pmset` 改设置。
- ② 要能在测试里换成替身，沿用 `LOOP_LAUNCH_CMD` 的做法（环境变量指向替身可执行文件）。测试绝不调用真实的 `caffeinate`。
- ③ 只在下面这些条件都满足时只重做评审：
  - 失败类别是「临时故障」，最后一次检查是「评审 / 失败」；
  - 工作区 HEAD 等于最后交付的 commit，没有未提交改动；
  - 提示词、验收标准哈希没变；
  - 这个 commit 在当前哈希下复测「通过」或「没验证」。

  有一条不满足，就走现在的续跑逻辑，行为不变。重做时：不开开发会话，不重跑复测；失败的那次调用不算一次退回。续跑命令立即返回回执，评审在后台跑，和现在交付后的检查一样。评审出结论后照常走：通过就完成或收尾，必修就照常返修。
- ④ 只改评审材料的拼法：内容 diff 排除被删文件，另加一节「删除的文件」列出路径和原行数。「新增文件」「运行差异」等其他节不变。
- 不新增拒绝点、配置字段或开关，不改状态协议名 `loop-status/1`。
- README 同步：「数据与状态」写清 `facts`；续跑说明里写清 ③ 什么时候只重做评审；单独一小段写 ② 怎么防睡、挡不住合盖。
- 只改 `src/`、`test/`、`README.md`。不改 PA 项目、旧 loop 和用户的全局配置。`src` 总行数仍须 ≤2000（`test/dependencies.test.ts` 会检查），全部测试 2 分钟内跑完。

## 验收标准

A1. 操作：替身任务评审必修到上限停下，再续跑，然后 `查询 --all --brief --json`
    预期：该执行的 `loop.facts` 里 `name` 是卡上的任务名，`startedAt` 等于 task.json 的 `createdAt`，`resumes` 为 1；`stops` 有一条：`step` 评审中、`state` input_required、`reason` 评审必修到上限，`at`、`resumedAt` 都有值，`resolvedBy` 为续跑
A2. 操作：A1 续跑之后再查
    预期：`loop.wait` 已清空，`facts.stops` 里那条原因还在
A3. 操作：替身评审第一次调用报错
    预期：state 为 failed、类别临时故障；`facts.stops` 多一条，`step` 评审中、`reason` 临时故障
A4. 操作：A3 之后什么都不改，直接续跑
    预期：开会话的替身没被调用；没有新的复测记录；评审重做一次，通过后阶段为「完成」；A3 那条 `resolvedBy` 为续跑，`resumes` 加 1
A5. 操作：A3 之后在工作区改一个文件，再续跑
    预期：和改之前的续跑行为一样，回到「开发中」
A6. 操作：停止一个在跑的执行，再续跑
    预期：`facts.stops` 多一条 `state` cancelled、`reason` 已停止，续跑后补上 `resumedAt`，`resolvedBy` 为续跑
A7. 操作：一个执行进入 working；然后让它停在等你（用注入的时钟推进）
    预期：working 期间防睡替身被调用并处于生效；离开 working 后最迟 3 分钟，替身记录显示已不生效
A8. 操作：一次交付删除一个文件、修改另一个文件，进入评审
    预期：评审输入里被删文件只出现在「删除的文件」一节，有路径和原行数，内容不出现；修改的文件 diff 照旧
A9. 操作：读取一个没有 `facts` 的旧状态文件，查询并续跑
    预期：查询照常返回，续跑照常进行，之后状态里开始有 `facts`
A10. 操作：合入后由协调方在本机开一个真实任务，运行 `pmset -g assertions`（开发方不做这一条）
    预期：任务在跑时能看到一条阻止空闲睡眠的断言；任务停下或完成后 3 分钟内消失
