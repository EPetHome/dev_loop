# 提示词：留痕脚本也拿到部署登记的环境变量

## 目标

项目登记的留痕脚本（`.autoreview.json` 的 `snapshot`），现在只拿到宿主环境，加上 `LOOP_TASK_DIR`、`LOOP_REPO`、`LOOP_SNAPSHOT_MODE`、`LOOP_SNAPSHOT_OUT`、`LOOP_SNAPSHOT_COMMIT`、`TMPDIR`（`src/core/snapshot.ts:20`）。`deploy.env` 只给部署、检查、回退三个脚本（`src/steps/deploy.ts:40`、`:77`）。

可是 live 模式本来就是读线上指标，脚本得知道线上在哪；而项目登记线上位置的地方只有 `deploy.env`。结果是项目只能在留痕脚本里把线上路径再写一遍，不写就失败。

这件事真实发生过。PA 的留痕脚本要用 `NODE_BIN`、`APP_DIR`、`CONFIG` 等变量，它们都只在 PA 的 `deploy.env` 里：

- 11-11 PA 第一次经 dev-loop 部署，部署前后两次 live 留痕都失败，报「须明确指定 NODE_BIN」。
- 同一天晚上 PA 一次执行开工时，陪跑基线和留痕也因同样原因失败。

部署本身没受影响，但基线、评审前的运行差异、部署前后的对比，全都没有生成。

要的结果：每个时机的留痕脚本都拿到当前登记的 `deploy.env`，规则和部署脚本一致。

## 已拍板

- 本人 11-11：「提卡到dev-loop那边」。在 dev-loop 改；线上路径只留在 `deploy.env` 一处，不让项目在留痕脚本里再写一份。
- 优先级从低到高：宿主环境 → `deploy.env` → 框架变量（上面列的 `LOOP_*` 和 `TMPDIR`）。`TMPDIR` 仍然是框架给的独立临时目录，`deploy.env` 里有同名的也不能覆盖它。
- 读项目仓库根目录当前的登记，和部署命令一样（`loadDeploy(t.repo)`），不读启动时的配置快照。
- 没有 `deploy` 段时，行为和现在完全一样。
- `deploy` 段不合法时，只记「留痕 / 失败」并写明原因，不改阶段、不阻断任何流程，沿用留痕失败的现有处理。

## 边界

- 只改一处：`src/core/snapshot.ts` 的 `snapshot()`。五个调用点（`src/core/settle.ts:107`、`src/cli/companion.ts:27`、`src/cli/inspect.ts:14`、`src/steps/deploy.ts:51`、`:55`）不各自改。
- 不新增拒绝点、配置字段或开关；不改 `deploy.env` 的格式和校验；不改部署、检查、回退脚本拿到的环境。

## 验收标准

A1. 操作：项目 `deploy.env` 登记 `PROBE=1`，留痕脚本把它看到的 `PROBE` 写进输出；在开工陪跑、评审前、部署前、部署后四个时机各采一次
    预期：四份留痕输出里都是 `PROBE=1`；执行记录里有四次「留痕 / 已存」
A2. 操作：宿主环境有 `PROBE=0`，`deploy.env` 登记 `PROBE=1`，跑一次留痕
    预期：脚本看到的是 `1`
A3. 操作：`deploy.env` 登记 `TMPDIR=/tmp/别处`，留痕脚本输出它看到的 `TMPDIR` 和 `LOOP_SNAPSHOT_MODE`
    预期：`TMPDIR` 是框架给的临时目录，`LOOP_SNAPSHOT_MODE` 是框架给的值
A4. 操作：项目没有 `deploy` 段，跑开工陪跑和评审前留痕
    预期：和改之前一样成功；已有的留痕测试照常通过
A5. 操作：`deploy` 段不合法（例如 `env` 的键是小写），跑开工陪跑
    预期：留痕记「失败」并写明是 deploy 登记不合法；任务阶段不变，开发照常进行
A6. 操作：改掉 `deploy.env` 里的值，再采一次 live
    预期：留痕看到的是新值
