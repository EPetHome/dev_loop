## 已拍板

**评审规则（改 `src/core/review-prompt.md`）**

1. 必修门槛：触发落在三类之一才算必修——验收标准或提示词写到的场景；正常使用会走到的路径；现实中会发生的外部情况（网络断、进程被杀、磁盘满）。人为构造的输入（例如改几个字骗过规则）、没人会那样配的配置组合，记「小问题」。例外：安全、权限、数据丢失不降标准，安全类里恶意构造的输入照样算必修。
2. 第 2 轮起，必修只认三种：上轮必修没修好；本轮修复在正常路径上引出了回归；首轮漏看、但落在验收场景主路径上的问题。其余新发现记「小问题」。
3. 验收边界不清时，先列「需求疑问」，不自己挑最严的理解去列必修。评审认为不回答就判断不了某条算不算必修时，在那条疑问前写「阻断：」。本批只要求评审这样写，dev-loop 不据此停下。
4. 第 2 轮起的审查范围：本轮 diff 改到的函数，加上直接调用它们的地方。
5. 材料里有「项目评审规则」时，它是本项目的补充标准：条目注明评审能查的，按上面的门槛判；注明查不了的（只能看截图），不报必修。
6. 输出格式不变：五个标题；必修每条带 `位置：相对路径:行` 和 `触发：`；`src/core/review-parse.ts` 的解析要求不变。新增测试：`review-prompt.md` 的必修格式说明里必须包含 `review-parse.ts` 检查的 `触发：` 标签和 `路径:行` 写法。

**评审材料加「项目评审规则」一节**

7. 取起点提交里仓库根目录的 `REVIEW.md` 全文，再读其中指向仓库内文件的相对链接，同样取起点提交的版本，各附全文。指向仓库外、绝对路径、网址的链接不读。链接的文件在起点版本里不存在，写明「起点版本里没有」。没有 REVIEW.md 时这一节写「无」，评审照常进行。

**复盘工具（`tools/coordination/`）三处误判**，按 bug 单的「预期结果」修：
