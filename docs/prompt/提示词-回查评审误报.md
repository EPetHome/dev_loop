# 回查评审误报

## 目标

dev-loop 的独立评审在历史执行里共报了约 136 条「必修」，第 1 轮评审有 71% 的执行被退回，第 2 轮以后的必修大多是新发现。本人看不了这么多条，需要你逐条判断哪些成立、哪些报过头，再把重复出现的「报过头」归纳成候选规则，交本人批准。批准后的规则会写进各项目的 REVIEW.md「不算必修」一节。

## 已拍板

- 只读分析，不改任何代码、卡、问题单或 dev-loop 运行数据。只写下面「产出」里的一个报告文件。
- 每条必修只给三种结论：**成立**、**报过头**、**判断不了**。判断依据只用下面四问，逐问写一句话：
  1. 触发条件：正常使用中会发生，还是要人为构造（本机有人改文件、刻意制造并发、改系统时钟等）？
  2. 后果：是否落在核心链路上（停摆、离线回不来、数据丢失或写错、装上没签名的程序、越权、泄露）？
  3. 需求：是否在当批提示词和验收标准的范围内？
  4. 后续：开发方是否真的改了行为？还是只补了测试或注释？
- 只要四问里有一问拿不准，就写「判断不了」并说明缺什么材料，不硬判。
- 候选规则的门槛：同类「报过头」至少出现 2 次，并且来自至少 2 次不同的执行。不够门槛的只列在明细里。
- promate-v2-agent 的 B1 执行（评审 5 轮、2 次到上限）单独写一节，逐轮说明。

## 边界

- 材料都在 `~/.dev-loop/tasks/<执行编号>/`：
  - `checks.jsonl` 里 `step=评审`、`result=必修` 的 `detail` 是必修原文；
  - `review-<sha>-r<轮>-a<次>.md` 是评审完整输出；
  - `review-input-r<轮>.md` 是当轮评审材料（提示词原文、diff、复测结果、开发方说明）；
  - `task.json` 的 `repo`、`prompt` 是项目仓库和提示词位置。需要看后续修复时，到项目仓库里用 git 只读查看相应 commit。
- 不评价 dev-loop 本身的代码，不提改 dev-loop 的方案。
- 不把推断写成事实；所有结论都附上可复核的出处（执行编号、文件、轮次）。

## 产出

写一个文件：`/Users/Admin/Desktop/dev-loop/docs/分析-评审误报回查.md`，结构如下：

1. 一张总表：执行数、必修总数，成立、报过头、判断不了各多少。
2. 候选规则（达到门槛的）：每条写「这类情况不算必修」的一句话、它属于哪个项目的哪个模块、命中的必修出处（至少 2 条）。
3. B1 逐轮说明。
4. 附录：全部必修的明细表，列为执行、轮次、位置、一句话摘要、四问、结论。

## 验收标准

A1. 操作：打开报告的总表和附录
    预期：附录行数等于总表里的必修总数，三种结论的数量之和也等于必修总数
A2. 操作：任选附录里 5 条，按出处打开对应的 `checks.jsonl` 或评审原文
    预期：摘要与原文一致，四问各有一句依据
A3. 操作：查看每条候选规则
    预期：每条都列出至少 2 条出处，且来自至少 2 次不同的执行
A4. 操作：执行 `git -C /Users/Admin/Desktop/dev-loop status --short`
    预期：除新增的报告文件外，与开始前相同
