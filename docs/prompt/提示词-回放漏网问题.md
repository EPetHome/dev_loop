# 回放漏网问题

## 目标

找出 dev-loop 启用（2026-11-09）以后，哪些 bug 是经过 dev-loop 复测和评审「通过」，后来才被发现的；再判断每个 bug 本该由哪一层拦住。结果用来补项目的测试用例、REVIEW.md「常漏清单」和主路径清单，并为问题单补两个新字段：「引入批次」和「本该拦住」。

## 已拍板

- 只读分析，不改任何代码、问题单、卡或 dev-loop 运行数据。只写下面「产出」里的一个报告文件。
- 范围是两个项目的全部 `【bug】` 问题单，包括 `issues/` 和 `issues/【history】/` 两处：
  - `/Users/Admin/Desktop/personal agent/issues/`
  - `/Users/Admin/Desktop/Promate/issues/`
  注意：`【history】` 里有不少单子的状态仍是「待修复」或「已合入待验」，**放进历史不等于已解决**，以单头的状态为准。
- 每张单按下面的顺序查，查到哪一步停下就写到哪一步：
  1. 引入它的代码在哪里：用 git log / blame 找到引入的 commit；找不到就写「定位不到」。
  2. 这个 commit 是不是 dev-loop 交付的：对照 `~/.dev-loop/tasks/*/checks.jsonl` 里的 commit，以及 dev 上 `Merge <卡名>: reviewed|unverified <sha>` 形式的合入信息。不是的，写「非 dev-loop 引入」，到此为止。
  3. 是 dev-loop 交付的，再查：
     - 当时复测跑了哪条命令，有没有测到这段代码；
     - 评审材料（`review-input-r*.md`）里有没有这段 diff；
     - 评审原文里有没有提到这个问题（哪怕只列成小问题），分成「提到并列为必修」「提到但没列必修」「没提到」三种。
  4. 本该拦住：按下面的顺序判断，取第一个符合的：
     - **测试用例**：能写成「输入 X → 应得到 Y」，不用把整个应用跑起来就能复现；
     - **主路径清单**：要把应用真正跑起来才会出现（多个组件连起来、真实环境、重启、登录、真实账号或配置）；
     - **REVIEW.md**：很难稳定复现（时序、并发、旧数据兼容、权限），但读 diff 看得出来；
     - **拦不住**：需求本身没写，或者是外部变化造成的。
- 归纳候选：同一层、同一类原因的漏网至少出现 2 次，才归纳成一条候选（测试用例、REVIEW 常漏条目或主路径条目）。REVIEW 常漏条目要写成「触发：diff 改了什么 → 检查：看什么 → 出处：哪几张单」。

## 边界

- dev-loop 执行数据在 `~/.dev-loop/tasks/<执行编号>/`，`task.json` 里的 `repo` 是项目仓库。只用 git 的只读命令。
- 不提改 dev-loop 本身的方案，不评价当时的开发方。
- 不把推断写成事实；每个判断都附上出处（问题单文件、commit、执行编号、评审轮次）。

## 产出

写一个文件：`/Users/Admin/Desktop/dev-loop/docs/分析-漏网问题回放.md`，结构如下：

1. 总表：两个项目各有多少张 bug 单；其中定位不到多少、非 dev-loop 引入多少、dev-loop 引入多少；dev-loop 引入的按「本该拦住」四类各多少。
2. 分阶段：dev-loop 引入的 bug 里，评审「提到并列为必修」「提到但没列必修」「没提到」各多少。
3. 候选：达到门槛的测试用例、REVIEW 常漏条目和主路径条目。
4. 附录：每张单一行，列为问题单、单头状态、引入 commit、引入批次、复测有没有测到、评审有没有提到、本该拦住、出处。「引入批次」和「本该拦住」两列写成以后可以直接抄进问题单的样子。

## 验收标准

A1. 操作：打开报告的总表和附录
    预期：两个项目附录的行数分别等于总表里的 bug 单数，各分类的数量之和等于总数
A2. 操作：任选附录里标「dev-loop 引入」的 3 行，按引入 commit 和执行编号去核对
    预期：这个 commit 确实出现在该执行的 `checks.jsonl` 里
A3. 操作：查看每条候选
    预期：每条都列出至少 2 张出处问题单
A4. 操作：分别对 dev-loop、personal agent、Promate 三个仓库执行 `git status --short`
    预期：除 dev-loop 里新增的报告文件外，与开始前相同
