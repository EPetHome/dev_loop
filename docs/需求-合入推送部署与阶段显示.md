## 问题描述

dev-loop 的「开发 → 复测 → 评审」已稳定。任务到「完成」以后有四个问题：

1. **没有合入、推送、部署命令。** `bin/loop 合入`、`bin/loop 部署` 现在返回「本步不支持此命令」。这几步由模型会话手工执行 git 命令和部署步骤完成。

## 预期结果

### 一、核心

下面五条是本单要的全部结果，后面各节是每条的细则。

1. **合入**（✅ 要做）：本人说「合入」后，协调方运行一条命令 `bin/loop 合入 <执行编号>`。dev-loop 把这个任务最后一次交付的 commit 合并进本地 dev 分支，生成一个合并提交，然后退出。整个过程只运行 git，不启动 pi，不调用评审，不调用任何模型。目标分支固定为 dev（卡的 target 只允许 dev）。
2. **推送**（✅ 能力要有，默认关闭）：只有命令里加了 `--推送`，才在合入后把本地 dev 推到 origin/dev；不加就不推。dev-loop 不会在任何其他情况下推送。
3. **部署**（✅ 要做）：本人说「部署」后，协调方运行 `bin/loop 部署 <执行编号>`。dev-loop 把要部署的 commit 检出到一个临时目录，运行项目仓库里登记好的部署脚本。脚本由项目写一次、提交进项目仓库，以后每次部署运行同一份，不再现场写。整个过程不调用任何模型。
4. **记录**：合入、推送、部署每执行一次，都写进这个执行的记录（`checks.jsonl`、`summary.md`、`status.json`），包括结果、用了几秒、涉及哪个 commit。`bin/loop 查询` 能看到。
5. **阶段显示**（✅ 要做）：pi 开发窗口的底部状态栏和窗口标题，一直显示这个任务当前处于哪个阶段，例如【开发中】【复测中】【评审中】【等你】【完成】【已合入】【部署中】【已部署】。

共同规则：

- ✅ 合入、推送、部署都不自动触发，只在命令被运行时执行。（PA 需求书第四节：自动合入、自动部署要等 AGENTS.md 相应条款改了才生效。）
- 三条命令都不碰 main，不强推，不改任务分支，不删 worktree。
- 命令输出沿用现有命令的格式：成功时标准输出一段 JSON；失败时标准错误输出 `{error:{category, raw}}`，退出码 1。

### 二、合入

命令：`bin/loop 合入 <执行编号或卡路径> [--commit <sha>] [--接受未验证] [--推送]`

按顺序执行，任何一步停下都不再往下走：

| 步 | 情况 | dev-loop 做什么 |
|---|---|---|
| 1 | 取要合入的 commit | 取 `status.json` 里的 `loop.commit`，即最后一次交付登记的 commit。还没交付过 → 拒绝，报「没有交付记录」 |
| 2 | 给了 `--commit` | 必须与第 1 步的 commit 相同（可用短 sha）。不同 → 拒绝，报「目标已变化：确认的是 X，当前是 Y」 |
| 3 | 检查是否检查过 | 这个 commit 在 `checks.jsonl` 里有复测「通过」或「没验证」，有评审「通过」，且提示词、验收标准的内容哈希与现在一致。缺任何一项且没加 `--接受未验证` → 拒绝，列出缺哪几项。加了 → 继续，结果标「未验证」 |
| 4 | 已经在 dev 上 | 这个 commit 已是 dev 或 dev 的祖先 → 不合并，结果为「已在 dev」，退出码 0；有 `--推送` 时继续第 8 步 |
| 5 | 找 dev 的检出目录 | 在 `git worktree list` 里找检出了 dev 的目录。没有 → 拒绝，报「dev 没有检出到任何目录」 |
| 6 | 合并 | 在该目录运行 `git merge --no-ff`。🔧 提交信息：`Merge <卡名>: reviewed <短sha>`；加了 `--接受未验证` 时为 `Merge <卡名>: unverified <短sha>`（沿用 PA 现有写法） |
| 7 | 合并失败（冲突、会覆盖该目录里未提交的文件，或其他非 0） | 有合并进行到一半时运行 `git merge --abort`，使 dev 的 commit 和该目录的文件回到合并前；原样输出 git 的报错；不重试；结果为「合入失败」 |
| 8 | 加了 `--推送` | 合入成功或已在 dev 之后，按第三节推送 |

- 成功时输出：执行编号、合入的 commit、合入前和合入后的 dev commit、结果（已合入 / 已在 dev）、是否未验证、用了几秒、撤销命令 `git -C <dev 检出目录> revert -m 1 <合入后的 commit>`。
- 第 1、2、3、5 步的拒绝只输出错误，不写记录、不改阶段。第 4、6、7 步的结果写记录。
- dev 检出目录里与本次合并无关的未提交文件保持原样（由 git 保证，dev-loop 不另做检查）。PA 的 dev 检出在 `~/.personal-agent-v2-runtime`，服务实际运行的是 `~/.personal-agent-v2-app`，所以合入不会改变正在运行的 PA。
- 🔧 目标值（不是验收标准）：不含推送，命令 10 秒内返回。

### 三、推送（✅ 能力要有，默认关闭）

只在 `合入 --推送` 时执行：

| 步 | 情况 | dev-loop 做什么 |
|---|---|---|
| 1 | 仓库没有名为 origin 的远端 | 拒绝，报「没有 origin」，不写记录 |
| 2 | 确定要推的提交 | 运行 `git fetch origin`；要推的是 dev 上有、origin 任何分支上都没有的提交。origin/dev 存在时，这就是 `origin/dev..dev` |
| 3 | 密钥扫描 ✅（11-09 本人认同保留） | 扫描第 2 步全部提交的新增行和新增文件。命中 → 不推送，结果「扫描命中，未推送」，报 文件:行 和命中的规则名，**不输出命中的内容**；扫描出错 → 不推送，结果「扫描出错，未推送」 |
| 4 | 推送 | `git push origin <dev 的 commit>:refs/heads/dev`。不加 `--force`，不推其他分支和标签 |
| 5 | 推送命令退出码非 0 | 运行一次 `git ls-remote origin refs/heads/dev` 核对：远端等于要推的 commit → 结果「已推送」；不等 → 结果「推送失败」，原样输出 git 报错（例如远端有本地没有的提交）；核对命令也失败 → 结果「推送结果不确定」，给出核对命令。都不重推、不强推、不拉取 |

- 🔧 扫描规则由 dev-loop 内置，不依赖外部工具（11-10 核对：本机没有 gitleaks、trufflehog、detect-secrets、git-secrets）。至少覆盖：私钥文件头、常见平台密钥格式、新增了 `.env` 或 `.env.*` 文件。⏳ 完整规则清单在方案里列。
- 对同一次合入重复运行 `--推送`：远端已等于本地 dev 时，推送什么也不改，结果「已推送」。不需要指令编号。

### 四、部署（✅ 要做）

**项目登记**：在项目根目录的 `.autoreview.json` 里加 `deploy`：

```json
{
  "deploy": {
    "cmd": "scripts/deploy.sh",
    "check": "scripts/deploy-check.sh",
    "rollback": "scripts/deploy-rollback.sh",
    "timeoutMin": 20
  }
}
```

- `cmd` 必填；`check`、`rollback` 可选；`timeoutMin` 可选，默认 20，三个脚本各自适用。
- 三个值都是**仓库内可执行文件的相对路径，不是 shell 命令串**（与 `reviewerCmd` 同一规则）。脚本随项目代码一起提交，这就是「写一次、每次复用」。
- 没有登记 `deploy` 的项目，部署命令拒绝运行，默认就是关闭。

**命令**：`bin/loop 部署 <执行编号或卡路径> [--commit <sha>]`

| 步 | 情况 | dev-loop 做什么 |
|---|---|---|
| 1 | 项目没有登记 `deploy.cmd` | 拒绝，报「项目没有登记部署脚本」，不写记录 |
| 2 | 确定要部署的 commit | 默认是本地 dev 当前的 commit；给了 `--commit` 就用它。输出里标明这个 commit 是否已在 dev 上 |
| 3 | 准备代码 | 在系统临时目录建这个 commit 的独立检出。登记的脚本在这份检出里不存在或不可执行 → 拒绝，删除检出，不写记录 |
| 4 | 运行 `cmd` | 工作目录是临时检出；环境变量：`LOOP_DEPLOY_COMMIT`（完整 sha）、`LOOP_REPO`（仓库根目录）、`LOOP_EVIDENCE_DIR`（本次部署的证据目录，脚本可在这里写备份位置、健康检查结果）。超时就结束整个进程组，按失败处理 |
| 5 | `cmd` 成功 | 登记了 `check` 就运行它（同样的目录和环境变量）。成功 → 结果「已部署」。没登记 `check` → 结果「已部署（未检查）」 |
| 6 | `cmd` 或 `check` 失败或超时 | 🔧 登记了 `rollback` 就运行一次，环境变量另加 `LOOP_DEPLOY_FAILED=cmd` 或 `check`：成功 → 「部署失败，已回退」；失败 → 「部署失败，回退也失败」。没登记 `rollback` → 「部署失败，未回退」。都不重试 |
| 7 | 收尾 | 无论结果如何，删除临时检出 |

- 输出：commit、是否已在 dev、结果、每个脚本的退出码和秒数、日志路径。三个脚本的完整输出写进执行目录下的 `deploy-<短sha>-<时间>.log`。部署失败时退出码 1。
- 部署不改 dev，不推送，不调用任何模型。
- 部署具体做什么（备份、换目录、重启、健康检查）由项目脚本决定，dev-loop 不判断，只按退出码走流程。

         │         ▲   │       │(交付后又改)        │失败退回    │必修退回
         │         │   │       └────────→ 开发中 ◄──┴───────────┘

         │         │                ▼                  ▼
         │         └────续跑──── 等你 ◄───────────────┘
         │                         ├─停止→ 已停止 ─续跑→ 开发中
         │                         └─合入 --接受未验证→ 已合入

### 六、记录与查询

- `checks.jsonl`：每次合入、推送、部署追加一行。`step` 为「合入」「推送」「部署」，`result` 为上面各节的结果，含 commit、开始和结束时间、毫秒数、证据路径。
- `summary.md`：表里在「dev-loop 自身」之前加「合入」「推送」「部署」行，结论写最近一次的结果，耗时写累计；做过才出现。
- `status.json`：`loop-status/1` 的五种 state 不加新值。state 为 `completed` 时，`loop.phase` 按第五节更新，`message` 写一句结果。✅ 唯一会改 state 的情况：到上限「等你」（`input_required`）后用 `--接受未验证` 合入成功，state 改为 `completed`，阶段为「已合入」。合入就是执行你在「等你」时选的「接受未验证」，执行完流程就走到这里。其他 state 下只追加记录，不改阶段。`bin/loop 查询` 直接可见，PA 不需要读内部文件。
- 到上限转「等你」时的提示，现在写「接受未验证（本步只记录决定，不执行合入）」，改为「接受未验证：运行 bin/loop 合入 <执行编号> --接受未验证」。

### 七、新增的拒绝点及出处

按项目规则，每个新增拒绝都要写明它解决的真实问题：

| 拒绝 | 解决的问题 |
|---|---|
| 没通过检查不合入，除非加 `--接受未验证` | 核心需求底线第 6 条；旧 loop 10 次合入有 9 次强合，检查的成本付了，保障没拿到 |
| `--commit` 与当前交付不一致不合入 | 核心需求底线第 6 条「版本不符就拒绝」；本人确认后又续跑出新 commit 时，合进去的就不是确认的版本 |
| 扫描命中或出错不推送 | 仓库公开，11-09 本人认同保留 |

其余拒绝（没有交付记录、dev 没检出、没有 origin、项目没登记部署脚本、脚本不存在）是无法执行，不是规则。

### 八、不做

- 部署互斥锁、失败自动重试、合入后再跑测试、合入后删 worktree 和任务分支：都没发生过对应问题。
- 指令编号去重：合入和推送靠 git 状态天然幂等；部署重复运行就是再部署一次，由本人决定。PA 接入时再定。
- 自动合入、自动推送、自动部署：等 PA 需求书第八节第 11 项和 AGENTS.md 的条款。
- 卡上 `flow` 写「提交」「部署」：🔧 启动时仍拒绝，报错里提示改用 `bin/loop 合入`、`bin/loop 部署`。
- Claude、Codex 的阶段显示。
- 项目自己的部署脚本（例如把 PA 的切换流程写成 `deploy`、`check`、`rollback`）：属于各项目的开发任务，在各自仓库开卡，不在本单。

## 验收标准

A1. 操作：对评审通过的执行运行 `bin/loop 合入 <执行编号>`。
    预期：dev 多一个合并提交，它的第二个父提交是该任务最后交付的 commit；输出含合入前后 sha、秒数和撤销命令；评审替身脚本和 pi 替身的调用次数都是 0。
A2. 操作：对评审没有通过的执行运行 `bin/loop 合入 <执行编号>`。
    预期：拒绝，输出列出缺少的检查项；dev 的 commit 不变。
A3. 操作：让任务分支和 dev 修改同一行后运行 `合入`。
    预期：输出 git 的冲突报错，退出码 1；dev 的 commit 不变，dev 检出目录的 `git status` 与合入前相同。
A4. 操作：以本地裸仓库作 origin，对评审通过的执行运行 `合入`，不加 `--推送`。
    预期：裸仓库的 dev 不变。
A5. 操作：同样条件下运行 `合入 --推送`。
    预期：裸仓库的 dev 等于本地 dev，输出结果「已推送」。
A6. 操作：让待推送范围中间的某个提交含一段合成的测试密钥，运行 `合入 --推送`。
    预期：裸仓库的 dev 不变；输出给出 文件:行 和规则名，输出里找不到这段密钥。
A7. 操作：登记替身 `cmd`、`check` 后运行 `bin/loop 部署 <执行编号>`。
    预期：两个替身各运行一次，收到的 `LOOP_DEPLOY_COMMIT` 等于 dev 当前 commit；输出「已部署」；临时检出目录已不存在。
A8. 操作：登记一个返回失败的 `check` 和一个 `rollback`，运行 `部署`。
    预期：`rollback` 运行一次，输出「部署失败，已回退」，退出码 1。
A9. 操作：用模拟的 pi 接口，从交付开始走一圈到评审通过。
    预期：状态栏依次收到 `dev-loop【已交付】<任务名>`、`dev-loop【复测中】<任务名>`、`dev-loop【评审中】<任务名> · 第 1 轮`、`dev-loop【完成】<任务名>`，窗口标题同步变化。
A10. [人工] 操作：在真实 pi 窗口里交付一次，等复测和评审跑完。
    预期：期间你从窗口底部和标题能一眼看出当前是哪个阶段。
