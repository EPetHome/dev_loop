> 用词
> - **账本**：每张卡一份、只追加的事实记录，用新文件（M2）。状态不另存，一律从账本现算；`status.json`、`checks.jsonl` 照旧按原格式写出，只给外部读，dev-loop 自己不读（IF1）。
> - **意图**：只能由本人发起的记录：开工、答复、加轮、接受未验证、停。由 PA 或协调方代为写入，附本人原话。
> - **事实**：工具或 pi 插件写的记录：准备好、开始（步骤 · sha · pid）、窗口状态、提交、待办、送达、复测、评审、合入、部署等。开发能调的只有 `loop 提问`（写疑问）和 `loop 交付`（触发收货工具）（P4、C2）。
> - **调度器**：`loop tick`，不调用模型、没有记忆，跑一次就退出。每次被叫醒都读账本，找出缺的那一步，后台起一个工具，然后结束。
> - **提交**：收货工具写进账本的提交 sha，也叫「收货提交」。pi 自己在 git 里 commit、还没收货的，叫「git 提交」，不算数：不消掉待办，也不进复测（P3、C2）。本文其余地方说「提交」「新提交」，都指收货提交。
> - **起点**：收货提交和目标分支的合并基点（`git merge-base`），现算不存。平时就是开工时的起点；解决合入冲突、把 dev 合进来以后，自动前移到合进来的那个 dev 提交。范围检查、评审看的 diff、E2E 选跑、起点对照都按它算（C3）。
> - **待办**：最近一次收货以后交给开发的活（开工、评审必修、复测失败、越界清单、答复、合入冲突、部署失败、提醒交付、出错后的「继续」、分诊发的「继续」），之后还没有新的收货提交。可以有多条，重开窗口时全部带上。从账本现算，不存。
> - **工具**：做一件事、可重复调用的命令。按「卡 + 提交 + 提示词哈希 + 验收哈希」记账，同样的输入已经成功过就直接返回。
> - **分诊**：调用模型做判断，只在两种时候用：提醒过仍没交付时，判 pi 做完了没有（C2）；规则归不了类的失败，给出分类建议。不写结论。

**四条铁律**

1. 账本只有工具和 pi 插件能写。开发能调的只有 `loop 提问`（写疑问）和 `loop 交付`（由收货工具检查范围后提交），写不了结论和意图（P4、C2）；本人的意图由协调层代写，附原话；PA 发完通知用 `loop 已通知` 记一笔（C5）。
2. 调度器每次都从账本现算状态，自己不存任何状态；同一张卡同一时间只有一个 tick 在动（卡锁）。
3. 合入、部署只认账本：这个提交同时有复测通过和评审通过，或者有本人的「接受未验证」。评审轮数用完后，评审工具拒绝再跑，只有本人能加轮。
4. 自动恢复只能让这一步再做一次，不能放行，也不能替本人拍板。放行由合入、部署工具自己读账本核对，不采信调度器（K2，第十节「准确性」）。

### 四、调度规则：一张表替代状态机（🔧）

```
对每张在办的卡，先抢卡锁（抢不到说明另一个 tick 正在处理，直接退出），
再从上往下找第一条成立的，做完这一步就结束本轮：

⓪ 有开工意图，还没有「准备好」                          → 准备工具
① 有未关闭的疑问 / 轮数用完 / 开发推不动 / 环境修不好      → 不动，等本人（PA 读 `loop 查询` 后发通知）
② 开发窗口正在干活，或者有工具正在跑，或者上一轮是本人中止的、之后本人还没说过话 → 不动
③ 有待办，开发窗口不在了，或者上一轮出错中断                → 开发工具：重开窗口 / 按退避发「继续」，不扣轮数（I1）
④ 窗口闲、上一轮正常结束，有改动或还没收货的 git 提交、但没调交付，还没提醒过 → 提醒一次（不花钱）
⑤ 窗口闲、上一轮正常结束，提醒过仍没交付，                 → 分诊读最后一段话（第六节）
   或者待办送达后忙过又闲了、没有任何改动
⑥ 最新收货提交没有复测结论                              → 复测工具
⑦ 复测通过，没有评审结论                                → 评审工具
⑧ 最新收货提交有必修 → 写待办（轮数 -1）；通过 → 按卡上授权走收尾（第七节）
```

- **叫醒和并发**：tick 跑一次就退。工具或插件写完事实后顺手调一次，launchd 每分钟再兜底调一次。每张卡一把文件锁，两个 tick 不会同时动同一张卡。
- **「开始」和失败尝试**：工具开跑先写「开始：步骤 · sha · pid」，跑完写结论。有「开始」没结论、pid 还活着 → ② 不动；pid 已经死了 → 记一次失败尝试，下次照常重起。重试次数和熔断都按这些记录现算。
- **待办**（见用词）：⑤ 只看待办，所以复测、评审期间窗口闲着，不会误叫分诊。
- **旧提交的结论**（P2）：⑧ 只处理最新收货提交的结论；评的是更早的收货提交的照记，不发回、不扣轮数。
- **被打断不算做完**（I1）：插件在 `agent_settled` 时记结束方式。只有 `stop` 才可能走 ④ 收货；其余 6 种都不收货、不评审、不扣轮数，并记一行。③ 不处理本人中止的那一轮，直到本人再说话。
- **解除中止**（I1）：本人中止以后，本人说的任何新话都会解除中止：窗口原话，或者在聊天、飞书里说继续（由协调层记成答复）。解除后如果窗口已经不在，③ 照常重开窗口，带上待办。
- **交付和收货**（C2 选 A）：pi 调 `loop 交付` 就是收货工具本身，当场检查范围、提交、写「提交 sha」，不经过 tick；之后 ② 等 pi 这一轮结束，再由 ⑥ 起复测。④ 和 ⑤ 只管「忘了交付」：先提醒一次，再停才分诊，分诊判「做完了」才代为收货。提醒按「提交 + 改动」记一次，同样的改动不重复提醒。
- **决定留痕**：tick 每次做决定都记一行「命中第几条 → 做了什么」，`loop 查询` 直接显示，排查不用自己推。
- **规则顺序靠测试守**：顺序写错不会报错，只会悄悄做错事，所以每条规则一个测试，再用真实账本回放。

| | 现在：收到事件才迁移状态 | 新：看账本补缺口 |
|---|---|---|
| 怎么推进 | 收到「交付」「停下」这类事件，从状态 A 迁到 B | 每次醒来看缺什么就补什么 |

### 十、怎么降低失败后的恢复成本（🔧 K1）

```
恢复成本 = 发生次数 × （发现 + 看懂现场 + 选对动作 + 执行 + 重做）
```

| 环节 | 现在的代价 | 怎么降 |
|---|---|---|
| 发生次数 | 68 次停下 | 删掉胶水，零件变少；开工前「只查」把能提前发现的问题拦在门口；不稳定的测试单独记录，不混进产品失败 |
| 发现 | 机械故障中位要等 12–19 分钟 | 机械故障不需要人发现：调度器自己重试。确实需要人时，PA 立刻推飞书 |
| 看懂现场 | 状态散在 status.json、停下记录、会话进程、工作区、PA 任务单里，几份互相矛盾 | 只有一份真相：账本 + git + 进程；`查询` 现算后一页说清 |
| 选对动作 | 8 种恢复命令，选错会互相踢 | 本人只说人话；每次等本人最多给 4 个选项，写清「不回会怎样」 |
| 执行 | 本人手动跑命令 | 本人的回复由 PA 写成意图，调度器执行 |
| 重做 | 复测一次 10–13 分钟；会话断了，思路跟着丢；同一提交重复评审 | 结论按提交号缓存；会话文件续用加交接笔记；复测提速到 2 分钟以内（AGENTS.md 原定），按改动选跑 |

**六条机制**

1. **错误不落成状态。** 失败只是账本里缺了一条事实，调度器下次醒来自然会补。没有「失败态」，就不需要「恢复命令」。
2. **每一步都幂等，按提交号记账。** 已经成功的步骤，重跑直接返回结果。中途死掉只丢当前这一步，不丢整圈。
3. **先分类，再处理。**

| 类别 | 例子 | 处理 | 交给谁 |
|---|---|---|---|
| 瞬时 | fetch failed、超时、限流 | 按 `retry` 退避重试（默认 3 次，1 / 4 / 16 分钟） | 工具自己 |
| 产出不合格 | 评审格式错、越界改动、没提交 | 把报错原样交回产出方，重做一次 | 产出方（评审员 / 开发） |
| 产品问题 | 复测失败、部署 check 失败 | 发回开发，扣轮数 | 开发 |
| 环境问题 | 依赖装不上、端口被占、凭证过期 | 自动重试几次，不扣轮数；还不行就等本人。和产品问题分不清时，用起点对照（见下文「准确性」） | 本人 |
| 看不懂 | 规则对不上的报错 | 分诊给出分类建议，归入上面几类 | 分诊 |
| 需要判断 | 需求疑问、轮数用完 | 等本人 | 本人 |

4. **熔断。** 每一类重试都有上限（`retry`，默认 3 次），每张卡有总预算（`cardRetryBudget`，默认 10 次，参照 W3-D 守护脚本空转 10 次），防止空转；熔断后只发一次通知。
5. **等本人时，现场自带说明。** 一条消息包括：出了什么事（附原文一句）、已经自动试过什么、不回会怎样，以及 2–4 个选项和各自的后果。轮数用完时另附收敛趋势：每轮必修几条，是否集中在同一文件、同一类问题（R1 第 8 条）。本人用人话回，PA 翻译成意图。
6. **恢复路径进测试。** 测试里在每一步把调度器、工具、pi 窗口各杀一次，断言不靠人也能走完；再用真实的 checks.jsonl 回放（W3-C、B6、W3-D）。现在的恢复类 bug（返修断线、格式误判）都出在没人测过的恢复路径上。

#### 准确性：恢复不能让结论变差（✅ K2，11-23 本人「三条都同意」）

原则：准确性不能指望每次恢复都做对，要靠两条规则兜住：所有自动恢复都只能让这一步「再做一次」，不能放行，也不能替本人拍板；放行只在闸门处判断（铁律 3、4）。这样恢复机制出错最坏也就是白跑或多打扰一次，不会造出假通过。

| 错误 | 例子 | 要求 |
|---|---|---|
| 🔴 假通过 | 没过的提交被合入或部署 | 设计上必须为 0 |
| 🔴 越权 | 模型替本人回答了需求疑问，或替本人接受了未验证 | 设计上必须为 0 |
| 🟡 白跑 / 多打扰 | 半成品被收货，白跑一轮；本来不用等本人，却等了 | 允许发生，用度量盯着 |

```
重试 · 格式重排 · 重跑复测 · 发回开发 · 重开窗口 · 分诊建议
                 │  只能产生一个结果：这一步再做一次
                 ▼
┌ 闸门（合入、部署工具自己读账本，不采信调度器）
│ 放行只认两种证据：
│  A 同一个提交、同一组输入：一条真实跑完的「复测通过」+ 一条「评审通过」
│  B 本人的「接受未验证」意图，附原话
│ 其他记录（不稳、重排、分诊建议、窗口原话）都不能放行
└────────────────────────────────────────
```

**五条硬约束**（对应验收 A6、A2 和测试清单 T2、T7、T8）

| # | 自动动作 | 怎么会出错 | 硬约束 |
|---|---|---|---|
| 1 | 评审格式不对，交回评审员重排 | 重排时评审员把「需返修」改成了「通过」 | 结论以原文为准，重排只用来把条目提取出来；重排时只给解析报错，不给任何新材料 |
| 2 | 复测超时，分诊判「测试挂住」，同一提交重跑 | 带竞态的产品 bug，重跑时碰巧过了 | 分诊只能决定「重跑一次」，不能决定通过；重跑通过也要记一条「不稳」，并带进评审材料；同一张卡里同一个测试第二次不稳，就当产品问题发回开发 |
| 3 | 结论按提交缓存，同样的输入直接返回 | 输入变了，却命中了旧结论 | 缓存键包含所有影响结论的输入：提交的 tree、提示词哈希、验收哈希、test 命令、localFiles 摘要、评审提示词版本和模型。只缓存「通过」和「必修」，失败一律不缓存 |
| 4 | 无记忆调度、多个 tick 并发、进程被杀 | 跳过了一步，或结论记到了别的提交上 | 合入、部署工具自己再核一遍闸门，不依赖调度器；复测和评审在固定 sha 的独立检出里跑，写结论前核对 sha（现在的 `checkPin` 保留） |
| 5 | 分诊读 pi 的最后一段话 | 越权：把 pi 的提问判成「卡住了」，发了「继续」，pi 就自己替本人做了需求决定 | 拿不准一律按疑问处理，宁可多问一次；分诊只能给四种结果：收货（C2，只触发复测和评审，不是放行）、重跑这一步、发回开发（附原文）、等本人 |

**起点对照**：分不清是环境问题还是产品问题时，在起点提交上跑一次同样的检查。起点也挂，算环境问题（不扣轮数）；起点能过，算产品问题（发回开发）。判断是确定的，不用模型，代价是多跑一次检查。

**怎么证明真的准**

| 手段 | 做法 |
|---|---|
| 每条硬约束配一个测试 | 验收 A2、A6，测试清单 T2、T7、T8 |
| 历史回放 | 把全部执行的账本过一遍新闸门：同样的记录，新闸门放行的提交必须和旧闸门完全一致，不一致的逐条列出（验收 A10） |
| 账本自检 | `loop 查询` 每次现算时，核对每条「完成 / 合入」都能找到证据 A 或 B，找不到就报出来。这是报告，不新增拦截点 |
| 漏网率 | 本人验收时发现的问题，回溯到 dev-loop 放行的那个提交；拿[分析-漏网问题回放](分析-漏网问题回放.md)当基线，每批对比 |
| 汇报透明 | 总结里列出这一轮所有自动恢复动作：重试几次、重排几次、几条不稳、分诊判了什么 |

边界：评审本身准不准（必修误报、漏掉 bug）归 R1、换回 astra、历史回查管，恢复机制只保证结论不会比现在更差。残余风险：带竞态的 bug 两次都碰巧通过，不会留下「不稳」信号；这种情况现在也拦不住，不是新架构引入的。

**度量**（都从账本现算，每个阶段和基线对比）：恢复时长（从停下到重新跑起来）、本人介入次数、白跑时长。基线是本文「现状数据」：68 次停下、累计 70.6 小时、介入率 61%。

## 验收标准

本节只验 dev-loop：凡是飞书消息的发送、去重，都在 PA 自己的批次里验，这里只看 `loop 查询` 给出的等待原因和待通知内容。按写法第二节最多 10 条（D2）；其余要测的行为见「完成后需要提供」里的测试清单，同一批次交付。

A1. 操作：一张卡在准备、开窗口、收货、复测、评审、合入这几步，各杀一次 tick、正在跑的工具、开发窗口，之后不做任何操作
    预期：卡自己走到「完成」，没用任何人工命令；开发窗口用原会话文件重开，带上待办；账本里每一步的成功事实都只有一条（转换类：重启前后、重复）
A2. 操作：往账本里手工加一条「完成」，这个提交其实没有复测通过或评审通过，然后调合入
    预期：合入工具拒绝；`loop 查询` 报出这条缺证据的记录
A3. 操作：pi 有改动、正常停下，没调交付，最后一段话是在提问；收到提醒后又停下，还在提问；本人答复后，pi 调 `loop 交付`
    预期：先提醒一次；第二次停下由分诊判成疑问，不收货、不进复测；答复送进窗口；pi 调交付后不经分诊，直接收货、进复测
A4. 操作：pi 改到一半，这一轮因网络出错结束（`error`），工作区留着半成品；另起一次：本人按 Esc 中止后关掉终端，再在聊天里说「继续」
    预期：出错那次不收货、不复测、不评审、不扣轮数，隔 1 分钟自动发「继续」；Esc 之后既不自动继续，也不重开窗口；说「继续」后中止解除，重开窗口并带上待办
A5. 操作：评审调用前 3 次返回网络错误，第 4 次正常
    预期：不等本人；账本里只有一条评审结论；`loop 查询` 里没有待通知的事
A6. 操作：评审员交出一份内容合格、但没有「触发：」标签的评审（用 W3-C 首轮原文）
    预期：交回评审员重排一次后登记；结论仍是需返修，必修条数和原文一致；不出现「临时故障」
A7. 操作：一批两张卡，B 依赖 A，A 没授权合入，调 `loop 开工`；给 A 补上合入授权后原样再调一次；然后再原样调一次
    预期：第一次当场返回原因，账本里什么都没写；第二次返回新的执行编号，开始准备；第三次返回同一个编号，不再开窗口（转换类：失败以后重来、重复）
A8. 操作：合入时和 dev 冲突，pi 把 dev 合进来解决后交付
    预期：冲突清单发回开发窗口，不扣轮数；收货时不出现越界；评审看到的 diff 里没有 dev 上别人的改动；新提交复测、评审都通过后合入
