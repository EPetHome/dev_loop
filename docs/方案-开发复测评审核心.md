## 三、命令（入口 `bin/loop`）

| 命令 | 第几步 | 做什么 |
|---|---|---|
| `启动 <开发卡> [--派单编号 X] [--指令编号 Y] --json` | 1 | 校验卡，建执行目录，写状态文件（进行中），几秒内返回执行编号；之后在后台建 worktree 和任务分支、复制 localFiles、跑 setup、打开开发会话 |
| `交付` | 1 | 开发方在会话里运行：scope 外的改动拒绝并列出；scope 内的改动提交到任务分支，登记交付后马上返回 |
| `查询 [<卡> \| --all] [--brief] --json` | 1 | 读状态文件；`--all --brief` 一次返回全部执行，带 `complete: true` |
| `续跑 / 停止 / 放弃 <卡> [--task 名]` | 1 | 恢复原会话 / 结束会话，标为已停止 / 停止并删除 worktree，保留分支和证据 |
| `合入 <卡> [--commit] [--仅本地] [--接受未验证] [--指令编号]` | 2 | 见第八节 |
| `整合 / 验收 <卡>` | 3 | 见第八节 |
| `答复 <卡> --task 名 --text-file F --指令编号 Y` | 4 | 只在「要你决定」时接收，送进会话，记录来源「经 PA」 |
| `开发 pi\|claude\|codex --cwd` | 4 | 在当前目录直接开发（不建 worktree），走同一圈逻辑 |

开发方定位自己的任务：优先用环境变量 `LOOP_TASK_DIR`；没有时按当前目录匹配登记过的 worktree。

## 四、数据

- 🔧 根目录：`~/.dev-loop/tasks/<执行编号>/`，与旧 loop 的 `~/.pi-autoreview` 完全分开；可用环境变量覆盖，测试一律指向临时目录。
- 执行编号：`<项目>-<卡名>-<任务名>-<6 位随机>`，文件名一律用 ASCII。

| 文件 | 内容 | 写法 |
|---|---|---|
| `task.json` | 启动时定下的信息：仓库、卡路径和哈希、任务名、提示词路径、scope、测试命令、分支、worktree、各项上限、派单编号、宿主 | 只写一次 |
| `checks.jsonl` | 每行一条：commit、tree、步骤（复测/评审）、结果（通过/失败/必修/没验证）、开始和结束时间、耗时、证据路径、提示词哈希、验收标准哈希 | 只追加 |
| `status.json` | 给本人和 PA 看，字段见下表 | 每次变化时原子重写 |
| `instructions.jsonl` | 处理过的指令：编号、类型、结果 | 只追加 |
| `test-<commit>.log`、`review-<commit>-r<N>.md`、`summary.md` | 证据和一屏总结 | — |

✅ **结论只看 commit**：同时满足下面三条，这个 commit 就算检查过，别的都不参与判断。

- `checks.jsonl` 里这个 commit 有复测通过（或没验证）；
- 也有评审通过；
- 提示词和验收标准的哈希与现在一致。

`status.json` 字段（含义按需求书-PA 第七节）：

| 字段 | 内容 |
|---|---|
| `protocol` | 约定版本，如 `loop-status/1` |
| `source` | `{ worker: "loop", instance: 本机名 }` |
| `executionId`、`dispatchId`、`batchId` | 执行编号；派单编号（PA 派的才有）；批次编号（第 3 步起，多任务卡才有） |
| `state` | `working` / `input_required` / `completed` / `failed` / `cancelled` |
| `message` | 一句人话；`input_required` 时写清要决定什么、有哪些选项 |
| `updatedAt`、`seq`、`generation` | 最后更新时间；每写一次加 1；执行目录重建时才加 1 |
| `heartbeatSec`、`timeLimitSec` | 心跳间隔 60 秒；当前这一步的时限 |
| `refs` | 提示词、验收标准、卡的路径 |
| `error` | `failed` 时必填：`{ category, raw }`，category 取 PA 的六类 |
| `evidence`、`actions` | 证据和总结的路径；支持的动作 |
| `loop` | 阶段（开发中/复测中/评审中/等你/完成/失败/已停止）、当前 commit、复测退回次数、评审轮次、会话进程身份（宿主、进程号、启动时间）、各步耗时 |

失败分类：

| 情况 | 类别 |
|---|---|
| 评审调用网络失败，重试后仍失败 | 临时故障 |
| 卡、提示词、scope 不合法 | 输入问题（`启动` 直接返回错误，不建执行） |
| 卡上有还没支持的步骤 | 不支持 |
| git 推送被拒、文件没有权限 | 权限不足 |
| dev-loop 自己抛出的异常 | 工具内部错误 |
| 其他 | 未知 |

## 五、一圈怎么推进

```
            启动
             │
             ▼
        ┌─ 开发中 ◄────────────────────────────┐
        │    │ bin/loop 交付                    │ 退回（测试输出 / 必修）
        │    ▼                                  │
        │  已交付 ──会话停下──► 复测中 ──通过──► 评审中 ──通过──► 完成
        │                         │失败            │必修
        │                         └────────────────┘
        │                         到上限 ──► 等你
        └─ 停下但没交付 ──► 提醒一次 ──再停──► 等你
     任何时候：自身出错 ──► 失败；停止 ──► 已停止
```

会话停下时，三家宿主都调用同一个处理函数，按下面的顺序判断：

1. 有登记的交付，且当前 HEAD 的 tree 和交付时一致、工作区没有未提交的改动 → 往下走。
2. 交付之后又改了代码 → 退回一句「交付后又改了，做完请重新运行 bin/loop 交付」。这一步不计入退回次数。
3. 这个 commit 已经检查过 → 直接完成，总结里写「沿用」。
4. 复测：在 worktree 里用 `sh -c` 跑卡上的测试命令，按时限执行。
   - 退出码为 0 → 通过。
   - 否则退回：命令、输出最后 60 行、含 error/fail 的行；完整输出写进日志。
   - 测试写的是「无：原因」→ 记为没验证，继续评审。
5. 评审：组装输入，调用 astra，解析结果。
   - 通过 → 完成。
   - 需返修 → 只退回必修，每条写明「文件:行」和触发条件；建议和需求疑问只写进文件。
   - 调用重试一次仍失败 → 失败（临时故障）。
6. 停下时既没交付也没改动 → 转「等你」，把开发方最后一段话放进 `message`；有改动但没交付 → 提醒一次，再停仍没交付就转「等你」。

- 每个任务同一时刻只处理一次停下，用锁文件保证。
- 退回上限：复测 3 次，评审必修 4 次，分开计数，卡上的 `limits.测试`、`limits.开发评审` 可以覆盖。到上限后转「等你」，选项是：再给一轮 / 停止 / 接受未验证。
- 时限：复测 20 分钟，评审每轮 60 分钟，卡上可以覆盖。
- 每一步都计时，结果写进 `checks.jsonl` 和 `status.json`；总结里分别列出开发、复测、评审、等你、dev-loop 自身各花了多少时间。

## 六、评审

输入只给这几样：

- 提示词原文；
- 验收标准（卡上有的话）；
- 任务分支起点到本次 commit 的 diff 和新增文件列表；
- 开发方最后的交付说明；
- 复测的命令和结果；
- 第 2 轮起，再加上一轮的必修清单和开发方的回复。

评审规则在旧的 `review-prompt.md` 基础上改：

- 「材料」一节加上复测结果；
- 明确「风格、结构、命名不列必修」；
- 第 2 轮起，先核对上轮必修，再只看本轮新改动和它影响到的地方；
- 输出格式不变。

模型和思考档默认为 astra、xhigh，可以用项目的 `.autoreview.json`（`reviewerModel`、`reviewerThinking`、`reviewerCmd`）覆盖。

## 八、附加步骤（第 2、3 步）

- **合入（第 2 步）**：只合入已经检查过的那个 commit；卡上选了验收的，验收也要在这个 commit 上通过。
  - 先拿到仓库锁，确认目标分支和 commit 与本人确认的一致，再合进 dev。
  - 推送 origin/dev 前，对这次要推的全部提交做密钥扫描；扫出问题或扫不了，都不推。
  - 同一个指令编号重复来，返回第一次的结果。
  - 结果说不清时如实报「说不清」，不自动重推。
  - `--仅本地` 只在本地合入；`--接受未验证` 只能由本人决定。
- **整合（第 3 步）**：任务完成后依次 `git merge` 进批次分支；有冲突就退回对应任务。
- **验收（第 3 步）**：从旧 loop 的 `acceptance.ts`、`acceptance-core.ts` 复制逐条执行和留证的部分。在批次分支上跑，失败条目按 `[任务名]` 退回，重验规则按需求。
- **部署**：本期不做；卡里写了部署，`启动` 时直接拒绝。
