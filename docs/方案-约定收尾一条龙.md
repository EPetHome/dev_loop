## 三、开发卡

沿用 `flow`，不加新字段。写法文档已有的规则是「流程由协调方写进卡里，不让模型在运行中决定」。

```json
"flow": ["开发评审", "测试", "合入", "部署"]
```

`src/core/card.ts` 第 60–66 行的校验改成：

| 写法 | 结果 |
|---|---|
| 顺序必须是 `开发评审, 测试, 合入, 部署, 推送` 的子序列，第一项必须是开发评审 | 不符则拒绝 |
| 写了部署或推送，没写合入 | 拒绝 |
| 写「提交」 | 仍拒绝，提示改写「合入」，提交已由 `交付` 完成 |
| 写「验收」「整合」 | 仍拒绝，第 3 步才支持 |

解析结果多一个 `after`，取 flow 里合入及之后的部分。core 只看 `after.length`，守住「核心不感知附加步骤」。

**为什么建议写在卡上。** 卡由协调方写，不花本人工夫；开卡时默认写到部署，体验和项目默认一样。项目默认多一层配置和优先级规则，而且没写的旧卡重新启动时也会自动上线。

**启动快照。** `createTask` 把 `after` 存进 `task.json`，收尾只读这份。旧执行没有这个字段，按没有收尾处理。

**启动时校验**放在 `src/cli/main.ts` 的启动分支，在创建执行目录之前：

- flow 含部署：`loadDeploy(repo)` 必须登记了 `cmd`、`check`、`rollback`。
- flow 含推送：必须有 origin。
- 不检查脚本文件是否存在，因为这批可能正是来添加脚本的。部署时会在该 commit 的检出里再查一次。

手工 `bin/loop 部署` 不要求 `rollback`，和现在一样。

### 三之二、多批接力

卡加一个可选字段 `next`，相对卡文件目录，指向下一张卡：

```json
{"name": "第 1 批", "flow": ["开发评审", "测试"], "next": "../第2批/开发卡.json"}
{"name": "第 2 批", "flow": ["开发评审", "测试", "合入", "部署"]}
```

| 规则 | 做法 |
|---|---|
| 启动时 | 沿 `next` 把整条链解析一遍；有环、某张解析失败、中间批写了合入以后的步骤，都拒绝，不建执行目录 |
| 下一批的起点 | 上一批的交付 commit，不是 dev。`createTask` 加参数覆盖 `baseCommit`。所以 dev 全程不动，最后一批合入时一次带上所有批次 |
| 评审范围 | 每批只评审自己相对上一批的改动，现有 `settle` 第 91 行用 `baseCommit`，不用改 |
| 触发 | `settle` 的收尾分支条件变成 `t.after?.length || t.next`；`cli/finish.ts` 走完 `after` 后，有 `next` 就 `createTask` 加 `background` |
| 对外状态 | 上一批转 completed，`loop.next` 写下一批的执行编号，派单编号沿用 |
| PA | 读到 `loop.next` 就跟到下一个执行，不发「做完了」（PA 那批改，约 5 行） |
| 中途停下 | 后面的不启动。修好后走完这批，`next` 照常接上 |

## 四、触发

依赖规则是 `hosts` 不能引用 `steps`，`core` 不感知附加步骤（`test/dependencies.test.ts` 强制检查）。所以用子进程，和 `src/cli/main.ts` 拉起 `launch.ts` 的做法一样：

```
core/settle.ts        只把状态转成「收尾中」
hosts/pi.ts、hook.ts   settle 返回后，看到「收尾中」就拉起进程
cli/finish.ts         组合合入、部署、推送（只有 cli 能引用 steps）
```

新文件 `src/hosts/after-settle.ts`：

```ts
export function startFinish(dir: string): void {
  const s = statusOf(dir);
  if (s.loop.phase !== "收尾中" || alive(s.loop.finisher)) return;
  const fd = openSync(join(dir, "finish.log"), "a");
  try {
    spawn(join(APP_ROOT, "bin/loop"), ["收尾", dir, "--json"],
      {cwd: taskOf(dir).repo, env: process.env, detached: true, stdio: ["ignore", fd, fd]}).unref();
  } finally { closeSync(fd); }
}
```

调用点：`src/hosts/pi.ts` 第 55 行、`src/hosts/hook.ts` 第 20 行，都在 `settle` 之后、`continue` 为假时。

**必须脱离会话**：用户可能关窗口；Claude、Codex 的 Stop hook 有 4900 秒时限；PA 部署自己时会重启，PA 发起的执行不能跟着 PA 一起死。这个独立进程也是「PA 之外」负责退回的那个东西。

## 六、收尾命令

新文件 `src/cli/finish.ts`，命令是 `bin/loop 收尾 <执行编号或卡路径> [--json]`。自动触发和手工重试走同一条路径。

```
1. 没有 after → 拒绝「这张卡没有约定收尾」
2. 阶段不是「收尾中」，等待原因也不是「收尾没走完」 → 拒绝「当前不在待收尾」
3. 拿本执行的 finish.lock，拿不到 → 拒绝「正在收尾」
4. 登记 finisher，转 working、「收尾中」，timeLimitSec 置空
5. 每 60 秒 heartbeat
6. 排队：拿项目级锁，拿不到每秒重试，期间 message 写「排队中」
7. 按 after 运行，每步之前检查 state 是否 cancelled：
     只到合入：merge(dir, {commit, acceptUnverified: false})
     到部署：  prepared = prepareMerge(dir, commit)     检查资格、试合并，不动 dev
               deploy(dir, {commit: prepared})
               merge(dir, {commit, prepared})           dev 快进到 prepared
     推送：    push(dir)
8. 全部成功 → 写 结果.md；有 next 就启动下一批；转 completed，阶段保持最后一步
     message 写：验收标准位置、中途退回次数和原因、另有几批待验
9. 任一步抛错 → checks.jsonl 记「收尾 / 失败」，按第六节之二分流
10. 无论如何：清 finisher、停心跳、放锁
```

**试合并**（`src/steps/merge.ts` 新增 `prepareMerge`）：

```
检查合入资格（和 merge 第 11–18 行相同）
已在 dev → 直接返回 dev 当前 commit
git merge-tree --write-tree dev <commit>     有冲突就抛错，列出冲突文件
git commit-tree <tree> -p dev -p <commit> -m "Merge ..."
```

本机 git 2.39.5 支持 `--write-tree`（需要 2.38 以上）。这样生成的提交和真合并结构一样，但 dev 不动。部署成功后在 dev 的检出目录运行 `git merge --ff-only <prepared>`。整个过程持有项目级锁，dev 不会在中途被别的收尾移动。

**为什么不合并后再部署**：先合入的话，部署失败时 dev 留着一版没上线的代码，下一批会基于它继续。用 `git revert` 撤销也不行：同一分支再合并时，之前的内容不会回来。

其他要点：

- 项目级锁放在 `tasksRoot()/.queue-<仓库路径摘要>.lock`，复用 `src/infra/files.ts` 的 `lock`。它的等待是阻塞式的，会卡住心跳，所以用 `waitMs=0` 在外层异步重试。
- 手工 `合入`、`部署`、`退回` 也进同一个队列。
- `停止`：`stop()` 不向 `finisher` 发信号，第 7 步的检查负责不再进入下一步。
- `续跑`（`src/core/lifecycle.ts`）：第 66 行把 `finisher` 算进「正在检查」；第 68 行沿用分支加条件 `s.loop.wait !== "收尾没走完"`，让失败后续跑回到开发。
- `交付`（`src/core/deliver.ts`）：`alive(s.loop.finisher)` 时拒绝。

### 六之二、失败分流和返修

| 失败 | 去向 |
|---|---|
| 试合并冲突 | 退回开发方 |
| 部署失败，已回退（含线上没动过） | 退回开发方 |
| 部署失败，回退也失败 | 等你 |
| 合入资格不足、推送失败 | 等你 |

```

转 working、「开发中」
```

### 六之三、结果

收尾结束时，`cli/finish.ts` 在卡所在目录写 `结果.md`。已存在就追加一节，不覆盖。只写事实：commit、合入前后的 dev、部署时间、证据目录、退回次数和原因、验收标准位置。结论由协调方下次开会话时补。

待验数：统计卡目录同级的 `../*/验收.md` 里第一行是「状态：待验」的文件。

## 七、退回命令

`bin/loop 退回 <执行编号或卡路径> [--json]`，实现放在 `src/steps/deploy.ts`，和部署共用检出和运行脚本的代码。

```
1. 读项目级记录 tasksRoot()/.deployed-<仓库路径摘要>.json（部署成功时写入）
2. 这个执行不是项目最新一次部署 → 拒绝（无法执行，不是规则）
3. 检出当时部署的 commit，运行登记的 rollback
     环境变量：LOOP_DEPLOY_COMMIT、LOOP_REPO、LOOP_EVIDENCE_DIR=当时的证据目录、LOOP_DEPLOY_FAILED=manual
4. 记录，阶段「已退回」；dev 不动；清掉项目级记录
```

退回之后 dev 比线上新。协调方开下一张卡时要知道这一点：修好之前，别的批次卡上写到合入。这是流程约定，不加程序拒绝。

## 十二、PA 接入（在 PA 项目开卡）

### 部署脚本

步骤来自 11-10 和 11-11 两次实际部署，改了三处：看门狗不停、等空闲、加观察。

```
deploy.sh（在临时检出里运行）
  1. 构建、类型检查、跑测试                    ┐
  2. 预演迁移：拿配置副本跑，检查每个都能反向  │ 线上没动，
  3. 用新代码校验迁移后的配置和设置            │ 失败就退出
  4. 备份应用（应用文件不变，不用停服务）      │
  5. 等 PA 空闲，最多 30 分钟                  ┘
  ──────────── 从这里开始动线上 ────────────
  6. 停主服务，确认退出（看门狗不停）
  7. 备份数据，逐文件核对（排除看门狗自己的状态文件）
     备份路径写进 $LOOP_EVIDENCE_DIR
  8. 跑迁移，原子替换应用和配置
  9. 起主服务，等到 ready

deploy-check.sh
  观察 OBSERVE_MIN 分钟：主服务 PID 不变、心跳前进、飞书连着、模型失败数没增加
  运行的文件和 commit 一致
  全部通过后，重启看门狗换新版，等到 ready

deploy-rollback.sh
  证据目录没有备份路径 → 什么都不做（线上没动过）
  有 → 调用备份里上一版的回退程序：
       停主服务 → 换回旧应用 → 跑迁移的反向转换 → 起主服务 → 确认看门狗在
```

设计理由：

| 点 | 理由 |
|---|---|
| 空闲的判断 | 沿用今晚的条件：`activeInput` 为空、运行中的 Pi 作业为 0。别的 dev-loop 批次在跑不用等，它们是独立窗口，PA 重启后能接上 |
| 看门狗不停 | 切换失败且回退失败时，还有它报警。切换超过 2 分钟会多报一条「停了」，恢复后再报恢复 |
| 看门狗最后换 | 观察期内由旧版看着新版，新版看门狗有问题时也能退回 |
| 回退用上一版的程序 | 这批把脚本改坏时，回退不受影响。第一次接入时没有上一版，用自己的 |
| 数据不恢复 | 新版本运行期间写入的内容不能丢 |

### 迁移约定

- 位置：`code/agent/deploy/migrations/<批次名>.mjs`，随这批代码提交，导出 `up` 和 `down`。
- `down` 基于**当前**配置反向转换，不用备份覆盖，所以运行中改过的授权不会复活。
- 授权项目、设置、标准这些本人运行中会改的文件，退回时不覆盖。
- 没有 `down` 的，第 2 步失败，线上没动。这种批次卡上只写到合入，部署时找本人。
- 已跑过的记在本机账本，同一份不跑第二次。
- 预演只查得出新代码读不了的配置。数据含义上的迁移（比如 11-11 的模型时钟）校验不出来，靠协调方开卡时判断和评审。

| 项 | 内容 |
|---|---|
| 备份 | deploy.sh 观察通过后，只删自己创建的、最老的备份，保留最近 2 份；部署前磁盘低于 3G 就退出，线上不动。旧格式的备份没有 manifest，脚本不碰，存量单独清理 |

| 启动说明 | 第 30、56 行的旧话改掉 |

### 备份实现（✅ 11-11 本人：「写入吧」）

目录结构，新备份放进单独的子目录，脚本只管这里，上一层的旧备份和改配置前的小备份，结构上碰不到：

```
~/.personal-agent-backups/deploy/<UTC 时间>-<短 commit>/
  app/            旧应用，改名移入，是唯一一份
  data/           数据目录克隆
  attachments/    附件克隆
  config/         配置、设置、授权项目、标准（小文件，普通复制）
  plists/
  manifest.json   createdBy、commit、时间、state（ok / rolled-back）、data 的逐文件摘要
```

deploy.sh 里和备份有关的部分：

```sh
ROOT="$BACKUP_ROOT/deploy"
B="$ROOT/$(date -u +%Y%m%dT%H%M%SZ)-${LOOP_DEPLOY_COMMIT:0:7}"
STAGE="$ROOT/.stage-$$"

# 切换前，线上没动
[ "$(stat -f %d "$APP_DIR")" = "$(stat -f %d "$BACKUP_ROOT")" ] || exit 1   # 跨卷时 cp -c 会静默变成整份复制
[ "$(df -k "$BACKUP_ROOT" | awk 'NR==2{print $4}')" -ge 3145728 ] || exit 1  # 少于 3G 不部署
mkdir -p "$STAGE"; cp -R code/agent/. "$STAGE/"
if cmp -s code/agent/package-lock.json "$APP_DIR/package-lock.json"; then
  cp -cR "$APP_DIR/node_modules" "$STAGE/node_modules"                       # 依赖没变：克隆
else
  (cd "$STAGE" && npm ci)
fi
(cd "$STAGE" && npm run typecheck && npm run build && <测试命令>)

# 主服务停止后
mkdir -p "$B/config"
cp -cR "$DATA_DIR" "$B/data"
cp -cR "$ATTACH_DIR" "$B/attachments"
cp "$CONFIG" "$SETTINGS" "$PROJECTS" "$STANDARDS" "$B/config/"
# 校验：data 逐文件 sha256 和原件比，排除 *-shm、watchdog-*、日志；两个 sqlite 跑 integrity_check
echo "$B" > "$LOOP_EVIDENCE_DIR/backup-path"

# 切换
mv "$APP_DIR" "$B/app"
mv "$STAGE" "$APP_DIR"
# 写 manifest.json，state=ok
```

deploy-rollback.sh：

```sh
B="$(cat "$LOOP_EVIDENCE_DIR/backup-path" 2>/dev/null)" || exit 0   # 没有备份路径：线上没动过
# 停主服务
if [ -d "$B/app" ]; then
  [ -d "$APP_DIR" ] && mv "$APP_DIR" "$B/app.failed"                # 两步 mv 可能只完成了第一步
  mv "$B/app" "$APP_DIR"
fi
# 用当前配置跑迁移的 down；数据默认不恢复
# 起主服务；manifest state=rolled-back
```

清理放在 deploy-check.sh 观察通过之后：列出 `$ROOT` 下 manifest 的 `createdBy` 为 deploy.sh 的目录，按时间倒序，保留最新 2 个 `state=ok` 的，比它们更旧的 `rm -rf`。删旧备份不影响线上：APFS 按引用计数，共享的数据块还有人用就不会释放。

验证过的事实（11-11 在本机）：`cp -cR` 克隆 208MB 的真实依赖目录用时 1 秒、实际占用约 5MB（元数据），7983 个文件内容一致，6 个符号链接保留；应用目录、备份目录、数据目录在同一个卷。

要注意的点：

| 点 | 处理 |
|---|---|
| `cp -c` 跨卷不报错，静默整份复制 | 切换前比较卷号 |
| SQLite 用 WAL 模式，数据在 `.sqlite` 和 `-wal` 两个文件里 | 整个目录一起克隆，主服务停止后才做 |
| 看门狗不停，它的只读连接会动 `-shm`，还在写自己的状态文件 | 校验时排除，克隆后跑 `integrity_check` |
| 两步 `mv` 之间中断 | 回退脚本判断 `$APP_DIR` 是否存在 |
| 回退后 `$B/app` 已被移走 | manifest 标 `rolled-back`，不算有效备份 |

## 十二之二、留痕（🔧）

和部署同一个分工：框架通用，指标由项目报。

```
dev-loop（通用）                         项目（每个项目一份）
部署前运行 snapshot，存基线       ──►    snapshot 脚本：输出统一格式的 JSON
观察结束运行 snapshot，存一份            每个节点的次数、失败数、耗时
bin/loop 对比 <执行编号>：                资源占用（CPU、内存）
  现在和基线逐项比，写报告
```

- 配置：`.autoreview.json` 顶层加 `snapshot`，可选，仓库内可执行文件的相对路径，规则和 `deploy.cmd` 相同。没登记、或这个 commit 里没有这个脚本，就跳过，不拒绝。
- 脚本的约定：环境变量 `LOOP_SNAPSHOT_MODE` 为 `scenario`（用替身跑固定场景）或 `live`（读线上进程、资源、配置），`LOOP_SNAPSHOT_OUT` 是输出文件路径，写一个 JSON 对象。时限 5 分钟。
- 什么时候运行：

| 时机 | 模式 | 在哪运行 | 存到 |
|---|---|---|---|
| 开工时（陪跑） | scenario | 陪跑工作区，起点 commit | `<任务目录>/snapshot-base.json` |
| 复测通过后、评审前 | scenario | 开发工作区，交付 commit，用 `core/run.ts` 的 `run` | `<任务目录>/snapshot-<commit>.json` |
| 部署 cmd 之前 | live | 部署的临时检出 | `<证据目录>/snapshot-before.json` |
| check 成功之后 | live | 部署的临时检出 | `<证据目录>/snapshot-after.json` |

- 比较：新文件 `src/infra/snapshot.ts`，把两个 JSON 拍平成「路径 → 值」逐项比，输出新增、减少、变化的行。纯函数，不理解指标含义。
- 评审材料（`settle.ts` 第 94 行的 `material`）加一节「运行差异」：`git diff --name-only 起点 交付` 的文件清单，加 scenario 基线和这次的比较结果。缺文件就写「没有基线」。
- 命令 `bin/loop 对比 <执行编号> [<另一个执行编号>]`：只给一个编号时，现场运行一次 live，和这次部署的 `snapshot-after.json` 比；给两个编号时，比两次部署的 `snapshot-after.json`，用于和上一次验收通过的版本比。
- 所有 snapshot 失败都只写一条 `留痕 / 失败` 记录，不改状态，不影响复测、评审、部署。
- 第一次基线在项目接入时记录。
- 观察期只有几分钟，本机程序这段时间可能没有请求，所以观察结束时只比进程和资源；节点耗时要积累一段时间，用 `对比` 命令按需看。
- dev-loop 自己的流程留痕已有：`checks.jsonl` 记了每一步的结果和耗时，收尾各步也会记进去。

基线的内容（🔧 11-11 本人回复「可以」，暂定）：

| 层 | 记什么 | 谁出 |
|---|---|---|
| 通用静态 | commit、依赖摘要、两次部署之间改了哪些文件 | dev-loop 内置，项目不用写 |
| 项目静态 | 配置差异、进程、内存磁盘、累计计数 | 项目 snapshot 脚本 |
| 固定场景轨迹 | 用替身模型跑固定场景，记节点路径、工具次数、token | 项目 snapshot 脚本；写不出场景的项目跳过 |

- 基线不用人定：每次部署成功自动存一份。默认和上一次部署比，也可以和上一次验收通过的比。

## 十二之三、陪跑（方向 ✅ 11-11，做法 🔧）

```
开工 ─┬─ 开发工作区：开发方只管写代码
      └─ 陪跑工作区（同一 commit 起步，碰不到开发方）
           旧版构建 → 跑固定场景 → 存基线
开发方交付 → 复测 → 评审，同时用新版跑同样的场景 → 和基线比 → 差异交给评审
```

做法：

```
hosts/launch.ts 的 launchMain 在 prepare 完成后，拉起独立进程 bin/loop 陪跑 <任务目录>
（子进程方式和 startFinish 相同，日志写 companion.log）

cli/companion.ts：
1. 项目没登记 snapshot → 记「陪跑 / 跳过」，退出
2. git worktree add --detach <任务目录>/companion <baseCommit>
3. 复制 localFiles，运行 setup
4. 脚本不存在 → 记「陪跑 / 跳过」；存在 → 运行，LOOP_SNAPSHOT_MODE=scenario，
   输出到 <任务目录>/snapshot-base.json，临时数据放这个工作区内
5. 记「陪跑 / 基线已存」或「陪跑 / 失败」
6. 无论结果，git worktree remove --force 删除陪跑工作区
```

- 只用 `appendCheck` 写记录，不调 `update`，不碰 state 和阶段，所以影响不到开发方。
- 接力的下一批起点是上一批的交付，同样跑自己的基线。
- 第 1 批不开独立小会话，场景和验收标准由协调方开卡时写（⏳ 试用后再看）。

## 十二之四、释放

`bin/loop 释放 <执行编号或卡路径> [--json]`：

```
1. state 不是 completed，或已释放 → 拒绝（无法执行）
2. git worktree remove --force 删除开发工作区
3. 保留分支、checks.jsonl、日志、证据目录
4. 记「释放 / 已释放」，status.loop.released = true，阶段不变
```

- 由协调方在本人验收通过后运行。
- 释放后 `续跑` 拒绝，提示工作区已释放。
- 陪跑工作区、部署临时检出用完就删，不等释放。

## 十三、风险与没验证
