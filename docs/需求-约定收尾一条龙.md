## 问题描述

本人的初衷（✅ 11-11）：「这几个步骤是在开发前就约定好了，一条龙走完的。所以站在我的角度是这个功能没有完善好，只做了一半，现在要补上。」

现状是 dev-loop 走到「完成」就停。合入、部署只是两条命令，要有人去运行：

```
本人的初衷：开卡时约定 → 开发 → 复测 → 评审 → 合入 → 部署
实际做到的：             开发 → 复测 → 评审 → 停
                                          └ 靠模型听懂一句话，再现场想办法
```

问题有四个：开发前说好的事，开发完还要再下一次令；模型要现查流程；项目没有固定的部署方式，每次现场编；手工部署没有记录，状态还会被改回「完成」。

## 复现步骤

1. 跑完一张卡，`bin/loop 查询` 显示「完成」，之后什么都不会自动发生。
2. 在卡的 `flow` 里写「部署」，`bin/loop 启动` 拒绝。
3. 对 PA 运行 `bin/loop 部署 <执行编号>`，拒绝，报「项目没有登记部署脚本」。
4. 运行 `bin/loop 合入` 成功后让开发会话再停一次，阶段从「已合入」变回「完成」。

### 三、走法

卡的 `flow` 可选的完整顺序：`开发评审 → 测试 → 合入 → 部署 → 推送`。

| 卡上的 flow | 评审通过后 |
|---|---|
| `开发评审, 测试` | 停在「完成」，和现在一样 |
| `开发评审, 测试, 合入` | 自动合入，停在「已合入」 |
| `开发评审, 测试, 合入, 部署` | 先试合并，部署成功后 dev 才前进，停在「已部署」 |
| `开发评审, 测试, 合入, 部署, 推送` | 再推送到远端，停在「已推送」 |

### 五、退回

- 🔧 新命令 `bin/loop 退回 <执行编号>`：把线上换回这次部署之前的版本。只能退回这个项目最新的一次部署。
- 🔧 **退回只动线上，不动 dev。** git 里撤销一个合并后，同一分支再合并时，之前的内容不会回来，会造成代码丢失。所以修复向前走。
- 🔧 **退回不能让已撤销的权限复活。** 授权项目、设置、标准这些本人运行中会改的文件，退回时不覆盖；配置按当前内容反向转换。

### 六、部署方式

- 🔧 卡上写了部署的，项目必须登记部署、检查、回退三个脚本。能退回是自动部署的前提。
- 🔧 这批要迁移配置或数据的，迁移必须能反向转换。做不到就是撤不回的事，这批的卡只写到合入，部署时找本人。
- 🔧 切换前等 PA 空闲：没有正在处理的输入、没有运行中的 Pi 作业。
- 🔧 切换后观察一段时间，稳定才算部署成功。

应付变动：

| 变动 | 做法 | 谁 |
|---|---|---|
| 项目第一次接入 | 写三个脚本并登记 | 协调方开批，开发方写 |
| 普通批次 | 不动，直接运行 | 没人写 |
| 这批改了配置或数据 | 脚本不动，随这批加一个迁移文件 | 这批的开发方 |
| 值变了（路径、服务名） | 改 `deploy.env` | 协调方 |
| 部署步骤本身变了 | 改脚本，和这批代码一起提交 | 协调方判断，开发方写 |

🔧 谁来判断：项目接入时，协调方问本人要不要部署、怎样算成功；开卡时，协调方判断这批影响不影响部署。

### 十五、留痕（🔧）

本人原话：「我们需要留痕，这样哪怕改动大其实也还是好定位的。比如我们先记录一次当前执行情况，每个接口、节点啊执行清楚，执行时间、负载啊等等，有个基线，然后更新了出问题也好定位。」「这个对每个项目都是有好处的。」

草案：和部署同一个分工，dev-loop 管存和比，项目报自己的指标；项目没登记就跳过，不拒绝。细节见详设第十二节之二。

✅ 陪跑（11-11）：「我觉得开发方压力大了，在一个节点就是开发的时候，能不能同步并行走一个小环境，和开发方同源开始不干涉？」协调方说明后，本人回复「可以。记录。」

做法：开工时从同一个 commit 另开一个陪跑工作区，和开发方同时跑，互不影响。

| 工作 | 放哪 | 状态 |
|---|---|---|
| 跑旧版基线（纯程序） | 陪跑 | 🔧 |
| 写这批新增的场景、验收标准草稿 | 🔧 第 1 批不开独立小会话，由协调方开卡时写；试用后再看要不要 | ⏳ |
| 用新版跑同样的场景，和基线比，差异交给评审 | 交付后 | 🔧 |
| 这批的迁移脚本、部署失败返修 | 留给开发方 | 🔧 |

不干涉靠：独立工作区、独立的临时数据目录、产出只写进任务目录；陪跑失败只记录，不影响开发和收尾，不新增拒绝。

## 验收标准（程序检查，这是写法要求的字段）

A1. 操作：用 flow 写到部署的卡，从交付走到评审通过，之后不运行任何命令。
    预期：部署替身运行时 dev 还没变；部署成功后 dev 等于替身收到的 commit；最后 state 为 completed、阶段为「已部署」；除评审替身外没有模型调用。
A2. 操作：用 flow 写到合入的卡走到评审通过。
    预期：dev 多一个合并提交；部署替身运行 0 次；阶段为「已合入」。
A3. 操作：部署替身运行时读取 `status.json`。
    预期：state 是 working，阶段是「部署中」。
A4. 操作：登记一个失败的检查脚本和一个回退脚本，flow 写到推送，走到评审通过。
    预期：回退运行一次；dev 不变；推送没有发生；state 为 working、阶段为「开发中」，开发方收到失败原因。
A5. 操作：A4 之后开发方把检查脚本改成成功，重新交付。
    预期：自动再走复测、评审、收尾；dev 前进；最后 state 为 completed，message 写明退回过 1 次和原因。
A6. 操作：让回退脚本也失败。
    预期：不退回开发方；state 为 input_required，等待原因为「收尾没走完」，message 写明回退也失败。
A7. 操作：用两张接力的卡，第 1 张不写收尾，第 2 张写到部署，从第 1 张交付开始。
    预期：第 1 张通过后第 2 张自动启动，起点是第 1 张的交付；第 2 张部署前 dev 不变；部署后 dev 包含两张的改动。
A8. 操作：A1 完成后，让开发会话再停下一次。
    预期：部署替身的总运行次数仍是 1；阶段仍是「已部署」。
A9. 操作：同一项目的两个执行同时走到收尾，部署替身记录开始和结束时间。
    预期：两次部署的时间段不重叠，两个执行最后都是 completed。
A10. 操作：A1 完成后运行 `bin/loop 退回 <执行编号>`。
    预期：回退替身运行一次，收到这次部署的证据目录；dev 不变；阶段为「已退回」。
