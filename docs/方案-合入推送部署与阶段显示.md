## 一、总体做法

- 三个附加步骤各占 `src/steps/` 下一个文件：`merge.ts`、`push.ts`、`deploy.ts`。按依赖规则，它们之间互不引用。「合入后推送」由 `cli` 先调 `merge` 再调 `push` 组合完成。
- core 只新增**通用**函数：查缺了哪些检查、追加一条记录并按规则改阶段、总结里显示任意额外步骤。core 不出现「合入」「推送」「部署」这些词。
- 阶段做成 core 里的常量，共 19 个。准备中、已交付、已放弃三处拆分和等你的原因，都在 core 现有的 transition 调用处改。
- pi 阶段显示在 `src/hosts/pi.ts`：每秒读一次 `status.json`，有变化就写状态栏和窗口标题。做法与旧 loop `kernel-pi.ts` 相同。
- 不新增依赖，不新增构建步骤。src 现在 1083 行，上限 2000 行（`test/dependencies.test.ts`），本方案预计新增约 400 行。

## 三、infra 新增

| 函数 | 位置 | 行为 |
|---|---|---|
| `gitTry(cwd, args, env?)` | `git.ts` | 运行 git，不抛错，返回 `{code, stdout, stderr}`。只用于需要原样拿到 git 报错的地方 |
| `worktreeOf(repo, branch)` | `git.ts` | 解析 `git worktree list --porcelain`，返回检出 `refs/heads/<branch>` 的目录，没有就返回 `undefined` |
| `isAncestor(repo, a, b)` | `git.ts` | `git merge-base --is-ancestor a b`，退出 0 为真，1 为假，其他抛错 |
| `loadDeploy(repo)` | `config.ts` | 读仓库根目录**当前**的 `.autoreview.json` 里的 `deploy`。没有就返回 `undefined`。`cmd` 必填；`cmd`、`check`、`rollback` 必须通过现有 `safeRelative`；`timeoutMin` 为 1–240 的整数，默认 20。不合法时抛 `.autoreview.json 的 deploy 不合法：<原因>` |

`loadDeploy` 与 `loadConfig` 分开：`deploy` 写错只影响部署命令，不挡 `启动`。`task.json` 里启动时存下的 `config` 不含 `deploy`，部署一律读当前文件。

## 四、core 新增（通用）

### 1. `LoopError`

```ts
export class LoopError extends Error {
  constructor(public category: string, message: string, public result?: unknown) { super(message); }
}
```

附加步骤失败时抛它。`category` 取 PA 六类之一，`result` 是本次已执行部分的输出。拒绝类仍抛现有 `InputError`（输入问题）。

### 2. `missingChecks(dir, commit, hashes = inputs(taskOf(dir))): string[]`

按 `checks.jsonl` 返回这个 commit 缺的检查，空数组表示检查过：

| 情况 | 返回 |
|---|---|
| 同 commit、同两份哈希下没有复测「通过」或「没验证」 | `复测：没有通过记录` |
| 同 commit、同两份哈希下没有评审「通过」 | `评审：没有通过记录` |
| 同 commit 有记录，但两份哈希都对不上现在的文件 | 另加一条 `提示词或验收标准已变化，原检查不再算数` |

`checked()` 改为 `missingChecks(...).length === 0`，行为不变。

### 3. `annotate(dir, phase, message)` 与 `recordStep(dir, entry, view?)`

`recordStep` 追加一条 `Check`：
- `step`、`result`、`commit`、开始和结束时间、`durationMs`、`evidence`、`detail` 由调用方给；
- `tree` 取这个 commit 的 tree；
- 两份哈希取当前 `inputs()`，读不到提示词时填空字符串（部署不依赖提示词）。

追加后按 `view` 更新状态，规则如下：

| 当前 state | `view.complete = true`（只有合入成功或已在 dev 时传） | 其他结果 |
|---|---|---|
| `completed` | 改 `loop.phase`、`message` | 改 `loop.phase`、`message` |
| `input_required` | `state` 改为 `completed`，`bucket` 置空，改 `phase`、`message` | 不改 |
| `working` / `failed` / `cancelled` | 不改 | 不改 |

最后无论是否改了状态，都重写一次 `summary.md`。

`annotate` 只做上表右列的「改阶段」，不追加记录，用于「部署中」。

**为什么 `input_required` 要改成 `completed`**：到上限转「等你」后，你选「接受未验证」并合入了，这件事就结束了。如果 state 留在 `input_required`，查询和 PA 会一直显示「要你决定」，与事实不符。需求书第六节已同步这一条。

### 4. `summary()` 显示额外步骤

- core 自己的步骤是：开发、复测、评审、等你、dev-loop 自身。
- `checks.jsonl` 里出现的其他 `step`，按首次出现的顺序，插在「等你」和「dev-loop 自身」之间。
- 「结论」取这个步骤最近一条的 `result`；「累计耗时」取它所有记录的 `durationMs` 之和，与表头一致。
- 没做过的步骤不出现。

### 5. 阶段常量与等你原因

- `PHASES`：需求书「阶段枚举」的 19 个值，按表中顺序，写成 `as const`。`Status.loop.phase` 的类型改为其中之一，`transition`、`annotate`、`recordStep` 只接受这些值。
- `WaitReason`：`复测退回到上限 | 评审必修到上限 | 停下没交付 | 需手动接入会话`，存在 `status.loop.wait`。
- `waitFor(dir, reason, message)`：调用 `transition(dir, "input_required", "等你", message, "inputMs")`，并写入 `loop.wait = reason`。`transition` 进入其他阶段时把 `loop.wait` 置空。
- 旧执行的 `status.json` 没有 `wait` 字段，按空处理。

| 位置 | 现在 | 改为 |
|---|---|---|
| `createTask` | 开发中 | 准备中 |
| `resume`，且工作区未就绪（`loop.ready` 为假） | 开发中 | 准备中 |
| `deliver`（非沿用） | 开发中 | 已交付 |
| `settle` 第 49 行：HEAD 与登记的交付不同 | 不改阶段 | 开发中，消息不变 |
| `settle` 到上限 | transition 到等你 | `waitFor(复测退回到上限 / 评审必修到上限)` |
| `settle` 停下没交付 | transition 到等你 | `waitFor(停下没交付)` |
| `launch.ts` Claude/Codex 准备好 | transition 到等你 | `waitFor(需手动接入会话)` |
| `stop(abandon = true)` | 已停止 | 已放弃 |

现有测试里对阶段名的断言随拆分更新，开发方在交付说明里逐条列出改了哪些断言。

## 五、合入（`steps/merge.ts`）

```ts
export function merge(dir: string, o: { commit?: string; acceptUnverified: boolean }): MergeResult
```

全部同步执行，只用本地 git：

1. `t = taskOf(dir)`，`s = statusOf(dir)`，`commit = s.loop.commit`。为空 → `InputError("没有交付记录")`。
2. 给了 `o.commit`：用 `git rev-parse --verify <值>^{commit}` 转成完整 sha。转换失败或与 `commit` 不同 → `InputError("目标已变化：确认的是 X，当前是 Y")`。
3. `missing = missingChecks(dir, commit)`。非空且没加 `acceptUnverified` → `InputError("合入资格不足：<逐项>。确需合入请加 --接受未验证")`。
4. `before = rev-parse refs/heads/dev`。`isAncestor(commit, dev)` 为真 → `recordStep(合入, "已在 dev", view {phase: 已合入, message: "已在 dev <短sha>", complete: true})`，返回。
5. `holder = worktreeOf(repo, "dev")`。没有 → `InputError("dev 没有检出到任何目录，无法合并")`。
6. 合并信息：`Merge <卡名>: reviewed <短sha>`，有缺项时为 `Merge <卡名>: unverified <短sha>`。卡名读 `t.card` 文件的 `name`，读不到就用任务名 `t.name`。
7. 在 `holder` 里运行 `gitTry(["merge", "--no-ff", "--no-edit", "-m", 信息, commit], {GIT_MERGE_AUTOEDIT: "no"})`。
8. 第 7 步失败：
   - 先用 `git diff --name-only --diff-filter=U` 取冲突文件；
   - `git rev-parse -q --verify MERGE_HEAD` 存在就运行 `git merge --abort`；
   - `recordStep(合入, "合入失败", detail = git 原文, view {phase: 合入失败, message: "冲突：<最多 3 个文件>"，没有冲突文件时为 "git 拒绝合并"})`；
   - 抛 `LoopError("输入问题", git 原文, result)`。冲突要人改输入，所以归「输入问题」🔧。
9. 成功：`after = rev-parse refs/heads/dev`。`recordStep(合入, 有缺项 ? "已合入（未验证）" : "已合入", view {phase: 已合入, message: "<after 短sha>"（未验证时为 "<after 短sha>，未验证"）, complete: true})`。

返回：

```json
{ "executionId": "…", "commit": "…", "devBefore": "…", "devAfter": "…",
  "result": "已合入 | 已合入（未验证）| 已在 dev", "unverified": false, "seconds": 0.8,
  "worktree": "<dev 检出目录>", "revert": "git -C '<dev 检出目录>' revert -m 1 <devAfter>" }
```

不碰 main、不改任务分支、不删 worktree、不跑测试，由各步骤只写 dev 这一点保证。不加锁：同一仓库没有发生过并发合入。

## 六、推送（`steps/push.ts`）

```ts
export async function push(dir: string, o: { timeoutMs?: number } = {}): Promise<PushResult>
```

网络命令用现有 `childExec`（进程组、超时），🔧 默认时限 120 秒，测试可注入。

| 步 | 做法 | 结果 / 错误类别 |
|---|---|---|
| 1 | `git remote get-url origin` 失败 | `InputError("没有 origin")`，不写记录 |
| 2 | `git fetch --no-tags origin` | 失败或超时 → 结果「推送失败」，类别「临时故障」 |
| 3 | `refs/remotes/origin/dev` 等于本地 dev | 结果「已推送」，detail「远端已是最新」，不执行 push |
| 4 | 要推的提交：`git rev-list --reverse dev --not --remotes=origin` | 即「dev 上有、origin 任何分支上都没有的提交」 |
| 5 | 密钥扫描（见下） | 命中 → 结果「扫描命中，未推送」，类别「输入问题」；出错 → 结果「扫描出错，未推送」，类别「工具内部错误」 |
| 6 | `git push origin <dev sha>:refs/heads/dev` | 退出 0 → 「已推送」 |
| 7 | 第 6 步非 0：`git ls-remote origin refs/heads/dev`（时限 30 秒） | 等于 dev sha → 「已推送」；不等 → 「推送失败」，类别沿用核心方案第四节「git 推送被拒 → 权限不足」，超时为「临时故障」；核对也失败 → 「推送结果不确定」，类别「未知」，输出核对命令 |

第 1 步通过后、第 2 步之前调用 `annotate(dir, "推送中", "<dev 短sha>")`。

所有结果都用 `recordStep(推送, 结果, commit = dev sha)` 记录，阶段和 message 如下：

| 结果 | 阶段 | message |
|---|---|---|
| 已推送 | 已推送 | `<短sha>` |
| 扫描命中，未推送 | 推送失败 | `扫描命中 N 处` |
| 扫描出错，未推送 | 推送失败 | `扫描出错` |
| 推送失败（远端拒绝） | 推送失败 | `远端拒绝` |
| 推送失败（fetch 或 push 超时、网络错误） | 推送失败 | `网络失败` |
| 推送结果不确定 | 推送结果不确定 | `用 git ls-remote origin refs/heads/dev 核对` |

不加 `--force`，不推标签，不拉取，不重试。项目自己的 git hooks 照常运行。

### 密钥扫描

逐个提交运行：

```
git -c core.quotePath=false diff-tree -p -U0 --no-renames --no-ext-diff --no-textconv --root <sha>
git -c core.quotePath=false diff-tree -r --name-only --diff-filter=A --no-commit-id --root <sha>
```

- 第一条按 `+++ b/<路径>` 和 `@@ … +c,d @@` 计算新增行行号，只检查以 `+` 开头的新增行。二进制文件跳过。
- 第二条拿新增文件名，用于 `.env` 规则。
- 命中输出：`<短sha> <文件>:<行> <规则名>`，**不输出行的内容**。
- 合并提交在 `diff-tree` 默认输出里为空，不单独扫描。它带进来的改动在被合并的提交里已经扫过。人工解决冲突时新写的内容扫不到，这一点写进 README。dev-loop 自己产生的合并遇到冲突就放弃，不会产生这种内容。

🔧 内置规则（规则源码写成不会命中自身的形式，例如 `-{5}BEGIN`；测试要覆盖「扫描 push.ts 本身不命中」）：

| 规则名 | 匹配 |
|---|---|
| 私钥 | `-{5}BEGIN [A-Z ]*PRIVATE KEY-{5}` |
| AWS 访问密钥 | `\b(?:AKIA\|ASIA)[0-9A-Z]{16}\b` |
| GitHub 令牌 | `\bgh[pousr]_[A-Za-z0-9]{36,}` 或 `\bgithub_pat_[A-Za-z0-9_]{50,}` |
| sk- 类 API 密钥 | `\bsk-(?:ant-\|proj-)?[A-Za-z0-9_-]{20,}` |
| Slack 令牌 | `\bxox[abposr]-[A-Za-z0-9-]{10,}` |
| Google API 密钥 | `\bAIza[0-9A-Za-z_-]{35}\b` |
| .env 文件 | 新增文件的文件名是 `.env` 或 `.env.*`，但 `.env.example`、`.env.sample`、`.env.template` 除外 |

不加「`password = "…"`」这类通用规则：误报会挡住推送，又没有放行开关。

## 七、部署（`steps/deploy.ts`）

```ts
export async function deploy(dir: string, o: { commit?: string; timeoutMs?: number } = {}): Promise<DeployResult>
```

1. `cfg = loadDeploy(t.repo)`。没有 → `InputError("项目没有登记部署脚本（.autoreview.json 的 deploy.cmd）")`。
2. `sha`：给了 `o.commit` 就把它 `rev-parse` 成完整 sha，否则取 `refs/heads/dev`。解析失败 → `InputError`。`onDev = isAncestor(sha, dev)`。
3. `tmp = mkdtemp(<系统临时目录>/dev-loop-deploy-)`，`git worktree add --detach <tmp>/src <sha>`。
4. 逐个检查登记的脚本：在 `<tmp>/src` 里必须是普通文件，且 `accessSync(X_OK)` 通过。不满足 → `InputError("脚本不存在或不可执行：<路径>")`，不写记录，进入第 9 步收尾。
5. `stamp` 取本地时间 `YYYYMMDD-HHMMSS`。证据目录 `<执行目录>/deploy-<短sha>-<stamp>/`，日志 `<执行目录>/deploy-<短sha>-<stamp>.log`。调用 `annotate(dir, "部署中", "<短sha>")`。
6. 运行 `cmd`：`childExec(<tmp>/src/<cmd>, [], {cwd: <tmp>/src, timeoutMs, env})`。
   - `env` 含 `LOOP_DEPLOY_COMMIT`、`LOOP_REPO`、`LOOP_EVIDENCE_DIR`。
   - `timeoutMs` 默认 `cfg.timeoutMin × 60000`，测试可注入。
   - 日志依次写入 `$ <脚本>`、完整输出、`退出码 N，用时 X 秒[，超时]`。
7. `cmd` 成功且登记了 `check` → 同样方式运行 `check`。
8. `cmd` 或 `check` 失败（非 0 或超时）且登记了 `rollback` → 运行一次 `rollback`，`env` 另加 `LOOP_DEPLOY_FAILED=cmd|check`。
9. `finally`：`git worktree remove --force <tmp>/src`，再删除 `tmp`。移除失败只写进日志，不覆盖部署结果。

| 情况 | 结果 | 阶段 | 退出码 / 类别 |
|---|---|---|---|
| cmd 成功，check 成功 | 已部署 | 已部署 | 0 |
| cmd 成功，没登记 check | 已部署（未检查） | 已部署 | 0 |
| 失败，rollback 成功 | 部署失败，已回退 | 部署失败 | 1 / 未知 |
| 失败，rollback 失败 | 部署失败，回退也失败 | 部署失败 | 1 / 未知 |
| 失败，没登记 rollback | 部署失败，未回退 | 部署失败 | 1 / 未知 |

脚本失败的原因只有项目自己知道，所以类别统一为「未知」🔧。`raw` 是日志最后 40 行。

message：已部署为 `<短sha>`，没登记 check 时为 `<短sha>，未检查`；部署失败为 `已回退`、`回退也失败` 或 `未回退`。

返回：

```json
{ "executionId": "…", "commit": "…", "onDev": true, "result": "已部署",
  "steps": [{ "name": "cmd", "path": "scripts/deploy.sh", "code": 0, "seconds": 12.3, "killed": false }],
  "log": "…/deploy-ab12cd3-20261110-153000.log", "evidenceDir": "…/deploy-ab12cd3-20261110-153000", "seconds": 15.1 }
```

## 八、pi 阶段显示（`hosts/pi.ts`）

- `Context` 结构类型增加可选的 `hasUI?: boolean` 和 `ui?: { setStatus(key: string, text?: string): void; setTitle(title: string): void }`，核心测试仍不依赖 pi 包。
- `session_start` 登记成功后：
  - 缓存任务名 `taskOf(dir).name`；
  - 立即刷新一次，再用 `options.every(refresh, 1000)` 每秒刷新一次。这是独立于 60 秒心跳的第二个定时器。
- `refresh()` 的行为：
  - 读 `statusOf(dir)`，算出状态栏文字和标题；
  - 与上次相同就跳过，不同就调用 `ui.setStatus("dev-loop", 文字)` 和 `ui.setTitle(标题)`；
  - `ctx.hasUI === false` 或没有 `ui` 时什么也不做；
  - 读状态出错时保留上次的显示，不影响会话。
- 文字规则：
  - 状态栏：`dev-loop【<phase>】<任务名>`，有附加信息时后接 ` · <附加信息>`。
  - 附加信息：评审中为 `第 <loop.reviewRounds> 轮`；等你为 `loop.wait`，旧执行没有该字段时用 message 第一行的前 30 个字；失败为 `error.category`；第 11–19 阶段为 `message`，即各步骤写入的短句（见第五到七节）；其余阶段没有附加信息。
  - 标题：`【<phase>】<任务名>`。
- `agent_before_settle` 处理完后立即调用一次 `refresh()`。
- `session_shutdown`：清掉定时器，调用 `ui.setStatus("dev-loop", undefined)`。

**为什么每秒读一次，而不是做事件通知**：阶段变化有两个来源，pi 进程内的复测、评审，以及其他终端里运行的停止、合入、部署。每秒读一次文件就能同时覆盖两种，只要一个机制。`status.json` 只有几 KB，每秒读一次的开销可以忽略。复测和评审都是异步子进程，运行期间定时器照常触发。需求书第五节「刷新」已同步为「1 秒内」。

旧 loop `kernel-pi.ts` 用的是同一个做法（第 44、80 行）：`session_start` 时保存 `ctx`，每 250 毫秒读一次账本，调用 `setStatus`。本人 11-10 确认实际能显示。可以参照它，但不引用它的代码。

## 九、命令行（`cli/main.ts`）

- 新选项：`--commit <sha>` 只用于合入、部署；`--接受未验证`、`--推送` 只用于合入。用在其他命令上 → `InputError("未知选项…")`。
- `合入`：`dir = select(o)`，`r = merge(dir, …)`。加了 `--推送` 再 `r.push = await push(dir)`。合入抛错时不推送。
- `部署`：`dir = select(o)`，`return await deploy(dir, {commit})`。
- 错误输出：现有 `catch` 改为输出 `{error:{category, raw, result?}}`。`LoopError` 带 `category` 和 `result`；`InputError` 照旧；其他错误照旧按权限不足或工具内部错误归类。
- 从「不支持」列表里去掉合入、部署；帮助文字补上两条命令。

## 十二、流水批次与开发方式

✅ 一个流水批次（11-10 本人）：一张卡、一个任务、启动一次。开发方在同一会话里按需求书「本次任务」的顺序 1→5 做完，每段自测通过再做下一段，全部做完才交付。dev-loop 随后复测、评审，必修退回原会话。

| 项 | 值 |
|---|---|
| 卡 | `docs/batches/合入推送部署-20261110/开发卡.json` |
| 提示词 | `docs/prompt/提示词-合入推送部署与阶段显示.md` |
| 验收标准 | 卡的 `acceptance` 指向需求书，评审能看到 A1–A10 和全部行为 |
| scope | `src/**`、`test/**`、`README.md` |
| test | `PATH=/Users/Admin/.hermes/node/bin:$PATH node --test test/*.test.ts` |
| 上限 | 复测退回 3 次，每次 20 分钟；评审必修 5 次（默认 4 次，改动较大，多给 1 次），每轮 60 分钟 |

✅ 开发方式：dev-loop 开发自己。本人 11-10 已在 dev 上做了首个提交 4fe3e21。

- 开发会话加载的是 dev 检出目录里的 dev-loop（旧代码），改动只在任务工作区，两者互不影响。所以这一批的会话里看不到新的阶段显示，合入后的下一个任务才看得到，需求书 A10 在下一个任务时验。
- 这一批合入时，dev 上还没有 `合入` 命令。可以用任务工作区里的新代码合入它自己：`<任务工作区>/bin/loop 合入 <执行编号>`，顺便实测 A1。
- 运行期间协调方不改需求书和提示词：两份文件的内容哈希是通过资格的一部分，改了会让已有的通过失效。
