# 写法：需求、提示词、验收标准、开发卡、问题单

> 这是唯一的写法来源，其他项目里只放指向这里的链接，不要复制一份。
> 内容迁自旧 loop 的 `README-验收标准.md`，11-09 按 dev-loop 改写，旧文件不再维护。
> 命令、开发卡字段、配置字段以 [README.md](../README.md) 为准，本文不重复。

## 一、流程中的文件

```
需求（docs/requirements/）→ 方案（docs/prompt/方案-*.md）→ 提示词（docs/prompt/提示词-*.md，含验收标准）
  → 开发卡（docs/batches/<批次>/开发卡.json）→ dev-loop 执行 → 结果与评审报告
```

- 一个事实只放在一个权威出处，其他地方用短链接指过去。
- 用户在聊天里拍板的事，协调方当轮写回需求；涉及怎么落地的，再改方案。两者冲突时，先改需求。

## 二、写验收标准

起草需求、任务或提示词时，末尾加一节 `## 验收标准`：

- 每条写「操作」和「预期」。
  - 操作是从外部做的事：执行命令、打开页面、调用接口。
  - 预期是从外部看得到的结果：命令输出、页面内容、接口返回、数据变化、日志。
- 一条只验一个行为，而且要有明确的终点。不写「处理所有边界」「完全正确」这种没法逐条核对的话。
- 只覆盖本次需求。代码结构、命名、性能不写进验收标准。
- 不知道具体命令或地址时，操作写到行为层面即可，不要编造命令名。
- 最多 10 条，按重要程度排列。
- 只用两种标签，按权限划分，不按难易划分：
  - `[授权]`：要用用户的真实账号、凭证或真实外部平台，或者会产生真实后果（真的发出消息、写正式数据、扣费），又没有测试账号或测试环境可以替代。用户亲手写「同意授权：A3」后才能执行；用户写「不授权：A3」，这条就留给用户人工验收。不要替用户写「同意授权」。
  - `[人工]`：需要用户主观判断，比如好不好用、文案是否得体、是不是想要的效果，写不出客观的「预期」。这类条目完成时列给用户看。
  - 一条链路里只有某一步涉及权限时，只把这一步标成 `[授权]`。能用测试账号或录下来的真实输入代替的，照常写成自动验的条目。
- 难做不是不写的理由。图形界面操作、步骤多、耗时长的，照常写。
- 自动执行验收是 dev-loop 第 3 步的附加步骤。这一步实现之前，验收标准由协调方和用户逐条核对。

格式示例：

```markdown
## 验收标准
A1. 操作：执行 `todo add 买菜`
    预期：输出「已添加」
A2. 操作：重启服务后执行 `todo list`
    预期：列表里还有「买菜」
A3. [授权] 操作：用正式账号点「同步到飞书」
    预期：正式飞书表里多一行今天的记录
A4. [人工] 操作：看新首页
    预期：布局和文案是你想要的
```

**多任务批次的写法：**

- 整批的验收标准单独写一个文件，开发卡的 `acceptance` 字段指向它。
- 每条开头标出归属任务，例如 `A3. [乙] 操作：…`。跨任务才会出现的问题，也要指定一个负责的任务。
- `[人工]` 条目不标归属；`[授权]` 条目照常标，例如 `A3. [乙] [授权] 操作：…`。

开发方不能改验收标准。标准要变，由用户确认后修改文件；文件变了，相关结论会自动重新检查。

## 三、写任务提示词

一般分四节：

- **目标**：要什么结果、为什么要，几行就够。
- **已拍板**：用户已经定下、开发方不能改的规则、格式和取舍。没有就写「无」。
- **边界**：允许改哪里，禁止做什么，明确不做什么。
- **验收标准**：按第二节的写法。

不要写这些，写了只会浪费时间和 token：

- 不要求全仓阅读，不手抄 HEAD、哈希和测试数量。需要先定位时，指出相关的定义、调用方和已有测试即可。
- 引用已有的来源文档，不复制大段规则。任务复杂时，补充不能改坏的行为和关键入口，不必硬凑四节。
- 不写联调和端到端测试步骤。
- 「已拍板」里只放用户明确在意的接口、格式和文案，其余交给开发方按现有代码习惯处理。
- 不把无法核实的推断写成「已实现」。

关于交付和测试：

- 不用在提示词里写交付标记。dev-loop 会在会话开头告诉开发方：做完后运行 `bin/loop 交付`。
- 提示词里写明开发方自测要跑什么，只跑本次相关的测试，不跑全量。
- 同一条测试命令写进开发卡的 `tasks[].test`，交付后由 dev-loop 先复跑这条命令，再进入评审。确实没有可跑的测试，就写 `无：原因`，这一项会记为「没验证」，不算通过。
- 写多细跟着风险走。前端界面、样式这类任务写短一些，验证用已有检查加上「改完打开页面看一眼」就够了。

## 四、写开发卡

- 每批一张 version 1 开发卡，放在 `docs/batches/<批次>/开发卡.json`。字段和示例见 [README.md](../README.md) 的「开发卡」一节。
- 流程由协调方写进卡里，不让模型在运行中决定。
- 每个任务都要写：`prompt`、`scope`（只允许改这些路径）、`test`（没有可跑的写 `无：原因`）。
- 单任务可以不带验收。多任务必须带验收，并且每条标明归属任务（dev-loop 第 3 步起支持）。
- 当前支持到哪一步，以 README 为准。还没支持的流程，启动时会被直接拒绝。

## 五、问题单

| 方面 | 写法 |
|---|---|
| 位置和文件名 | 未完成的放 `issues/`，已解决的放 `issues/【history】/`，一张单一个文件。文件名用 `【bug】<简单描述>.md` 或 `【req】<简单描述>.md`，一级标题与文件名（去掉 `.md`）一致。描述只写问题或需求本身，不带状态、日期或处理过程，定下以后不改名 |
| 类型 | `【bug】`：已有行为、实现或流程的缺陷。`【req】`：新能力或改进需求。按正文内容分类，不按修复状态分类 |
| 单头 | 三个固定字段：状态、排期、关联单（根因单、上下游） |
| 状态 | 待修复 → 修复中·<批次名> → 已合入待验·<批次名> → 已解决。已解决时写明关闭原因（完成 / 重复 / 不做），并写清怎么解决的、哪一批、怎么核实的 |
| 正文 | 问题描述、复现步骤、预期结果、环境与证据（写因果链和分层归因，没确认的原因写「待排查」）、本次任务、范围与限制、验收标准、完成后需要提供。不确定的内容写「待补充」 |
| 建单和开批 | 发现问题当轮就建单。同一根因合成一张单。默认先攒着，排批前按同源归并，一批只修一个根因。停摆、数据丢失这类不修就没法用的，排期标「立即修」 |
| 只完成一部分 | 用户核实已完成的部分后，由协调方关掉原单，剩下的另开新单，两张单互相链接 |
| 重复、不做 | 关闭原因写「重复」并链接到主单；不做的写清不做的理由。都由协调方按用户决定关闭 |
| 更新与归档 | dev-loop 不会自动回写或归档问题单。开批、合入、用户验收后，由协调方手动更新单头。已解决的单子移进 `issues/【history】/`，文件名不变，并修好在用文档里的链接 |
| 不做的事 | 不靠改文件名表示状态。开发完成、测试通过或合入，都不等于用户验收通过 |

新建单子用下面的模板（需求单把标题前缀改成 `【req】`）：

```markdown
# 【bug】<简单描述>

状态：待修复
排期：待排期
关联单：无（有根因单、上下游时写链接）

## 问题描述
待补充：问题与影响。

## 复现步骤
待补充：从外部执行的步骤、实际结果。

## 预期结果
待补充：应当看到的结果。

## 环境与证据
待补充：版本、环境、日志或截图路径。
因果链：待排查。
分层归因：待排查。

## 本次任务
待补充。

## 范围与限制
待补充。

## 验收标准
待补充：按本文「写验收标准」写操作和预期。

## 完成后需要提供
待补充：改动说明、验证证据及尚未验证项的入口。
```
