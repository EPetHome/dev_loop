# 写法：需求、提示词、验收标准、开发卡、问题单

> 这是唯一的写法来源，其他项目里只放指向这里的链接，不要复制一份。
> 内容迁自旧 loop 的 `README-验收标准.md`，11-09 按 dev-loop 改写，旧文件不再维护。
> 命令、开发卡字段、配置字段以 [README.md](../README.md) 为准，本文不重复。

## 一、流程中的文件

```
需求（docs/requirements/）→ 方案（docs/prompt/方案-*.md）→ 提示词（docs/prompt/提示词-*.md，含验收标准）
  → 开发卡（docs/batches/<批次>/开发卡.json）→ dev-loop 执行 → 结果与评审报告
```

- 一个事实只放在一个权威出处，其他地方用短链接指过去。
- 用户在聊天里拍板的事，协调方当轮写回需求；涉及怎么落地的，再改方案。两者冲突时，先改需求。

## 二、写验收标准

起草需求、任务或提示词时，末尾加一节 `## 验收标准`：

- 每条写「操作」和「预期」。
  - 操作是从外部做的事：执行命令、打开页面、调用接口。
  - 预期是从外部看得到的结果：命令输出、页面内容、接口返回、数据变化、日志。
- 一条只验一个行为，而且要有明确的终点。不写「处理所有边界」「完全正确」这种没法逐条核对的话。
- 写具体场景，不写在所有路径上都要成立的承诺。「不增加权限」「保持可重试」「迟来反馈照常登记」这类话没有边界，评审能一直找出反例；要保的东西，写成一两条具体场景：做什么操作、给什么输入、看到什么结果。评审只按写出来的场景和真实使用路径判必修（见[评审门槛单](../issues/【req】评审提示词的必修门槛和多轮收敛规则.md)）。出处：W3-C。
- 输入写不完的（自然语言回答、措辞、自由文本），要列样本清单，放进测试数据或批次目录，预期写成「样本清单里的每一条都判对」。样本以外的写法不算必修；想扩大覆盖面，就加样本。出处：W3-D 的验收没列样本，评审连续 13 轮改措辞找反例。
- 只覆盖本次需求。代码结构、命名、性能不写进验收标准。
- 不知道具体命令或地址时，操作写到行为层面即可，不要编造命令名。
- 最多 10 条，按重要程度排列。
- 有功能清单的项目，每条在开头标出它属于功能清单的哪一项，例如 `[F18]`（编号是功能清单里的固定编号）。这条标签决定它挂在功能地图的哪一项下面；没有功能清单的项目不标。
- 档位标签只用两种，按权限划分，不按难易划分；不标的就是自动档，由程序执行：
  - `[授权]`：要用用户的真实账号、凭证或真实外部平台，或者会产生真实后果（真的发出消息、写正式数据、扣费），又没有测试账号或测试环境可以替代。用户亲手写「同意授权：A3」后才能执行；用户写「不授权：A3」，这条就留给用户人工验收。不要替用户写「同意授权」。
  - `[人工]`：需要用户主观判断，比如好不好用、文案是否得体、是不是想要的效果，写不出客观的「预期」。这类条目完成时列给用户看。
  - 一条链路里只有某一步涉及权限时，只把这一步标成 `[授权]`。能用测试账号或录下来的真实输入代替的，照常写成自动验的条目。
- 难做不是不写的理由。图形界面操作、步骤多、耗时长的，照常写。
- 自动档的条目逐步写成 E2E 场景，在复测里执行（[需求-验证闭环](需求-验证闭环.md) D1）；还没写成场景的，由开发方的定向测试覆盖、评审核对。`[人工]`、`[授权]` 条目进批次的 `验收.md`（见下一节）。
- 预期由本人在立项时确认。开发途中本人用答复改了主意，评审按答复判；要正式改标准，按本节末尾的规则办。

格式示例：

```markdown
## 验收标准
A1. [F3] 操作：执行 `todo add 买菜`
    预期：输出「已添加」
A2. [F3] 操作：重启服务后执行 `todo list`
    预期：列表里还有「买菜」
A5. [F3] 操作：`todo add 买菜` 因磁盘满失败；腾出空间后，原样再执行一次
    预期：输出「已添加」，列表里只有一条「买菜」（转换类反例：失败以后重来）
A3. [授权] 操作：用正式账号点「同步到飞书」
    预期：正式飞书表里多一行今天的记录
A4. [人工] 操作：看新首页
    预期：布局和文案是你想要的
```

**多任务批次的写法：**

- 整批的验收标准单独写一个文件，开发卡的 `acceptance` 字段指向它。
- 每条开头标出归属任务，例如 `A3. [乙] 操作：…`。跨任务才会出现的问题，也要指定一个负责的任务。
- `[人工]` 条目不标归属；`[授权]` 条目照常标，例如 `A3. [乙] [授权] 操作：…`。
- 标签的顺序是：归属任务、所属功能、档位，例如 `A3. [乙] [F18] [授权] 操作：…`。

开发方不能改验收标准。标准要变，由用户确认后修改文件；文件变了，旧结论不再放行。正式增删 E2E 场景或检查点时，协调方同时修订功能地图和**开工时使用的源开发卡** `tasks[].e2e`，并按新清单复测。普通澄清不用改清单。

**状态转换清单。** 漏网的问题往往不在单条标准里，而在条目和条目之间的状态转换上：两条分别测都对，串起来才出错。例如 PA046：当时的验收标准分别测了「合法的单子放两次只启动一次」和「不合格的单子不启动」，却没有把「被拒 → 改好开发卡 → 原样重投」串成一条。所以写完验收标准以后，对照下表逐类问一遍：适用的类型，至少写一条把前后状态串起来的反例（格式见上面示例的 A5）；不适用的不硬凑。反例也占「最多 10 条」的名额，但不能挤掉本批已确认的核心交付：能把前后状态合写成一条的就合写，还装不下就拆批。

| 类型 | 写的时候问自己 | 出处（真实漏网或评审发现） |
|---|---|---|
| 失败以后重来 | 被拒或失败以后改好再来一次，会不会被当成重复？ | PA046 |
| 重启前后 | 一切正常的情况下重启一次，会不会误报或者丢状态？ | PA039 |
| 移除以后的残留 | 删掉或移出以后，留下的东西会不会被误判？ | PA024 |
| 时间偏差 | 两个时钟对不上的时候，结果还对吗？ | PA035 |
| 重复 | 同样的事做两次，是不是只算一次？ | PA046 |
| 旧数据 | 旧版本写下的数据，新版本还能读吗？ | promate-v2-agent B1 的评审发现（不是上线后的漏网） |
| 看不到不等于没有 | 系统看不到某样信息时，会不会说成「没有」？ | PA009 |

这张表按复盘结果增删：漏网的问题追到「验收标准没写这一条」，就归到某一类；同一类第 2 次出现、表里又没有，就列为候选，**经本人批准后**才加一行并写上出处，因为每加一行，后续所有适用的批次就多一项必写的要求；长期没再出现过的类型，复盘时可以提出删掉，同样由本人决定。出处见 [漏网问题回放](分析-漏网问题回放.md)。

## 二之二、验收.md

每批在批次目录（和开发卡同一个目录）放一份 `验收.md`，只列需要本人亲手做的条目，也就是 `[人工]` 和 `[授权]` 两类。程序能查的不写进去。**没有这两类条目的批次不建 `验收.md`**，免得多出一份永远在「待验」的文件。

第一行固定写状态，只用下面四种：

| 第一行 | 什么时候写 |
|---|---|
| `状态：待验` | 新建时 |
| `状态：通过` | 本人明确说过「通过」 |
| `状态：不通过` | 本人反馈了问题；第二行链接对应的问题单 |
| `状态：未确认（无反馈）` | 到时没收到反馈：这个项目下一次开工时，或部署满 7 天，以先到的为准 |

- 本人不用去核销。到时没有反馈，协调方就按上表改成「未确认（无反馈）」，提醒随之结束。收单脚本上线以后，这一步由脚本来做。
- 「未确认（无反馈）」和「通过」是两种不同的记录，不混用，也不降低验收标准。
- 「通过」「不通过」和 PA 读取器现有的用词一致；PA 历史上还用过「待验收」「不验」，照样有效。**「未确认（无反馈）」是新加的**：会自己读取 `验收.md` 的项目（目前是 PA），要等它的读取器认识这个状态以后才能写，在那之前保持「待验」不动。
- `[授权]` 条目没做，就在正文里单独列成「授权未做」，保留原来的授权要求，不能视同通过。
- 之后本人再反馈问题，照常建问题单，在「环境与证据」里写明是在哪一批验收时发现的。「引入批次」要有证据才填（老问题也可能在新版本里才被发现），查不到就写「定位不到」。
- dev-loop 只把第一行是「状态：待验」的文件计入「另有 N 批待验」。

## 三、写任务提示词

一般分四节：

- **目标**：要什么结果、为什么要，几行就够。
- **已拍板**：用户已经定下、开发方不能改的规则、格式和取舍。没有就写「无」。
- **边界**：允许改哪里，禁止做什么，明确不做什么。
- **验收标准**：按第二节的写法。

不要写这些，写了只会浪费时间和 token：

- 不要求全仓阅读，不手抄 HEAD、哈希和测试数量。需要先定位时，指出相关的定义、调用方和已有测试即可。
- 引用已有的来源文档，不复制大段规则。任务复杂时，补充不能改坏的行为和关键入口，不必硬凑四节。
- 不写联调和端到端测试的操作步骤。提示词列出本批要实现或复用的场景编号、脚本位置和复测入口；场景的操作步骤和预期，以项目的功能地图为准，不在提示词里另写一套。
- 「已拍板」里只放用户明确在意的接口、格式和文案，其余交给开发方按现有代码习惯处理。
- 预计会让体量明显变大的（新模块、新命令），在「目标」里写出预计增量。超出预算时由本人决定砍什么，不留给开发方压缩。出处：N1 为压到 2000 行合并代码行，见[体量单](../issues/【bug】体量硬上限只数行数，开发为过线合并代码行.md)。
- 项目有体量上限时，提示词写明：碰线就用 `loop 提问` 停下，报出现值、上限和可砍的候选；不许靠合并行、删注释、缩短命名或把代码挪到不计数的位置来过线。
- 不把无法核实的推断写成「已实现」。

关于交付和测试：

- 不用在提示词里写交付标记。dev-loop 会在会话开头告诉开发方：做完后运行 `bin/loop 交付`。
- 提示词里写明开发方自测要跑什么，只跑本次相关的测试，不跑全量。
- 同一条测试命令写进开发卡的 `tasks[].test`，交付后由 dev-loop 先复跑这条命令，再进入评审。确实没有可跑的测试，就写 `无：原因`，这一项会记为「没验证」，不算通过。
- 写多细跟着风险走。前端界面、样式这类任务写短一些，但「版式」一节不能省，写法见三之二。

## 三之二、界面卡

改了页面的卡就是界面卡：新增页面、改布局、加按钮、改文案都算。界面卡的验收写法、评审规则和其他卡一样，只是要多交三样：版式草图、对照草图的人工验收、交付截图。没有这三样，页面长什么样就没有对照标准，问题只能等本人上手才发现。出处：Promate 11-22 到 11-24 连续三次，见[界面卡单](../issues/【req】界面卡的版式要求与项目级界面规范.md)。

**提示词多一节「版式」。** 每个改动的页面画一张文本草图，写明：

- 一条记录占几行，显示哪些字段，按什么顺序；
- 操作怎么分层：主入口、收进「⋯」的、危险操作（放在哪、怎么确认）；
- 空着的时候、出错的时候长什么样；
- 页面上出现的文案原文。

```
已登记文件
┌────────────────────────────────────────────┐
│ 合同-2026.pdf     2.1 MB   11-22   [打开]  ⋯ │   ← 「⋯」里：重命名、移出、删除（红字，二次确认）
│ 报价单.xlsx       340 KB   11-21   [打开]  ⋯ │
└────────────────────────────────────────────┘
空着：「还没有登记文件。把文件拖进 Promate 文件夹即可。」
出错：顶部一行红字原因 +「重试」
```

示例取自 Promate；「一条一行」「主入口只放一个」是 Promate 的界面规矩，不是所有项目的要求。

**草图先给本人看。** 草图随方案一起给本人，本人认可了才开工。草图被否就改草图，不带着没认可的草图开工。

**验收加一条 `[人工]`**：`操作：打开 <页面>　预期：和版式草图一致`。

**交付附截图。** 每个改动的页面一张，空状态、出错状态有改动的也要截，开发方用项目已有的方式打开页面截图。

- 新版 dev-loop 上线前：截图存到 `$LOOP_TASK_DIR/截图/<页面>.png`，交付说明里列出文件名，协调方汇报时核对。
- 新版上线后：开发卡写 `tasks[].版式`（草图文件和页面清单），交付时用 `loop 交付 --截图 <文件…>`；缺了哪一页，dev-loop 就不收货，发回去补截图。字段以 README 为准。

**项目自己的界面规矩不写在这里。** 像 Promate 的「列表一条一行」「主入口只放一个」「详情页组件不叠到列表页」，写进项目仓库的界面规范，由项目 REVIEW.md 引用，评审会读到。本人每指出一次界面问题，协调方就在规范里加一条，写上日期和例子。写在这里还是写进项目，按「换个项目还成立吗」来判断，拿不准先写进项目（[KL1](需求-调度改为看账本补步骤.md)）。

## 四、写开发卡

- 每批一张 version 1 开发卡，放在 `docs/batches/<批次>/开发卡.json`。字段和示例见 [README.md](../README.md) 的「开发卡」一节。
- 流程由协调方写进卡里，不让模型在运行中决定。
- 收尾授权写在卡上，本人开工时一次批准，通过后不再等人：dev-loop 自己的卡默认写 `["开发评审", "测试", "合入", "推送"]`（合入即上线，不需要部署）；其他项目的部署由本人开工时决定是否写进卡。卡上没授权时，本人在完成的窗口里说「合入」作补救。出处：N4 完成后要本人另说「合入」、另批推送，本人 11-25 同意改为开工一次授权。
- 每个任务都要写：`prompt`、`scope`（只允许改这些路径）、`test`（没有可跑的写 `无：原因`）。
- 改页面的卡，在 `tasks[].版式` 里写草图文件和页面清单（三之二；新版上线后生效，字段以 README 为准）。
- 接入 E2E 时，从功能地图选出本批必跑场景与按路径触发的场景，把立项已确认的检查点放进 `tasks[].e2e`。共用模块的路径写入所有受影响场景；新增路径可列为每次必跑。项目仍从 `tasks[].test` [出报告](参考-运行细节.md#e2e-项目报告)。
- 已批准的脚本与测试种子不挪位置；由协调方按功能地图逐项写进本批 `scope.deny`，防止放宽断言或替换种子。本批新增脚本放在允许范围内，协调方按已批准的预期和证据核对后再纳入回归。
- 单任务可以不带验收。多任务必须带验收，并且每条标明归属任务（dev-loop 第 3 步起支持）。
- 当前支持到哪一步，以 README 为准。还没支持的流程，启动时会被直接拒绝。

## 五、问题单

| 方面 | 写法 |
|---|---|
| 位置和文件名 | 未完成的放 `issues/`，已解决的放 `issues/【history】/`，一张单一个文件。文件名用 `【bug】<简单描述>.md` 或 `【req】<简单描述>.md`，一级标题与文件名（去掉 `.md`）一致。描述只写问题或需求本身，不带状态、日期或处理过程，定下以后不改名 |
| 类型 | `【bug】`：已有行为、实现或流程的缺陷。`【req】`：新能力或改进需求。按正文内容分类，不按修复状态分类 |
| 单头 | 固定字段：状态、排期、关联单（根因单、上下游）。`【bug】` 单另加三个字段：<br>**关联批次**：修这张单的批次目录，排批时填。<br>**引入批次**：引入问题的执行编号和 commit；查不到写「定位不到」，不是 dev-loop 交付的代码写「非 dev-loop」。<br>**本该拦住**：按顺序判断，取第一个符合的，并附一句原因。能写成「输入 X → 应得到 Y」、不用把应用跑起来就能复现 → 测试用例；要把应用真正跑起来才会出现 → 功能地图（E2E）；很难稳定复现、但读 diff 看得出来 → REVIEW.md；需求本身没写或外部变化 → 拦不住 |
| 状态 | 待修复 → 修复中·<批次名> → 已合入待验·<批次名> → 已解决。已解决时写明关闭原因（完成 / 重复 / 不做），并写清怎么解决的、哪一批、怎么核实的。收单脚本上线以后，中间两个状态改由脚本现算，单头只写待修复 / 已解决 / 不做 / 重复；上线之前仍由协调方手写 |
| 关单（`【bug】`，完成） | 关单只看修复证据，和批次有没有收到本人反馈无关。三项都满足才关：① 修复批次复测、评审都通过；② 三个新字段都已填好；③ 写明由哪条检查防住（测试名或主路径条目），并且这条检查有「修复前失败、修复后通过」的记录；三层都拦不住的，写明原因。要用真实账号才能证明的，保留授权要求，本人授权或亲自做过才算。关单以后本人再反馈同一问题，就重开 |
| 正文 | 问题描述、复现步骤、预期结果、环境与证据（写因果链和分层归因，没确认的原因写「待排查」）、本次任务、范围与限制、验收标准、完成后需要提供。不确定的内容写「待补充」 |
| 建单和开批 | 发现问题当轮就建单。同一根因合成一张单。默认先攒着，排批前按同源归并，一批只修一个根因。停摆、数据丢失这类不修就没法用的，排期标「立即修」 |
| 只完成一部分 | 已完成的部分满足上面的关单条件后，由协调方关掉原单，剩下的另开新单，两张单互相链接 |
| 重复、不做 | 关闭原因写「重复」并链接到主单；不做的写清不做的理由。都由协调方按用户决定关闭 |
| 更新与归档 | dev-loop 不会自动回写或归档问题单。开批、合入以后，由协调方手动更新单头。只有关掉的单子（已解决 / 重复 / 不做）才移进 `issues/【history】/`，**没关的不许为了清理挪进历史**；移动时文件名不变，并修好在用文档里的链接 |
| 不做的事 | 不靠改文件名表示状态。关单表示修复有证据，不等于本人验收通过；本人验收的状态看批次的 `验收.md`（第二节之后的「验收.md」一节） |

新建单子用下面的模板（需求单把标题前缀改成 `【req】`）：

```markdown
# 【bug】<简单描述>

状态：待修复
排期：待排期
关联单：无（有根因单、上下游时写链接）
关联批次：待排批
引入批次：待查
本该拦住：待判断

## 问题描述
待补充：问题与影响。

## 复现步骤
待补充：从外部执行的步骤、实际结果。

## 预期结果
待补充：应当看到的结果。

## 环境与证据
待补充：版本、环境、日志或截图路径。
因果链：待排查。
分层归因：待排查。

## 本次任务
待补充。

## 范围与限制
待补充。

## 验收标准
待补充：按本文「写验收标准」写操作和预期。

## 完成后需要提供
待补充：改动说明、验证证据及尚未验证项的入口。
```
