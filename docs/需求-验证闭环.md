> 用词
> - **干净状态**：每次开跑前，数据、文件、进程和端口、配置四样都和上一次开跑前一模一样，而且是已知的。
> - **功能地图**：即文章第 2 课的 feature map，也就是笔记 §4.2 的「功能层」。从用户的角度，每个功能一条，写清操作和预期；它既告诉 agent 怎么走，也是评分标准，长期积累。（11-20 以前本文叫它「主路径清单」，现已改回文章的叫法）
> - **E2E 脚本**：按功能地图把应用真正跑起来检查的脚本，由机器跑，不调用模型。
> - **模型逐条验收**：由模型按本批标准逐项操作并取证。D8 待定，现行设计不设独立验收节点。
> - **verify skill**：教 agent 怎么起这个项目、怎么操作、去哪里取证的操作手册，不含检查标准。
> - **REVIEW.md**：项目级的评审规则，写明要防什么、常漏什么、什么不算必修。
> - **窗口原话**：本人在 pi 窗口里直接打的字，不经过 `答复` 或 `续跑 --话`。
> - **漏网**：评审通过以后才发现的 bug。**误报**：评审列为必修、其实不该列的问题。

### 四、三层检查的分工（🔧）

| | 测试用例 | REVIEW.md | 功能地图 |
|---|---|---|---|
| 回答的问题 | 给定输入，这段代码的输出对不对 | 评审看 diff 时，这个项目要盯什么、不用盯什么 | 用户能不能把这件事做完 |
| 谁写 | pi 写代码时一起写 | codex 起草，本人批准 | 预期由本人定（来自验收标准），pi 改不了 |
| 什么时候用 | 每次复测 | 每一轮评审 | 复测：按改动模块挑着跑，另有 1~2 条每次必跑 |
| 抓不住 | 要把应用真跑起来才出的问题；开发方自己没想到的情况 | 运行时才暴露的问题 | 少见分支、内部细节 |
| 怎么增删 | 跟代码一起改 | 漏网同类出现 2 次以上才加；每月剪枝 | 功能新增、修改、删除时同步改 |

一个 bug「本该拦住」按顺序判断，取第一个符合的：能写成「输入 X → 应得到 Y」、不用起应用就能复现 → 测试用例；要真跑应用才出现 → 功能地图；很难稳定复现、但读 diff 看得出来 → REVIEW.md；需求没写或外部变化 → 拦不住。

- dev-loop 从起点 commit 读取，开发方改不了评判自己的规则；本人批准的改动从下一批开始生效。
- 先零代码试：在下一批提示词里加一节「要防 / 不防」，有效果再改 dev-loop 去读 REVIEW.md。
- 第一版内容来自 codex 回查的候选规则，由本人批准。

### 六、E2E 与验收（11-20 已被第七节取代，保留作参考）

> 本节「E2E 放在评审前还是评审后」的分析，以当时设想的独立验证节点为前提。11-20 定为 E2E 不设独立节点（D1 ✅），可以反复跑的场景放进复测。下面的时间账和压缩耗时的办法仍可参考。

**时间账**（复测和评审耗时取实测中位数，E2E 按 5 分钟假设）：

```
放在评审前：每次交付都跑，平均每批 2.5 次 → E2E 约 12.5 分钟
放在评审后：只对评审通过的 commit 跑 1 次 → E2E 约 5 分钟（失败一次多一轮）
对照：16 批待验在等本人，最早的已经等了 8 天
```

**E2E 慢在哪、怎么压**：

| 慢在哪 | 怎么压 |
|---|---|
| 每次都从零起 server、库和 web | 一次执行只起一次环境，每轮只重置数据（秒级） |
| 每次跑全部路径 | 按改动模块挑着跑，另有 1~2 条每次必跑 |
| 用固定 sleep 等就绪 | 轮询就绪信号，设超时 |
| 时好时坏 → 重跑 → 等人 | 不许重试，找根因；修不了就删掉并记录原因 |
| 每一步都让模型想一想 | 回归部分用脚本，不调用模型；只有新功能验收用模型 |

- **干净状态**：每次单独跑，从同一份种子数据重新开始，不接着上一次的数据往下跑。种子可以从历史里沉淀：把出过问题的典型数据挑出来、去掉隐私，冻结成文件放进仓库。
- **两种 E2E 的衔接**：本批验收节点通过 → 这条路径写成 E2E 脚本、并进功能地图 → 以后每一批都会回归它。
- 部署之后的健康检查（例如 web 的 `web_health`）保持不变，它不是 E2E。

### 七、E2E 的两层和接入点

D1 已定。项目说明测什么、怎么操作、在哪里观察结果。通用层在复测时选择本次相关路径和每次必跑路径，执行并保留对应版本的证据。开发方可用项目手册自查。评审能看到正式复测的结果、证据和出错的步骤。

外部环境故障的建议行为见 D20。本人需要看到缺了哪条、原始报错，以及环境恢复后如何继续。产品断言失败按现有返修流程处理。脚本错误和缺失证据应指出原因，不能写成通过。S5 按 D16 单独授权。部署检查只复用适合线上且已获准的路径。

协调方负责项目手册的准确性，按实际未覆盖的步骤更新。场景选跑、证据格式、补跑和合入资格的实现见[实施方案](方案-验证闭环.md)。

### 八、窗口原话（D4 ⏳，其余 🔧）

- 原则不变：agent 不写状态；由代码记录事实，状态从事实推出来。
- pi 插件监听 `before_agent_start` 事件，`messageType` 为 user 时把原话追加到执行目录的 `窗口原话.jsonl`（时间 + 原文）。排除开场提示词，也排除 dev-loop 自己发进去的消息。
- 评审材料多一节「本人在窗口里说的话」。
- Claude/Codex 可以用 UserPromptSubmit hook 做同样的事，等 pi 这边做完再说。

### 九、留痕与汇总（D7 🔧）

- 原始数据是唯一的权威出处，不手改：`checks.jsonl`、`status.json`、`answers.jsonl`、评审原文、问题单、`验收.md`。
- 汇总报告（介入率、返修轮次、漏网数、误报率）在每月剪枝时或本人问起时现生成，带日期，生成以后不再维护。

### 十、检查的内容和闭环做到什么程度（D9、D10 ⏳，其余 🔧）

程序管得了「跑没跑、按什么跑、证据齐不齐」，管不了「查的东西本身对不对」。检查的内容最终都来自本人写的验收标准和问题单，所以内容的质量要靠闭环一次次补上来。

**检查的内容从哪里来**

| 检查 | 内容是什么 | 从哪里来 | 谁定 | 怎么防止内容写错、写弱 |
|---|---|---|---|---|
| 测试用例 | 「输入 → 期望输出」的断言 | pi 写代码时一起写 | pi | 评审会看；修复批次要做防复发证明 |
| 功能地图 + E2E 脚本 | 每条写前置、操作、检查点、预期、清理 | 本批验收标准，验收通过后转写 | 预期由本人定，脚本由 pi 写 | `scope.deny` 保护；防复发证明 |
| 模型逐条验收（要不要做以后再定） | 本批验收标准逐条 | 提示词 | 本人 | 已经和哈希绑定 |
| REVIEW.md | 要防 / 不防、常漏清单、不算必修 | codex 从问题单和历史里起草 | 本人批准 | 批准前做回放（见下） |
| verify skill | 怎么起、怎么操作、怎么取证 | pi 手动跑通后固化 | 协调方 | 每批都跑；从干净状态连跑 5 遍 |

**闭环分四个程度**

| 程度 | 含义 | 现状 |
|---|---|---|
| L0 开环 | 记得就修 | — |
| L1 修好了 | 这个 bug 不在了 | 现在的问题单做到这一层，而且关单还会漏 |
| L2 防住了 | 同样的错再犯，会被某一层自动拦下来，**并且有证明** | 目标：每张单都要做到 |
| L3 检查变准了 | 误报、漏网有数据，规则按数据增删 | 每月做一次 |

**防复发证明（D9 待确认）。** 对有明确修复版本的 bug，用同一条定向检查证明旧版出现原问题、交付版符合预期。测试或场景因环境问题没跑起来，不能用来证明旧版有缺陷。评审规则的证明取原问题改动和已知正常改动作对照。三层都拦不住时写明原因。证明用于关单，实施入口见[方案第六节](方案-验证闭环.md#六g13-怎样证明测试抓到了原问题)。

**一张 bug 单从出现到关闭，每一环靠什么控制**

| 环节 | 靠什么 | 控制方式 |
|---|---|---|
| 发现 | 本人上手试、线上 | 🟡 靠人；E2E 和部署检查能让一部分 bug 更早被发现 |
| 建单 | 本人说一句，协调方当轮建单 | 🟡 靠人 |
| 归因（引入批次、本该拦住） | 协调方或 codex 填 | 🟡 靠人；收单时由程序检查有没有填 |
| 修 | 修复批次走 dev-loop | 🟢 程序 |
| 防 | 补检查 + 防复发证明 | 🟢 程序跑证明，结果写进 `结果.md` |
| 关单 | 收单脚本：修复批次通过 + 字段齐 + 有防复发证明（或写明拦不住），三项都满足才移进 `【history】`；和批次有没有收到反馈无关 | 🟢 程序 |
| 生效 | 以后每批的复测、评审自动用上 | 🟢 程序 |
| 校准 | 每月由脚本生成报告，列出长期没触发或常误报的规则 | 🟡 本人看、本人批 |

**检查本身出错时的闭环**

| 错误 | 闭环 |
|---|---|
| skill 坏了 | 验证过不了，当批就走不下去，只能修好 —— 🟢 程序 |
| 误报（检查报了，其实没问题） | 本人或 codex 标记 → REVIEW.md「不算必修」，或者修掉不稳的测试 → 回放时用对照组确认不再误报 |
| 漏网（检查没报，其实有问题） | 建问题单，按上面的流程走到 L2 |

### 十一、沉淀：痕迹怎么变成「下次不再犯」（D11、D12 ✅，其余 🔧）

判断标准：**下一次会被程序或固定流程自动读到的地方，才叫沉淀下来了。** 写在没人自动去读的地方，只能算留下了记录。

**能放沉淀的地方，以及谁会自动去读**

| 沉淀到哪里 | 谁会自动读 | 什么时候读 | 现状 |
|---|---|---|---|
| 项目测试 | dev-loop 复测 | 每次交付 | 🟢 |
| 功能地图 + E2E 脚本 | 复测 | 每次交付 | 🔴 还没有 |
| REVIEW.md | 评审 | 每一轮 | 🔴 还没有 |
| 项目 AGENTS.md | pi 开发会话（会加载上下文文件） | 每次会话开头 | 🟢 |
| dev-loop 固定说明（`src/hosts/convention.ts`） | pi 开发会话 | 每次会话开头 | 🟢 |
| 通用评审规则（`src/core/review-prompt.md`） | 评审 | 每一轮 | 🟢 |
| 写法文档 | 协调方，写提示词之前必读 | 每次出提示词 | 🟢 |
| verify skill | 开发自查、复测里的 E2E | 每次交付 | 🔴 还没有 |
| 知识库笔记、聊天记录 | 没有人自动读 | — | 🔴 算不上沉淀 |

**沉淀分四步**

```
① 收集（程序）：这一批的全部信号
   必修、小问题、需求疑问、运行差异、停下原因、复测失败、收尾笔记、窗口原话
        ▼
② 比对（程序）：和这个项目的前几批比，同一个信号是不是又出现了
   判断「同一个」的依据：同一文件、同一场景、同一停下原因
   第 1 次 → 记一笔
   第 2 次 → 升为候选，并给出落位建议
        ▼
③ 落位（本人批准）：候选写进上表里某个有人自动读的地方
   哪儿都写不进 → 明确标「接受，不处理」，以后不再提示
        ▼
④ 确认（程序）：下一批里这个信号还出现吗
   还出现 → 落位没起作用，退回 ③
   不再出现，或者防复发证明通过 → 关闭
```

**每种信号落到哪里**

| 信号 | 程序能不能自动收集 | 默认落到哪里 |
|---|---|---|
| 必修 | 能（`checks.jsonl`） | REVIEW.md「常漏清单」或「不算必修」 |
| 小问题、需求疑问 | 能（评审原文格式固定） | 问题单（建单候选）或写法文档 |
| 运行差异 | 能（快照文件） | 问题单，或者修快照脚本 |
| 复测失败 | 能 | 项目测试（已经在这么做） |
| 停下没交付、模型出错 | 能（`facts.stops`） | dev-loop 固定说明或写法文档 |
| 收尾笔记 | 能（E2E 场景的输出） | verify skill |
| 窗口原话 | 能（第八节） | 需求或问题单 |
| 本人上手试发现的 bug | 问题单 | 按第四节的顺序：测试用例、功能地图、REVIEW.md |

拿上面 PA 的例子套一遍：11-11 第 1 次出现，记一笔；同一天下一批第 2 次出现，升为候选，建议落位「问题单 + 修快照脚本」；本人批准以后，后面 7 批就不会继续带着一个没人管的差异往下走。

### 十二、E2E 怎么组织（D15~D17 ⏳，其余 🔧）

项目从功能地图选取用户路径，能从入口操作到用户看见的结果。每条路径有可观察的检查点和预期，失败要能指出步骤，并给出原始证据。日常复测只选本次涉及的路径和少量必跑主路径。遇到不稳的检查要定位原因；退役长期无效的检查由协调方提出、本人决定。首批选 PA 的依据和案例见[漏网问题回放](分析-漏网问题回放.md)。

#### 功能清单、功能地图、E2E 场景怎么串起来（D18、D19 ⏳）

```
功能清单（本人写，产品层）       每一项：编号 · 我看到的样子 · 状态 · 怎么验
   │ 一项功能下面挂 1~N 条路径
   ▼
功能地图（验证层）               每条路径：所属功能 · 前置 · 触发 · 检查点 · 预期 · 清理
   │ 一条路径对应一个场景脚本
   ▼
E2E 场景（脚本位置固定）        由程序执行，结果绑定 commit；「新增 / 已批准」记在功能地图里（D17）
```

功能清单里的「我看到的样子」，就是文章所说「从用户视角写的预期」。功能地图把它拆成可以逐条执行的路径。

| 功能清单的变化 | 立项时 | 验证时 | 验证通过以后 |
|---|---|---|---|
| **新增**一项 | 验收标准从「我看到的样子」写出来，本人在这里确认预期 | 验收节点按验收标准真跑，结果绑定被测版本 | 协调方核对脚本和证据与预期一致，把功能地图里这一条改为「已批准」，脚本不挪（D17）；**对应版本部署成功以后**，功能清单这一项改为「已上线」，「怎么验」写上路径编号 |
| **修改**一项 | 提示词列出受影响的路径：挂在这一项下面的，加上依赖它的；它们的新预期写进「预期变化」（受提示词哈希保护） | 受影响的路径按新预期跑 | 已批准的场景按新预期更新 |
| **删除**一项 | 提示词列出要删的路径，以及依赖它的路径（笔记 §4.2 的例子：上线删除同步以后，新增同步的清理步骤也要跟着改）；**再加一条反向场景：原来的入口或行为确实消失了** | 反向场景和依赖它的路径都要跑；只跑依赖路径的话，旧入口即使还在也可能全部通过 | 对应的路径和场景删除，反向场景保留一段时间；对应版本部署成功以后，功能清单这一项标「已删除」，写明日期和原因 |

体检（D19）查的是上表有没有漏做的地方：程序比对功能清单、功能地图和场景脚本三者，把不一致的地方列给协调方。

#### PA 第一批怎样判断

项目需要能模拟用户操作和外部事件，并观察用户收到的通知、对外请求、内部状态和错误步骤。PA 首批可以使用隔离数据和已有替身，时钟改造或全程日志关联 ID 均不作为前置条件。PA 项目用例与检查点的对应关系、已有手段和选跑约定见[实施方案](方案-验证闭环.md)。

**PA 第一批场景**（出处见 [漏网问题回放](分析-漏网问题回放.md)）

| 编号 | 档位 | 场景 | 断言 | 出处 |
|---|---|---|---|---|
| S1 | 替身 | 保存非默认设置后连续启动两次；停机期间改值后再启动 | 第二次启动不发「设置已生效」；改值后只发一次，并列出真实的旧值和新值 | PA039 |
| S2 | 替身 | 已授权的项目被移出、投递目录保留，下一轮扫描；再新建一个从未授权的错名目录 | 前者不报「不认识」，后者照常提醒 | PA024 |
| S3 | 替身 | 投递一张任务单，因为它指向的开发卡不合法而被拒；**只改开发卡**，再把**内容完全相同**的任务单原样投一次 | 第一次被拒时 dev-loop 替身启动 0 次；重投以后恰好启动 1 次。只要求「同名」会漏掉原故障，因为旧逻辑是按任务单内容判断重复的（PA046 原单验收条件 A1）；另外，合法的任务单原样投两次，仍然只启动一次（A2） | PA046 |
| S4 | 替身 | 投递一张合法任务单，一直跑到收到通知 | **这张任务单恰好收到一次「完成」通知才算通过**；只收到「已停下」，或者收到两次「完成」，都判失败（现有脚本把「✅」和「⏸」都算作通知，第一版就要改掉）。环境没起来时，保留出错的步骤和原始报错，场景记「未验证」。不要求防复发证明 | 原快照场景 3 |
| S5 | 真模型（按批授权，不进复测） | 依次问「worker 在哪注册」「项目分级有什么区别」「升档是否必须先满五次」，每问之后追问「你根据哪里判断」 | 调用了查询工具；回答带出处；看不到的说明缺哪一项，不说成「没有」；不引用旧版本代码 | PA008、PA009、PA013 |

S1~S3 对应的修复都已经合入，可以马上拿修复前的版本做防复发证明：修复前失败、修复后通过。S4 不做这项证明（见上表）。

新增场景来自本批验收标准、问题单和本人批准的复盘候选。协调方按 D17 核对证据后纳入回归，后续按改动范围选跑。防复发证明的适用范围见 D15。

### 十三、陪跑和项目接入（🔧）

**陪跑现在怎么工作**

```
开工时   在起点另起一个 worktree → 复制 localFiles、跑 setup → 运行项目的 snapshot 脚本（替身场景）
         → snapshot-base.json → 删掉这个 worktree
复测后   在交付 worktree 里再运行一次 snapshot 脚本 → snapshot-<commit>.json
         → 两份逐字段比，得出「运行差异」→ 原样放进评审材料，供评审参考
部署时   部署前、check 通过后各采一次线上快照 → 存进证据目录；`对比` 命令可以拿来比较
```

它本来要做的是文章第 2 课说的**差分测试**：同样的场景，改动前和改动后各跑一遍，看结果有没有变。思路是对的，但现在只有 PA 登记了脚本，而且断在四个地方：

| 断点 | 后果 |
|---|---|
| 差异只是给评审作参考，没有规定「变了」算什么 | 评审最多写成小问题 |
| 差异里混着耗时、token 数这类每次都会变的字段 | 真信号被淹没 |

| 线上快照没有人读 | 白采 |
