# dev-loop

一张开发卡，跑完「开发 → 交付 → 复测 → 独立评审 → 返修或完成」。
卡上约定了收尾的，评审通过后由 `bin/loop` 自己走完合入、部署、推送，不调用模型；没约定的就停在「完成」。

- **只做核心这一圈**：合入、部署、推送是可选的附加步骤；整合、验收、多任务本步不做。
- **结论绑定交付版本和输入**：commit、提示词和验收标准的内容；接入 E2E 时再绑定场景清单。输入变化后，旧结论不再放行。
- **没验证就是没验证**：不伪造测试或评审通过；程序跑通不等于本人验收。
- **安全边界**：不碰 main、不强推、只推 `origin/dev`、不 stash/reset 你的改动、不读旧 loop 的运行数据。

下面示例里的 `bin/loop` 指 dev-loop 仓库里的可执行文件；在其他项目里使用时写它的绝对路径，或先做个别名。

## 快速开始

要求 Node ≥22.19，项目里有本地 `dev` 分支。不需要装 npm 包，也不需要构建。

**1. 在项目里写一张卡**，例如 `docs/batches/小改动/开发卡.json`：

```json
{
  "version": 1,
  "name": "小改动",
  "nature": "开发",
  "base": "dev",
  "target": "dev",
  "host": "pi",
  "flow": ["开发评审", "测试"],
  "tasks": [{
    "name": "甲",
    "prompt": "../../prompt/提示词-小改动.md",
    "scope": { "allow": ["src/example.ts", "test/**"] },
    "test": "node --test test/*.test.ts"
  }],
  "limits": {
    "测试": { "maxRepairs": 3, "timeoutMin": 20 },
    "开发评审": { "maxRepairs": 4, "timeoutMin": 60 }
  }
}
```

**2. 启动**——校验卡、建 worktree、在后台开会话：

```sh
bin/loop 启动 docs/batches/小改动/开发卡.json
```

**3. 开发，做完交付**——项目[接入验证手册](docs/参考-运行细节.md#pi-开发验证手册)后，可在 Pi 中用 `/skill:verify` 自查。做完后提交范围内改动并登记 commit：

```sh
bin/loop 交付 --说明 '改了什么、怎么自测的'
```

**4. 看结果**——复测和独立评审自动跑，通过即完成或自动收尾，有必修回原会话返修：

```sh
bin/loop 查询 <执行编号> --json
```

## 命令

| 命令 | 作用 |
|---|---|
| `启动 <卡> [--派单编号 X] [--指令编号 Y]` | 校验卡、建 worktree 和会话；只表示已接收，后台完成准备后才算真正开始 |
| `交付 [--说明 文本\|--text-file 文件]` | 提交允许范围内的改动，登记 commit，进入复测/评审 |
| `查询 [<卡或执行编号>\|--all] [--brief] [--json]` | 看状态；`--all --brief` 一次看全部，不调用模型，只在待本人确认时查 Git |
| `续跑 <卡或执行编号> [--话 文本\|--text-file 文件]` | 从「等你」继续；带话会送进原开发会话 |
| `续跑 <执行编号> --交付提交 <完整SHA>` | 查询给出此选项时，核对并登记现有提交，后台继续复测和评审 |
| `续跑 <执行编号> --接受环境缺项 <尝试编号>` | 仅查询显示可接受时可用；登记本次外部环境缺项，然后评审，不把缺项写成通过 |
| `答复 <卡或执行编号> (--话 文本\|--text-file 文件)` | 只在你等时接收本人原话，追加记录后按带话续跑 |
| `停止\|放弃 <卡或执行编号>` | 停止保留现场；放弃删除 worktree，保留分支和证据 |
| `证明 <执行编号>` | 用同一份测试材料对照历史旧版和登记交付版；只记录防复发证据，不参与合入、评审或部署 |
| `合入 <执行编号或卡路径> [--commit <sha>] [--接受未验证] [--推送]` | 合入最后一次交付；默认仅本地 dev，加 `--推送` 才推 `origin/dev` |
| `部署 <执行编号或卡路径> [--commit <sha>]` | 用项目登记的脚本临时检出部署 |
| `收尾\|退回\|陪跑\|释放 <执行编号或卡路径>` | 自动收尾、线上回退、留痕、清理工作区 |
| `对比 <执行编号> [<另一个执行编号>]` | 比两次部署后的快照，只报差异，不判断好坏 |
| `帮助` | 打印全部参数 |

命令前加 `bin/loop`；可用 `--json` 输出单行 JSON，指定执行的命令可用 `--task 名` 核对任务名。成功时 stdout 是 JSON；失败时 stderr 是 `{error:{category,raw,result?}}`，退出码 1。

`next` 决定接力；部署的 `deploy.cmd`、`check`、`rollback`、`deploy.env` 见项目配置。执行根目录用 `LOOP_TASKS_ROOT`，开发方优先用 `LOOP_TASK_DIR` 定位任务。「停下没交付」时查询可给出 `loop.deliveryConfirmation`；Claude/Codex 的原话未送达时需在窗口里说。

## 开发卡

文件里的路径都相对卡文件所在目录；`scope` 相对仓库根目录。

| 字段 | 必填 | 说明 |
|---|---|---|
| `version` | 是 | 固定 `1` |
| `name` | 是 | 卡名，会进合入提交说明 `Merge <卡名>: reviewed <短sha>` |
| `nature` | 是 | 固定 `开发` |
| `base` | 否 | 任务分支起点，默认等于 `target`；必须是已存在的本地分支，不能是 main |
| `target` | 是 | 固定 `dev` |
| `host` | 否 | `pi`（默认）/ `claude` / `codex` |
| `flow` | 是 | 按 `开发评审, 测试, 合入, 部署, 推送` 顺序的不重复子序列 |
| `tasks` | 是 | 本步只支持 1 个任务 |
| `tasks[].name` | 是 | 任务名 |
| `tasks[].prompt` | 是 | 提示词文件，必须在仓库内、≤200KB |
| `tasks[].scope` | 是 | `{ "allow": [...], "deny": [...] }`，也接受字符串数组；支持 `*`、`**`、`?` |
| `tasks[].test` | 选了测试则填写 | 项目现有测试命令；写 `无：原因` 记为「没验证」 |
| `tasks[].e2e` | 否 | 场景数组：每项有 `id`、`checks`，可填仓库相对 `paths` 和已获准的外部 `dependencies`。见下文 |
| `tasks[].proofs` | 否 | 防复发证明声明数组；启动时固定，交付后手工运行。见下文 |
| `limits` | 否 | `测试` / `开发评审` / `部署` 各自的 `maxRepairs`、`timeoutMin` |
| `acceptance` | 否 | 验收标准文件，参与结论绑定 |
| `next` | 否 | 下一张卡，相对卡目录；用于批次接力 |

限额默认值：测试 3 次返修 / 20 分钟，开发评审 4 次 / 60 分钟，部署 2 次 / 20 分钟。

### 复测用户场景（可选）

```json
"e2e": [
  {"id":"S3", "paths":["src/delivery/**"], "checks":["原单重投", "合法单去重"]},
  {"id":"S4", "checks":[{"id":"完成通知条数", "expected":1}], "dependencies":["隔离通知服务"]}
]
```

本次从开工起点到交付提交的**累计改动**命中 `paths` 就跑（含改名两端和删除，匹配同 `scope`）；不填 `paths` 则每次必跑。不另开节点，仍由 `tasks[].test` 执行，零个场景也跑普通检查。清单必填检查点名称，可同时固定 JSON 标量预期（例如条数）；脚本负责实际操作和产品断言。[项目报告与诊断格式](docs/参考-运行细节.md#e2e-项目报告)。

- 声明 `e2e` 却没有可运行命令：开工提示，复测记「没验证」，不满足正常合入和接力资格。未接入的旧卡仍按原约定处理 `无：原因`。
- 接入后，正常合入、自动收尾和接力要求当前输入下的复测「通过」或「本人接受环境缺项」，以及对应评审通过。正式改场景清单后须重新检查；挪走历史证据不会作废结论。
- `查询` 的 `loop.retest` 给出最近复测结果；接入卡另有尝试编号 `attempt`、缺项 `missingScenarios`、`canAccept`、原文路径及过期标记 `stale`。历史可查执行目录的 `checks.jsonl`。

### 防复发证明（可选）

```json
"proofs": [{
  "issue":"PA046", "scenario":"S3", "checkpoint":"原单重投",
  "before":"07e7738", "beforeActual":0, "expected":1,
  "testFiles":["test/retry.mjs","test/fakes/queue.mjs","test/seeds/order.json"],
  "test":"node test/retry.mjs"
}]
```

- `before` 可省略，默认开工起点；显式本地提交引用在启动时解析为完整 SHA。`testFiles` 逐个列出测试、替身、种子和需带入旧版的辅助文件，路径相对仓库根；项目须在 `.autoreview.json` 登记 `proofTestDirs`（如 `["test"]`），两端的这些目录只保留清单内材料，生成物请放在别处。场景用 `scenario` + `checkpoint`；定向单元用例改填 `testName`，不需要声明 `e2e`。
- `expected` 是修复后的业务期望值，`beforeActual` 是问题单描述的旧版实得值，两者须是不同的 JSON 标量。旧版须在目标断言处以指定旧值失败，交付版须在同一处通过且命令成功；不把编译失败、漏跑用例等当作旧版错误。两类脚本的[报告和退出码约定](docs/参考-运行细节.md#防复发证明报告)。
- 交付登记后运行 `bin/loop 证明 <执行编号> --json`，工作区释放后也可做。回执的 `proofs` 逐项给「已证明 / 未证明」和证据路径（两者都是成功出记录，不靠 CLI 退出码判断证明通过）。尝试保存在执行目录 `proofs/`、`checks.jsonl`，批次 `结果.md` 按问题单链接；归档损坏时保留原尝试并在 `ignoredAttempts` 写原因，不补登记或复用。证明不改复测或评审结论，不拦合入，也不自动关单。

### flow 决定卡跑到哪里

- `["开发评审","测试"]`：完成即停。
- 再加 `合入`：停在「已合入」；再加 `部署`：停在「已部署」；再加 `推送`：停在「已推送」。
- 写 `部署` 或 `推送` 必须先写 `合入`；`提交` 不要写进 flow（交付时已提交）；`验收`、`整合` 本步不支持。
- 评审通过后由脱离开发会话的独立进程收尾，关掉开发窗口也继续；同一 commit 只自动发起一次，走完之前不报完成。
- 自动收尾不会替你「接受未验证」；资格不够、冲突、部署失败回退、推送失败都会转「等你」。
- 用 `next` 串批次：中间批通过后不动 dev，自动启动下一批；整条链在启动前检查，坏卡、环、中间批带收尾都直接拒绝。
- 卡上约定了合入时，全部约定的收尾成功后自动释放干净工作区。有未提交文件就保留。接力中间批保留工作区。
- 收尾结束在卡目录追加 `结果.md`，记版本、时间、dev 前后、证据、退回原因和恢复入口。

## 项目配置

项目根目录可放 `.autoreview.json`（可选）：

```json
{
  "localFiles": [".env.local"],
  "setup": "npm ci",
  "reviewerModel": "astra",
  "reviewerThinking": "xhigh",
  "reviewerCmd": "./reviewer.sh",
  "snapshot": "scripts/snapshot.sh",
  "deploy": {
    "cmd": "scripts/deploy.sh",
    "check": "scripts/deploy-check.sh",
    "rollback": "scripts/deploy-rollback.sh",
    "timeoutMin": 20,
    "env": { "APP_DIR": "/path/to/app" }
  }
}
```

- `localFiles`：建 worktree 后复制进去的本机文件，不参与交付。
- `setup`：准备命令，跑一次；失败保留原始输出，可修好环境后续跑。证明在两版各自运行登记的命令，不复制 `localFiles`。
- `proofTestDirs`：证明可移植材料所在的测试目录；只对声明了证明的任务生效，在开工时固定。
- `reviewerCmd`：自定义评审脚本。不配就用 `pi -p` 全新只读会话，关掉扩展、MCP、技能和上下文文件。
- `snapshot` / `deploy.*`：留痕和部署脚本，都填**仓库内可执行文件的相对路径**，不是 shell 命令串。
- `deploy.env`：键须大写（`^[A-Z][A-Z0-9_]*$`）、不能以 `LOOP_` 开头，不放密钥；改值下次部署生效。
- 不登记 `deploy` 就等于关闭部署；部署要 `cmd`，自动部署还要求 `check` 和 `rollback`。

**Pi 验证手册（可选，不用加配置字段）**：项目把 `.pi/skills/verify/SKILL.md`（`name: verify`，带 `description`）提交到开工版本即接入。开工、重开续跑只显式加载当前任务工作区的这一个文件，不开启技能自动发现。手册用于开发自查，不替代开发卡的测试命令，不进入独立评审。

## 状态与「等你」

内部状态只有 `working`、`input_required`、`completed`、`failed`、`cancelled`；对外显示 21 个阶段（准备中、开发中、已交付、复测中、评审中、等你、完成……收尾中、已退回）。

转「等你」有七种原因，对应下一步：

| 原因 | 下一步 |
|---|---|
| 复测退回到上限 / 评审必修到上限 | `续跑` 再给一轮、`停止`，或 `合入 --接受未验证` |
| 停下没交付 | 查询显示当前提交可交付时，可按完整 SHA 确认；需要继续开发时用 `续跑` |
| 模型出错 | 查看原错后用 `续跑` 继续 |
| 需手动接入会话 | 按回执手工接入 Claude/Codex，再 `续跑` |
| 收尾没走完 | `续跑` 回开发，或 `收尾` 手工接手 |
| 复测环境未就绪 | 修复环境后用不带话的 `续跑` 原版本补跑，或 `停止`；仅普通检查已通过且查询允许时，可按当前尝试编号明确接受缺项 |

除「复测环境未就绪」外，「等你」时可用 `答复` 留下本人原话，之后评审会把答复一起带上。答复不改提示词和验收标准，也不作废已有结论。环境等待不增加返修次数；`答复` 和带话 `续跑` 只返回合法操作，不启动开发。

## 数据与证据

默认放在 `~/.dev-loop/tasks/<执行编号>/`，`LOOP_TASKS_ROOT` 可改根目录；开发方优先用 `LOOP_TASK_DIR` 定位任务。

- `task.json`：启动时写一次；`status.json`：原子重写，带递增 seq。
- `checks.jsonl`：检查、合入、推送、部署的结果与耗时。
- `answers.jsonl`：本人答复原文，只追加。
- `窗口原话.jsonl`：仅 dev-loop 管理的 Pi 开发窗口，按提交顺序追加原文和时间。后续静态评审仅供参考；与正式要求冲突时列「需求疑问」，不改变权限、验收标准或已有检查结论。
- `summary.md`：结论和各阶段耗时。
- 测试、评审原文在同目录；接入卡每次复测独立保存 `e2e/<尝试编号>/`。证据缺失不会把已通过的结论作废。

## 协调工具：开工复盘、收单和体检

独立入口 `node tools/coordinate.ts`，不由核心调用。只处理 `--project` 指定的项目；不代投递、不运行项目脚本、不改规则、测试预期或上线状态。项目外调用请给脚本的绝对路径。

| 命令 | 预览内容 |
|---|---|
| `开工 --project <项目目录> --card <待开工的卡>` | 上一批的信号及出处、重复候选、可关单及缺项、到期提醒、项目体检；当月尚未存档时生成月报 |
| `查询 --project <项目目录>` | 查看复盘/收单；不把本次调用算作下一次开工，仍检查已发生的开工和部署满七天 |
| `体检 --project <项目目录>` | 四类接入检查、功能/场景/脚本的提示，不设开工门槛 |
| `月报 --project <项目目录> [--month YYYY-MM]` | 按请求现场重算，含指标分母、未知和剪枝候选；默认本机当前月 |
| `候选决定 --project <项目目录> --decision <本人决定.json>` | 预览登记本人已作出的「接受不处理」或「已批准」；工具不替本人批准或修改规则 |

- `--card` 和 `--changed <路径>` 相对于项目根目录；可重复给 `--changed`，重命名给出新旧路径，删除给出旧路径。已有执行时可读起点到交付的 Git 改动。`--tasks-root` 可覆盖 `LOOP_TASKS_ROOT`（默认 `~/.dev-loop/tasks`）。
- 默认**只读**。核对 JSON 的 `project`、`changes` 和 `blocked` 后，用**同一命令及参数**加 `--apply <planId>` 才写入。变动已失效时重新预览；中断时用 `incomplete` 中的原编号重试。归档文件不改名，撞名不覆盖。日志、月报、决定和移动前的原件保存在项目内 `.dev-loop-coord/`，建议从 Git 排除。
- 项目的验收读取器已识别「未确认（无反馈）」或确认无读取器以后，才加 `--acceptance-ready`（或登记 `acceptanceReaderReady: true`）。否则只列到期项；无反馈不等于通过，授权没做的逐项保留。

**PA 的稳定调用**：用 Node 启动 `/Users/Admin/Desktop/dev-loop/tools/coordinate.ts`，参数数组 `['开工','--project', 项目绝对路径, '--card', 卡路径]`。只查流程只调预览；正式投递前展示 `previous`、`candidates`（`needsDecision: true` 才需再请本人决定）、`blocked`、`health` 等，再按调用方已获准的范围应用 `planId`，之后仍走原来的投递入口。PA 的读取器尚未迁好时不要带 `--acceptance-ready`。工具结果的 `protocol` 为 `coordinate-report/1`；`changes` 附拟写路径和内容摘要，`applied.results` 给每项实际结果（`applied` / `conflict`）及原件位置，`applied.complete: false` 表示有冲突未应用。`issues`、`acceptances` 是预览时的视图，写完可另调 `查询` 取现状。命令失败时退出 1，stderr 为 `{error:{category,raw}}`。体检提示和待授权不阻断开工，也不能当作授权。

## 自检

在 dev-loop 仓库根目录：

```sh
node --test test/*.test.ts
bash -n bin/loop bin/pi-dev
```
