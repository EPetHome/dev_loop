# dev-loop

一张开发卡，跑完「开发 → 交付 → 复测 → 独立评审 → 返修或完成」。
卡上约定了收尾的，评审通过后由 `bin/loop` 自己走完合入、部署、推送，不调用模型；没约定的就停在「完成」。

- **只做核心这一圈**：合入、部署、推送是可选的附加步骤；整合、验收、多任务本步不做。
- **结论只绑定三样东西**：commit、提示词内容、验收标准内容。改了任何一个，旧结论就不算数。
- **没验证就是没验证**：不伪造测试或评审通过；程序跑通不等于本人验收。
- **安全边界**：不碰 main、不强推、只推 `origin/dev`、不 stash/reset 你的改动、不读旧 loop 的运行数据。

下面示例里的 `bin/loop` 指 dev-loop 仓库里的可执行文件；在其他项目里使用时写它的绝对路径，或先做个别名。

## 快速开始

要求 Node ≥22.19，项目里有本地 `dev` 分支。不需要装 npm 包，也不需要构建。

**1. 在项目里写一张卡**，例如 `docs/batches/小改动/开发卡.json`：

```json
{
  "version": 1,
  "name": "小改动",
  "nature": "开发",
  "base": "dev",
  "target": "dev",
  "host": "pi",
  "flow": ["开发评审", "测试"],
  "tasks": [{
    "name": "甲",
    "prompt": "../../prompt/提示词-小改动.md",
    "scope": { "allow": ["src/example.ts", "test/**"] },
    "test": "node --test test/*.test.ts"
  }],
  "limits": {
    "测试": { "maxRepairs": 3, "timeoutMin": 20 },
    "开发评审": { "maxRepairs": 4, "timeoutMin": 60 }
  }
}
```

**2. 启动**——校验卡、建 worktree、在后台开会话：

```sh
bin/loop 启动 docs/batches/小改动/开发卡.json
```

**3. 开发，做完交付**——提交范围内改动并登记 commit：

```sh
bin/loop 交付 --说明 '改了什么、怎么自测的'
```

**4. 看结果**——复测和独立评审自动跑，通过即完成或自动收尾，有必修回原会话返修：

```sh
bin/loop 查询 <执行编号> --json
```

## 命令

| 命令 | 作用 |
|---|---|
| `启动 <卡>` | 校验卡、建 worktree 和会话；只表示已接收，后台完成准备后才算真正开始 |
| `交付 [--说明 文本\|--text-file 文件]` | 提交允许范围内的改动，登记 commit，进入复测/评审 |
| `查询 [<卡或执行编号>\|--all] [--brief] [--json]` | 看状态；`--all --brief` 一次看全部，不调 git 和模型 |
| `续跑 <卡或执行编号> [--话 文本\|--text-file 文件]` | 从「等你」继续；带话会送进原开发会话 |
| `续跑 <执行编号> --交付提交 <完整SHA>` | 查询给出此选项时，核对并登记现有提交，后台继续复测和评审 |
| `答复 <卡或执行编号> (--话 文本\|--text-file 文件)` | 只在你等时接收本人原话，追加记录后按带话续跑 |
| `停止\|放弃 <卡或执行编号>` | 停止保留现场；放弃删除 worktree，保留分支和证据 |
| `合入 <执行编号或卡路径> [--commit <sha>] [--接受未验证] [--推送]` | 把最后一次交付合进本地 dev；加 `--推送` 才推 `origin/dev` |
| `部署 <执行编号或卡路径> [--commit <sha>]` | 用项目登记的脚本临时检出部署 |
| `收尾\|退回\|陪跑\|释放 <执行编号或卡路径>` | 自动收尾、线上回退、留痕、清理工作区 |
| `对比 <执行编号> [<另一个执行编号>]` | 比两次部署后的快照，只报差异，不判断好坏 |
| `帮助` | 打印全部参数 |

命令成功时 stdout 是 JSON；失败时 stderr 是 `{error:{category,raw,result?}}`，退出码 1。

## 开发卡

文件里的路径都相对卡文件所在目录；`scope` 相对仓库根目录。

| 字段 | 必填 | 说明 |
|---|---|---|
| `version` | 是 | 固定 `1` |
| `name` | 是 | 卡名，会进合入提交说明 `Merge <卡名>: reviewed <短sha>` |
| `nature` | 是 | 固定 `开发` |
| `base` | 否 | 任务分支起点，默认等于 `target`；必须是已存在的本地分支，不能是 main |
| `target` | 是 | 固定 `dev` |
| `host` | 否 | `pi`（默认）/ `claude` / `codex` |
| `flow` | 是 | 按 `开发评审, 测试, 合入, 部署, 推送` 顺序的不重复子序列 |
| `tasks` | 是 | 本步只支持 1 个任务 |
| `tasks[].name` | 是 | 任务名 |
| `tasks[].prompt` | 是 | 提示词文件，必须在仓库内、≤200KB |
| `tasks[].scope` | 是 | `{ "allow": [...], "deny": [...] }`，也接受字符串数组；支持 `*`、`**`、`?` |
| `tasks[].test` | 选了测试则必填 | 测试命令；写 `无：原因` 记为「没验证」 |
| `limits` | 否 | `测试` / `开发评审` / `部署` 各自的 `maxRepairs`、`timeoutMin` |
| `acceptance` | 否 | 验收标准文件，参与结论绑定 |
| `next` | 否 | 下一张卡，相对卡目录；用于批次接力 |

限额默认值：测试 3 次返修 / 20 分钟，开发评审 4 次 / 60 分钟，部署 2 次 / 20 分钟。

### flow 决定卡跑到哪里

- `["开发评审","测试"]`：完成即停。
- 再加 `合入`：停在「已合入」；再加 `部署`：停在「已部署」；再加 `推送`：停在「已推送」。
- 写 `部署` 或 `推送` 必须先写 `合入`；`提交` 不要写进 flow（交付时已提交）；`验收`、`整合` 本步不支持。
- 评审通过后由脱离开发会话的独立进程收尾，关掉开发窗口也继续；同一 commit 只自动发起一次，走完之前不报完成。
- 自动收尾不会替你「接受未验证」；资格不够、冲突、部署失败回退、推送失败都会转「等你」。
- 用 `next` 串批次：中间批通过后不动 dev，自动启动下一批；整条链在启动前检查，坏卡、环、中间批带收尾都直接拒绝。
- 卡上约定了合入时，全部约定的收尾成功后自动释放干净工作区。有未提交文件就保留。接力中间批保留工作区。
- 收尾结束在卡目录追加 `结果.md`，记版本、时间、dev 前后、证据、退回原因和恢复入口。

## 项目配置

项目根目录可放 `.autoreview.json`（可选）：

```json
{
  "localFiles": [".env.local"],
  "setup": "npm ci",
  "reviewerModel": "astra",
  "reviewerThinking": "xhigh",
  "reviewerCmd": "./reviewer.sh",
  "snapshot": "scripts/snapshot.sh",
  "deploy": {
    "cmd": "scripts/deploy.sh",
    "check": "scripts/deploy-check.sh",
    "rollback": "scripts/deploy-rollback.sh",
    "timeoutMin": 20,
    "env": { "APP_DIR": "/path/to/app" }
  }
}
```

- `localFiles`：建 worktree 后复制进去的本机文件，不参与交付。
- `setup`：准备命令，跑一次；失败保留原始输出，可修好环境后续跑。
- `reviewerCmd`：自定义评审脚本。不配就用 `pi -p` 全新只读会话，关掉扩展、MCP 和上下文文件。
- `snapshot` / `deploy.*`：留痕和部署脚本，都填**仓库内可执行文件的相对路径**，不是 shell 命令串。
- `deploy.env`：键须大写（`^[A-Z][A-Z0-9_]*$`）、不能以 `LOOP_` 开头，不放密钥；改值下次部署生效。
- 不登记 `deploy` 就等于关闭部署；部署要 `cmd`，自动部署还要求 `check` 和 `rollback`。

## 状态与「等你」

内部状态只有 `working`、`input_required`、`completed`、`failed`、`cancelled`；对外显示 21 个阶段（准备中、开发中、已交付、复测中、评审中、等你、完成……收尾中、已退回）。

转「等你」只有六种原因，对应下一步：

| 原因 | 下一步 |
|---|---|
| 复测退回到上限 / 评审必修到上限 | `续跑` 再给一轮、`停止`，或 `合入 --接受未验证` |
| 停下没交付 | 查询显示当前提交可交付时，可按完整 SHA 确认；需要继续开发时用 `续跑` |
| 模型出错 | 查看原错后用 `续跑` 继续 |
| 需手动接入会话 | 按回执手工接入 Claude/Codex，再 `续跑` |
| 收尾没走完 | `续跑` 回开发，或 `收尾` 手工接手 |

「等你」时可以用 `答复` 留下本人原话，之后评审会把答复一起带上；答复不改提示词和验收标准，也不作废已有结论。

## 数据与证据

默认放在 `~/.dev-loop/tasks/<执行编号>/`，`LOOP_TASKS_ROOT` 可改根目录；开发方优先用 `LOOP_TASK_DIR` 定位任务。

- `task.json`：启动时写一次；`status.json`：原子重写，带递增 seq。
- `checks.jsonl`：检查、合入、推送、部署的结果与耗时。
- `answers.jsonl`：本人答复原文，只追加。
- `窗口原话.jsonl`：仅 dev-loop 管理的 Pi 开发窗口，按提交顺序追加原文和时间。后续静态评审仅供参考；与正式要求冲突时列「需求疑问」，不改变权限、验收标准或已有检查结论。
- `summary.md`：结论和各阶段耗时。
- 测试、评审原文在同目录；证据缺失不会把已通过的结论作废。

## 自检

在 dev-loop 仓库根目录：

```sh
node --test test/*.test.ts
bash -n bin/loop bin/pi-dev
```

测试只在系统临时目录里建仓库和提交，origin 用本地裸仓库，部署/评审用脚本替身，宿主用模拟事件和假的 pi API，不调用真实模型、GitHub 或终端。技术测试不等于业务验收。
